# 运维控制台型前端优化设计

## 1. 背景

当前 Binlog Server 前端已经具备统一的视觉风格和较完整的运维功能，包括任务总览、任务列表、筛选、批量创建、详情抽屉、集群概览等核心能力。整体上它已经比常见内部运维页面更完整，但首页的信息层级还不够清晰，导致“所有内容都重要”的视觉结果：

- 告警、失败、延迟等真正需要优先处理的信息没有被显著突出。
- 任务表格承担了展示、跳转、操作等多种职责，导致扫描成本偏高。
- 详情抽屉已经承载大量上下文，但仍未成为默认的主操作中心。
- 左侧筛选和源库反查对日常盯盘场景的优先级略显平均，没有完全围绕“发现异常 → 定位任务 → 处理问题”的主流程组织。

因此，这次优化不追求“产品官网式美化”，而是聚焦值班、巡检、排障场景，将页面重心收敛为高效的运维控制台。

## 2. 目标

本次设计目标如下：

1. 让用户进入首页后的前 3 秒内，能快速判断当前是否存在异常任务、失败任务、延迟任务。
2. 让任务列表更适合“快速扫描 + 定位异常”，而不是在每一行中承载过多操作负担。
3. 让详情抽屉成为主要的任务处理入口，统一承载关键状态、事件轨迹与任务操作。
4. 让筛选项优先服务日常运维动作，而不是平均服务所有次要场景。
5. 在不推翻现有前端技术栈和交互基础的前提下，以较低成本获得明显的可用性提升。

## 3. 不做什么

本次设计不包含以下方向：

- 不追求营销化、品牌化、展示化的大幅视觉改版。
- 不优先考虑移动端复杂交互设计，重点仍是桌面运维场景。
- 不引入新的复杂导航体系或多路由产品结构。
- 不重做全部组件风格，只优化当前页面的信息架构、视觉层级和核心操作流。

## 4. 目标用户

### 4.1 主要用户：运维/DBA/平台值班人员

这类用户关注：

- 当前有哪些任务异常。
- 哪些任务存在复制延迟、停止、失败、健康下降。
- 进入详情后能否快速拿到 checkpoint、复制状态、事件时间线和操作入口。
- 在高密度信息下是否仍能快速定位优先级最高的问题。

### 4.2 次要用户：实施/交付/系统维护人员

这类用户关注：

- 如何快速创建、编辑、批量导入任务。
- 如何根据源库或 cluster_key 做任务检索与核对。
- 如何在已有控制台内完成基础配置和排查。

## 5. 核心设计原则

### 5.1 告警优先

首页首先服务“异常发现”，不是服务“展示完整信息”。
高风险内容必须比中性统计信息更醒目。

### 5.2 列表负责发现，抽屉负责处理

列表用于快速扫描与定位问题。
详情抽屉用于承载完整上下文、操作入口和排障信息。

### 5.3 控制认知负荷

对运维用户来说，信息密度可以高，但必须有清晰主次。
不是减少信息，而是重排信息优先级。

### 5.4 一致的状态语义

状态不能只靠颜色区分，必须配合图标、文案和排序权重。
状态表达要统一，减少理解成本。

### 5.5 低风险渐进优化

尽量基于现有 Vue + Element Plus 页面结构演进，不以大规模推翻式重构为前提。

## 6. 推荐方案

推荐采用“告警优先控制台”方案。

该方案的核心思想是：

- 首页第一屏优先回答“哪里有问题”。
- 任务表只保留扫描和进入详情所需的核心交互。
- 详情抽屉成为唯一的高密度处理界面。
- 次要能力（如源库反查）降级为辅助区域或折叠区。

相比“双栏指挥台”或“纯列表工作台”，该方案更适合当前代码结构和已有组件组织方式，能够在较低改造成本下得到最明显的体验收益。

## 7. 页面结构设计

### 7.1 顶部 Header

Header 继续保留品牌识别和全局操作，但语义上更偏“控制台首页”。
建议保留：

- 页面标题
- 全局刷新
- 新建任务
- 批量创建
- 设置

建议优化：

- 弱化装饰性描述文案，强化当前页面职责说明。
- 将“刷新”视觉上提升为日常高频动作。
- 减少顶部区域的视觉占高，给异常信息留更多第一屏空间。

### 7.2 告警优先 KPI 区

当前的 KPI 卡片建议重排为两层：

第一优先级：
- 异常任务
- 失败任务
- 延迟任务

第二优先级：
- 运行中任务
- 总任务
- 正常任务

设计要求：

- 第一优先级卡片具备更高视觉对比度和更强提示性。
- 数字、状态名、图标形成稳定的视觉模板。
- 卡片点击后可直接联动筛选，例如点击“异常任务”后过滤任务表。

这样首页不再只是“概览卡片排列”，而是具备明确的运维入口语义。

### 7.3 左侧筛选区

左侧区域建议从“平均功能分布”调整为“运维优先级分布”。

建议保留为两部分：

1. 常用筛选
   - 状态
   - 健康度
   - 延迟区间
   - cluster_key
   - worker / ownership 维度（如已有可用数据）

2. 辅助工具
   - 源库反查
   - 低频检索项

设计要求：

- 常用筛选始终可见。
- 源库反查改为折叠卡片、次级面板或标签页，不与主筛选同权。
- 筛选结果应即时反馈到任务列表和 KPI 状态。

### 7.4 任务列表

任务列表是首页最核心区域，应服务“快速扫表、快速看风险、快速进入详情”。

建议优化如下：

- 默认按风险优先级排序，而不是按中性字段排序。
- 高风险任务（异常、失败、停止、高延迟）优先展示。
- 每行动作简化，不再摆放过多按钮。
- 每行建议只保留一个显性主入口，例如“详情”或点击整行进入详情。
- 其余操作迁移到详情抽屉中处理。

视觉上建议：

- 状态列强化语义权重。
- 延迟和健康度使用更醒目的标签模式。
- 行 hover 不只是颜色变化，可增加更清晰的聚焦反馈。
- 重要列固定排序逻辑，避免运维扫描路径不稳定。

### 7.5 详情抽屉

详情抽屉应升级为“任务处理中心”。

建议在抽屉内统一组织以下模块：

- 基本信息
- 复制状态
- Checkpoint / GTID / 当前文件位置
- Cluster / Lease / Worker 状态
- 上传与文件状态
- 事件时间线
- 启动、停止、编辑、重试上传等操作

设计要求：

- 抽屉顶部固定任务名称、状态标签和关键操作按钮。
- 关键信息优先显示，原始字段和次要字段放到下层信息卡片。
- 时间线、事件流和状态摘要尽量在一个上下文中闭环。
- 危险操作与普通操作区分明显，避免误触。

这会显著降低任务表每行的操作复杂度，同时保留完整可操作性。

## 8. 交互设计

### 8.1 扫描流程

首页默认流程应为：

1. 看第一屏 KPI，判断是否存在异常。
2. 看任务列表前几行，定位高风险任务。
3. 点击任务进入详情抽屉。
4. 在抽屉中完成诊断与处理。
5. 返回列表继续下一个任务。

### 8.2 操作策略

建议将任务操作分成两级：

- 一级：进入详情
- 二级：在详情中执行启动、停止、编辑、删除、重试上传等动作

这样可以：

- 减少首页误触概率。
- 降低表格噪声。
- 让所有关键操作都发生在上下文充分的区域。

### 8.3 筛选联动

KPI 卡片、筛选器、任务列表建议形成单一联动体系：

- 点击 KPI 卡片，自动应用对应筛选。
- 手动调整筛选后，列表与指标一起刷新。
- 页面应始终明确告诉用户“当前显示的是哪类任务”。

## 9. 视觉设计建议

### 9.1 视觉层级

本次视觉优化不依赖大量新装饰，而是依赖层级更明确：

- 高风险信息：高对比、高强调
- 常规信息：中等权重
- 背景信息：低干扰

### 9.2 色彩策略

建议颜色语义更稳定：

- 危险：失败、异常、不可恢复问题
- 警告：延迟、健康下降、待处理
- 正常：运行中、健康
- 中性：总数、背景统计、说明信息

避免大量浅色标签彼此看起来差异不大。

### 9.3 文案与术语

建议统一为中文运维术语体系，必要时保留技术名词，但命名风格需一致。

例如：

- Cluster Lease、Run History、ObjectKey 这类词建议统一表达方式。
- 标签、按钮、卡片标题、抽屉字段不要出现明显混搭的语气与语言。

### 9.4 动效与反馈

保留轻量动画即可，但不应喧宾夺主。
运维场景里，状态变更反馈比装饰动效更重要。

建议：

- 强化加载、刷新、操作成功、失败提示的一致性。
- 谨慎使用装饰性动效。
- 适当考虑 reduced motion 支持。

## 10. 可用性与可访问性

需要重点关注以下问题：

1. 状态不能只依赖颜色，还应配合图标和文案。
2. 表格中的小按钮数量应减少，点击目标要更明确。
3. 重要状态需要更好的对比度。
4. 图标按钮或带图标文案按钮应具备明确语义。
5. 危险动作应有清晰确认与分区，不建议依赖突兀的原生浏览器确认框风格。

## 11. 分阶段落地建议

### 第一阶段：低成本高收益

- 调整 KPI 排序与视觉强调
- 精简任务表行内操作
- 强化状态标签语义
- 调整左侧筛选优先级
- 统一页面术语与文案风格

### 第二阶段：结构优化

- 把详情抽屉升级为主处理中心
- 建立 KPI、筛选器、任务列表联动
- 重构任务详情的信息分组与操作分层

### 第三阶段：工程整理

- 将单页中的大块结构拆分为组件
- 抽取统一状态标签、指标卡、详情区块等复用组件
- 为后续 UI 演进建立更稳定的样式与交互基线

## 12. 验收标准

如果本次优化成功，应满足以下结果：

1. 用户进入首页后能更快识别风险任务。
2. 任务表更容易扫描，单行视觉噪声明显下降。
3. 详情抽屉成为清晰、稳定的任务处理中心。
4. 常用筛选更贴近值班与巡检场景。
5. 页面整体依然保持当前实现基础上的轻量演进，而不是大范围推翻。

## 13. 结论

本次前端优化最合适的方向不是“更花哨”，而是“更像真正的运维控制台”。

推荐围绕以下三个核心动作推进：

- 先把异常、失败、延迟抬到首页最显眼的位置。
- 再把任务表从“动作堆叠区”改成“风险扫描区”。
- 最后把详情抽屉升级为主处理中心。

这样既符合 Binlog Server 的产品属性，也最符合当前前端代码结构可承受的演进成本。
