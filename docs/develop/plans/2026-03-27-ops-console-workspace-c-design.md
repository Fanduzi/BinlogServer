# Ops Console Workspace C 方案设计

## 1. 背景

当前前端管理台已具备任务、源库、Worker、告警等能力，但页面信息密度高且能力混放：

- 源库反查与运维筛选全局常驻，导致各页面职责边界不清。
- 用户通过 URL 分享页面时，虽然已支持基础深链，但“页面语义 + 页面内工作流”仍不完整。
- 左侧导航在交互和布局上与目标参考（vben/chatgpt 类侧栏）仍有偏差。

用户明确要求采用 **C 方案**：以产品视角重构为“工作区模型”，先统一信息架构，再做交互细化。

## 2. 目标

1. 将管理台拆分为按职责聚焦的工作区页面，而非“大一统单屏”。
2. 每个工作区具备明确目标、就地工具和可分享 URL。
3. 左侧导航成为稳定的全局骨架：整列占位、可折叠、折叠按钮位于左下。
4. 支持后续向“视图预设、批量工作流、跨页搜索”演进，不推翻现有 API 层。

## 3. 非目标

- 不在本期引入全新前端框架或 UI 库。
- 不重写后端 API 契约。
- 不一次性实现全部高级能力（如多租户、权限矩阵、跨集群聚合）。

## 4. 信息架构（IA）

### 4.1 一级工作区

1. `/#/overview` 总览  
   展示全局健康、关键 KPI、风险趋势摘要。
2. `/#/tasks` 任务  
   任务列表、筛选、批量操作、详情入口。
3. `/#/sources` 源库  
   源库覆盖、源库反查、源域分布。
4. `/#/workers` Worker  
   Worker 在线状态、负载分布、Lease 视角。
5. `/#/alerts` 告警  
   异常/失败/延迟任务聚焦与处置入口。

### 4.2 工具归属原则

- 运维筛选：只属于 `tasks`（`alerts` 可继承一部分只读筛选状态）。
- 源库反查：只属于 `sources`。
- 集群整体摘要：`overview` 和 `workers` 可见，其他页面不常驻。

## 5. 交互设计

### 5.1 导航

- 左侧整列侧栏固定占位，不做悬浮卡片。
- 折叠后仅保留图标态，折叠按钮固定在侧栏左下。
- 导航项密度对齐“高频工具栏”场景（避免过大行高造成低信息效率）。

### 5.2 URL 深链

- 一级页面通过 hash path 表达：`/#/tasks`、`/#/sources` 等。
- 页面内关键模式通过 query 表达：如 `/#/tasks?mode=alerts`。
- 复制 URL 后，同事可直接落到相同工作语境。

### 5.3 状态模型

- 全局状态：认证、时间参考、全局搜索词（预留）。
- 页面状态：`tasksFilters`、`sourcesLookup`、`alertsMode` 等，互不污染。
- 筛选状态可按页面持久化（localStorage）作为后续迭代点。

## 6. 数据与风控

### 6.1 Lease 风险判定

针对 mock 与本地时间错位，Lease 风险不应一律显示“风险”。  
判定基准优先采用 `dashboard.generated_at`，无有效值时回退系统当前时间。

### 6.2 告警视图

`alerts` 页面只聚焦：

- `replication = ABNORMAL | DELAYED`
- 或 `task state = FAILED | RETRY_BACKOFF`

并保持与任务详情联动。

## 7. 方案对比

### A：样式微调
- 优点：快。
- 缺点：不解决能力混放与工作流断层。

### B：中等拆分
- 优点：成本可控。
- 缺点：对“工作区”抽象不足，后续扩展仍会拥堵。

### C（本方案）
- 优点：信息架构清晰、可深链、可演进。
- 缺点：改动面较大，需要分阶段验收。

## 8. 验收标准

1. 五个工作区 URL 均可直接访问与分享。
2. 源库反查不再出现在 tasks/overview/workers 页面。
3. 运维筛选不再全局常驻，仅在 tasks（及必要的 alerts）上下文出现。
4. 左侧导航折叠按钮位于左下，展开/折叠后布局稳定。
5. KPI 与页面行为一致，无“某个卡片跳转特例”。

## 9. 风险与缓解

- 风险：一次性改动模板较大，容易引入回归。  
  缓解：分阶段提交 + e2e 回归（导航/深链/筛选/详情）。
- 风险：用户期望偏向“功能参考”而非“UI 复刻”。  
  缓解：只对齐布局语义与交互位置，不复制品牌视觉。
