# 第 1 章：我们要解决什么问题

在深入代码之前，我们需要先理解：**这个系统为什么存在？它要解决什么问题？**

## 1. 背景：MySQL Binlog 备份的痛点

### 1.1 什么是 Binlog

MySQL 的 binlog（二进制日志）记录了所有数据变更操作。它的核心用途：

1. **主从复制**：从库通过 binlog 同步主库的数据变更
2. **数据恢复**：通过 binlog 重放，可以将数据恢复到任意时间点
3. **增量备份**：binlog 本身就是增量备份的载体

### 1.2 传统备份方式的问题

假设你管理着 10 个 MySQL 实例，需要备份它们的 binlog。传统做法可能是：

```bash
# 在每台 MySQL 服务器上
mysqlbinlog --read-from-remote-server --host=127.0.0.1 --port=3306 \
  --user=repl --password=xxx --stop-never mysql-bin.000001 > /backup/binlog.log
```

**这种方式的问题：**

| 问题 | 具体表现 |
|------|----------|
| **分散管理** | 每个实例单独配置、监控，运维成本高 |
| **状态不可见** | 备份到哪个位置了？延迟多少？不知道 |
| **断点难恢复** | 脚本挂了，从哪里继续？需要手动查 |
| **资源竞争** | 备份进程和业务进程在同一台机器，互相影响 |
| **无高可用** | 备份进程挂了，没人接管 |

## 2. Binlog Server 的解决方案

### 2.1 核心思路

**把 binlog 备份从"分散的脚本"变成"集中管理的服务"。**

```
┌─────────────────────────────────────────────────────────────┐
│                      Binlog Server                          │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐       │
│  │ Task A  │  │ Task B  │  │ Task C  │  │ Task D  │  ...   │
│  │ MySQL-1 │  │ MySQL-2 │  │ MySQL-3 │  │ MySQL-4 │       │
│  └────┬────┘  └────┬────┘  └────┬────┘  └────┬────┘       │
│       │            │            │            │              │
│       ▼            ▼            ▼            ▼              │
│  ┌─────────────────────────────────────────────────┐       │
│  │              本地存储 / 云存储                    │       │
│  └─────────────────────────────────────────────────┘       │
└─────────────────────────────────────────────────────────────┘
        ▲
        │ API 调用（创建任务、启停、查询状态）
        │
┌───────┴───────┐
│   运维人员     │
└───────────────┘
```

### 2.2 一句话描述

**Binlog Server 是一个集中式的 MySQL binlog 备份服务，它作为 MySQL 的"伪从库"，持续拉取 binlog 并存储到本地或云存储。**

### 2.3 关键能力

| 能力 | 说明 |
|------|------|
| **统一管理** | 一个服务管理所有实例的备份任务 |
| **可视状态** | 通过 API/UI 查看每个任务的进度、延迟、错误 |
| **断点恢复** | 记录 checkpoint，重启后自动从断点继续 |
| **灵活起点** | 支持从最新位置、指定文件位置、GTID 开始 |
| **可选上传** | 支持将 binlog 上传到 S3/OBS 等对象存储 |
| **高可用** | 支持集群部署，worker 故障时自动接管 |

## 3. 系统边界：它是什么，不是什么

### 3.1 它是

- **备份工具**：持续备份 binlog 到存储
- **管理平台**：提供 API 管理多个备份任务
- **监控数据源**：提供 metrics 和事件供观测

### 3.2 它不是

- **不是数据恢复工具**：它只负责备份，不负责恢复
- **不是全量备份**：它只处理 binlog（增量）
- **不是实时同步**：它有延迟（通常秒级）

## 4. 两种部署模式

### 4.1 Standalone（单机模式）

```
┌───────────────────────────────┐
│        单进程                  │
│  ┌───────┐  ┌───────┐        │
│  │  API  │  │ Runner │        │
│  └───────┘  └───────┘        │
│  内存存储（重启丢数据）         │
└───────────────────────────────┘
```

**适用场景：** 开发、测试、小规模部署

### 4.2 Cluster（集群模式）

```
┌──────────────────┐     ┌──────────────────┐
│  Control Plane   │     │     Worker       │
│  ┌────┐          │     │  ┌────┐          │
│  │API │          │     │  │Run │          │
│  │UI  │          │     │  │ner │          │
│  └────┘          │     │  └────┘          │
└────────┬─────────┘     └────────┬─────────┘
         │                        │
         └────────┬───────────────┘
                  ▼
         ┌────────────────┐
         │  MySQL 元数据库 │
         │  (任务/租约/...) │
         └────────────────┘
```

**适用场景：** 生产环境，需要高可用

## 5. 本章小结

| 问题 | 解决方案 |
|------|----------|
| 分散管理 | 集中式服务，统一 API |
| 状态不可见 | 提供实时状态查询和 metrics |
| 断点难恢复 | 持久化 checkpoint |
| 无高可用 | 集群模式 + 租约机制 |
