# 第 2 章：最小可行架构（MVP）

上一章我们理解了系统要解决的问题。现在让我们从**最简单的实现**开始，看看一个"能用"的 binlog 备份服务需要什么。

## 1. MVP：50 行代码能做什么

假设我们只想要一个最简单的功能：**连接 MySQL，拉取 binlog，写到本地文件**。

### 1.1 核心代码（伪代码）

```go
// 伪代码：最小 MVP
func main() {
    // 1. 连接 MySQL
    conn, _ := mysql.Connect("root:pass@tcp(127.0.0.1:3306)")

    // 2. 注册为从库
    serverID := 12345
    conn.RegisterSlave(serverID)

    // 3. 请求从最新位置开始
    pos, _ := conn.GetBinlogPosition()

    // 4. 循环读取 binlog 事件
    file, _ := os.Create("binlog.000001")
    for {
        event, _ := conn.ReadBinlogEvent()
        file.Write(event.Bytes)
        file.Sync()  // 确保写入磁盘
    }
}
```

### 1.2 这个 MVP 能做什么

| 能做 | 不能做 |
|------|--------|
| 拉取 binlog | 管理多个任务 |
| 写入文件 | 知道进度（延迟、位置） |
| 持续运行 | 断点恢复（重启从头开始） |
| | 通过 API 控制 |
| | 上传到云存储 |

### 1.3 这个 MVP 的问题

**问题 1：重启后从哪里继续？**

进程挂了重启，我们不知道上次拉到哪里了。只能从头开始，或者手动指定位置。

**问题 2：怎么知道备份进度？**

运维人员想知道：现在备份到哪个文件了？延迟多少？这个 MVP 没有提供任何查询能力。

**问题 3：怎么管理多个实例？**

要备份 10 个 MySQL 实例，就要启动 10 个进程，各自配置、各自监控。

## 2. 进阶：加上任务管理

为了解决问题 2 和问题 3，我们需要一个**任务管理层**。

### 2.1 引入 Scheduler

```
┌─────────────────────────────────────┐
│              Scheduler               │
│  ┌─────────┐  ┌─────────┐          │
│  │ Task 1  │  │ Task 2  │  ...     │
│  │ state   │  │ state   │          │
│  └────┬────┘  └────┬────┘          │
│       │            │                │
│       ▼            ▼                │
│  ┌─────────┐  ┌─────────┐          │
│  │ Runner1 │  │ Runner2 │          │
│  └─────────┘  └─────────┘          │
└─────────────────────────────────────┘
```

**Scheduler 的职责：**

1. 维护任务列表（内存中）
2. 管理任务状态（PENDING, RUNNING, STOPPED）
3. 启动/停止对应的 Runner

### 2.2 引入 API 层

```
┌─────────────────────────────────────┐
│              HTTP API               │
│  POST /tasks     创建任务           │
│  GET  /tasks     列出任务           │
│  POST /tasks/1/start  启动任务      │
│  POST /tasks/1/stop   停止任务      │
└───────────────┬─────────────────────┘
                │
                ▼
┌─────────────────────────────────────┐
│              Scheduler               │
│  (任务状态管理)                      │
└─────────────────────────────────────┘
```

## 3. 这个架构还有问题吗？

### 3.1 问题：重启丢状态

**场景：** 你创建了 10 个任务，都在运行。服务器重启后...

```
重启前：
  tasks: { "1": RUNNING, "2": RUNNING, ... "10": RUNNING }

重启后：
  tasks: {}  // 全没了！
```

**根本原因：** 任务状态存在内存里，进程退出就丢失。

### 3.2 问题：不知道进度

**场景：** 运维问"任务 1 现在拉到哪里了？"

```
你能回答：
  - 任务状态是 RUNNING
  - 但不知道：当前文件名？位置？延迟多少？

你需要：
  - 登录服务器
  - ls 看文件
  - 对比 MySQL 当前位置算延迟
```

### 3.3 问题：无法断点恢复

**场景：** 任务拉到 mysql-bin.000010 的位置 5000，进程挂了。

```
重启后：
  - 从哪里开始？不知道
  - 只能从头开始（重复备份）
  - 或者手动查文件，猜测位置
```

为了解决上述问题，我们需要：

## 6. 本章小结

1. **MVP**：最简单的实现只需要 连接 MySQL + 读取 binlog + 写文件
2. **任务管理**：引入 Scheduler 统一管理多个任务，提供 API 控制
3. **遗留问题**：重启丢状态、不知道进度、无法断点恢复
