# BinlogServer 升级指南

从当前运行的版本升级到目标版本之前，按从新到旧的顺序读完两者之间的每一条说明。每条都写明这一版有没有迁移、有没有新增或改变的配置项，以及重启前后要做的操作。需要更新 schema 的版本，启动前先用新版 `migrate` 执行 `./migrate up`。

README 只写最新版本。逐版本说明放在这里，完整发布说明在 [docs/releases/](../../releases/)：`vX.Y.Z.zh-CN.md`（中文）和 `release-notes-vX.Y.Z.md`（English）。带版本号的条目从 v0.5.62 开始。有几条标题里没有版本号：紧跟 v0.5.67 的两条（standalone 任务密钥、健康评估器）属于 v0.5.67；v0.5.62 之后的五条涉及 v0.5.57 至 v0.5.61；最后一条（地板仍是 schema 6，000007/000008/000009 可选）和其后指向 v0.5.67 发布说明的链接属于 v0.5.65 至 v0.5.67。更早的版本请看它们的发布说明。英文版见 [upgrade.md](upgrade.md)。

## 逐版本说明

- **v0.5.83：支持 MySQL 8.4 LTS（#555），每个 PR 验证原地升级（#557），没有迁移，也没有新配置项：** binlog 状态语句按 `VERSION()` 选择：MySQL 8.4 及以上用 `SHOW BINARY LOG STATUS`，更早的 MySQL 和 MariaDB 用 `SHOW MASTER STATUS`，带回退列表和按 `host:port` 的缓存，8.4 上 LATEST 启动和追平检查不再以 `ERROR 1064` 失败。支持的源库是 MySQL 5.7、8.0、8.4 LTS 和 MariaDB 10.3+。`e2e-upgrade-failback` 每个 PR 跑四档，包括从 v0.5.82 原地升级。修复 #437：在线 `migrate up` 到 000010 之后，已被保留策略删掉的行在下一轮补上 `retention_removed_at`，不再写第二条 `RETENTION_REMOVED`。v0.5.82 用同一个 schema 和配置，可以安全回滚，但它在 MySQL 8.4 上不能启动 LATEST 任务。已知问题：#559（两个 standalone 共用一个 `meta_dsn` 会互传封存段，请各用一个 meta 库）、#558（P4）、#556、#440（P3）。
- **v0.5.82：健康指标、推荐告警规则和通用 webhook（#545，ADR 0013），没有迁移，新增可选 `notify.*`：** `/metrics` 对本节点评估的每个任务输出 `binlog_server_task_healthy{task_id,reason}`（没有任务时是哨兵 `{task_id="",reason="ok"} 1`），另有 progress age、upload lag、open CRITICAL 三个 gauge。`deploy/prometheus/binlog-server-alerts.yml` 是推荐规则，CI 里用 promtool 测。`notify.webhook_url`（空就是关）、`notify.webhook_token`、`notify.timeout_sec`、`notify.attempts`、`notify.backoff_ms` 在健康状态变化和 CRITICAL finding 转移时 POST 一批 JSON；不跟随重定向，失败的一批只留在内存里。`health.evaluator` 默认仍是 `off`，要每任务序列和 webhook 需设为 `on`，并抓取每一个节点。v0.5.81 用同一个 schema 且忽略 `notify.*`，可以安全回滚。已知问题：#549（`cluster.role: worker` 没有 `/metrics`）、#550、#551（P3）。
- **v0.5.81：HTTP 关停变快，race 测试变确定（#535），没有迁移，没有新配置项：** 关停时控制面和 worker 健康服务先关掉空闲 keep-alive 连接和还没发请求的连接，有空闲客户端时 `SIGTERM` 不再等最多 5 秒；在途请求仍有 5 秒。这类客户端会看到连接被关闭并重连，和任何一次重启一样。`race-and-vet` 跑 `go test -race` 不再跳过任何测试，冷评估遍历在 CI 里用 strace 系统调用数和字节数封顶。修复 #439、#490、#504、#526、#534。v0.5.81 用同一个 schema 和配置，可以安全回滚。已知问题：#541、#540、#386（P3）、#510。
- **v0.5.80：源库、meta 库和 S3 的 TLS（#536，ADR 0012），没有迁移，`upload.use_ssl` 默认改为 `true`：** 没写 `upload.use_ssl` 的明文 HTTP 对象存储，升级后每次上传和 HEAD 都失败：`/api/health` 返回 503，reason 为 `UPLOAD_TLS`，提示 `set upload.use_ssl: false`；复制继续，段留在本地为 `UPLOAD_FAILED`。启动只有一条 WARN，没有「默认值已改」的日志。升级前写上 `upload.use_ssl: false`；写上并重启后待传段会补传。新增可选的 `source.tls`（按任务）和 `meta.tls`，模式为 `disabled`（默认，旧配置仍是明文）、`preferred`、`required`、`verify-ca`、`verify-identity`；`preferred` 信任服务端问候包，可被降级为明文，需要防护时用 `required` 或 verify 模式。新增 `upload.tls.ca_file`，用于私有 CA 的对象存储。`./migrate --config` 套用 `meta.tls`（#537）。新增指标 `binlog_server_upload_tls_failures_total`。v0.5.79 用同一个 schema，可以回滚二进制，但它不读 TLS 配置项，没写 `upload.use_ssl` 时走 HTTP，并会在任务下一次状态变化时丢掉 `source.tls`。已知问题：#541、#540（P3）、#510。
- **v0.5.79：ADR 0011 PR-3，集群 `SEGMENT_MISSING`，没有迁移，没有新配置项：** 集群模式下删掉本地封存段，现在和单机一样打开 CRITICAL `SEGMENT_MISSING`（#511，落地 #507；关联 #462），`/api/health` 返回 503。读到任务目录的租约持有者连续两轮推导后打开；只有记下的 `chain_owner` 能以 `EVAL` 关闭：文件回来，或本地保留让目录行到期。故障切换、重启和运维 Start 不再关掉它；没配上传时，运行器启动保留本地保留期内缺失段的目录行（日志 `retention: kept catalog row ...`）。升级前就缺失的封存段，升级后头几轮可能打开它。finding 和 `/api/health` 点名 `chain_owner=<node>`（集群）或 `node=<node>`（单机）；任务目录读不了时打日志，并列进 `/api/health` 的 `detail`。非 owner 节点可能在关闭后还列着它一段时间（#510）。#476 在 MySQL meta 上实测确认已修。v0.5.78 用同一个 schema，可以安全回滚。已知问题：#473（P1）、#513（P2）、#510、#512、#514。
- **v0.5.78：第 3 阶段周期巡检，没有迁移，新增可选的 `verify.*` 配置项：** 单机下进程内巡检（#501）启动后立刻跑一轮，之后每 `verify.every_sec`（默认 86400）一轮，读取受 `verify.budget_bytes_per_sec`（默认 4 MiB/s）限制。没有关闭开关，对象存储的 HEAD/GET 请求会变多。升级后，原有的坏本地段或坏对象可能打开 CRITICAL `VERIFY_FAILED` 或 `OBJECT_CORRUPT`，让 `/api/health` 返回 503。集群模式下跳过所有任务（A4 PARTIAL）。启动时桶 HEAD 失败、对象检查连续 3 轮没查完，会在 `/api/health` 的 `detail` 里写一条，status 仍是 ok。连续 3 轮的计数只在内存里，默认周期下重启会把这条 detail 推迟大约 3 天。发布包重新带上 `docs/releases/`（#505），两个二进制都只用 `-w` 构建（#499）。可以安全回滚到 v0.5.77；如果旧二进制拒绝未知配置项，先删掉 `verify.*`。
- **v0.5.77：安全和加固版本，没有迁移，新增两个可选配置项：** 构建升级到 Go 1.26.10 和 grpc v1.83.2（GO-2026-6809、GO-2026-6443；#491、#495）。启动时配置校验更严格：布尔项只接受 `true`/`false`，数值项拒绝非数字，未设置的 `${BINLOG_SERVER_META_DSN}` 占位符报错（#472）；重启前请先用新二进制检查配置。集群模式下每条 meta 连接都设置 `wait_timeout`、`net_read_timeout`、`net_write_timeout` 和 `innodb_lock_wait_timeout`（MariaDB 另有 `idle_transaction_timeout`）；`SET` 被拒绝时集群拒绝启动，代理吞掉 `SET` 时 `/api/health` 为 degraded。元数据行锁卡住时第二次观察打开 CRITICAL `META_LOCK_STALLED`（#492；运维约定见 `docs/releases/adr-0011-pr2.zh-CN.md`）。`GRANT ALL ON binlog_server_meta.*` 就够。新增 `cluster.side_kill`（`off`/`auto`，缺省 `off`）和 `health.node_gone_after_sec`（非共享存储上链 finding 委派给最后一任 owner，#461）。`GET /api/tasks` 返回 `desired_run`。恢复命令加上 `--verify-binlog-checksum` 和 `set -o pipefail`。v0.5.76 用同一个 schema，可以安全回滚。已知问题：#490、#494（P3）、#487、#488。
- **v0.5.76：meta 中断和 lease 接管不再让备份静默停掉（#453、#458），集群 `HEALTH_STALE`（#449），没有迁移，新增一个可选配置项：** 修复 #450、#454 和 #457。集群里续租宽限用尽（`lease_ttl_sec: 60` 时 meta 中断 35 秒以上）、无人认领的 lease 丢失或续租循环 panic，现在只结束本 epoch：desired 保持 RUN，任务以 epoch+1 从 checkpoint 续跑；没有人认领时一个 sweep 内打开 CRITICAL `TASK_NO_PROGRESS`，`/api/health` 返回 503。宽限让出时在途 append 被栅栏拒绝、又没有新主人时，任务保持可认领；已经落成 `STOPPED`、desired `RUN`、没有 owner 的行会被重新认领。旧 owner 在接管后发现 `.open.eN` 被删掉时让出，不再把 FAILED 写到新 owner 头上。旧二进制留下的 `STOPPED`、desired `STOP` 任务看起来和运维 Stop 一样，不会自动恢复。`GET /api/tasks` 带 `desired_run`。用 `curl -sS "$A/api/tasks?state=STOPPED" | jq '.items[] | select(.desired_run=="STOP") | {id, name, state, desired_run, last_error}'` 找出它们，对 `last_error` 含 `lease renew grace exceeded` 的手动 Start。Console 任务列表的「期望」列和详情里的「期望状态」是同一个字段。已经落成 `STOPPED`、desired `RUN`、没有 owner 的行会被重新认领，不要再 Start。修复按节点生效，请做完滚动升级。`health.evaluator: on` 时，`_health` 持有者对健康行超过新配置项 `health.stale_after_sec`（默认 0，即 5 倍 sweep）的任务在 `_cluster` 上打开 WARNING `HEALTH_STALE`，不让 `/api/health` 降级。v0.5.75 在同样的 schema 上运行，回退安全。已知问题：#451、#452、#455（P3），#456（P4）。
- **v0.5.75：schema 低于 9 时评估器不再静默，轮转不再误报 `CHECKPOINT_AHEAD`（#445），没有迁移和配置变更：** 修复 #436 和 #441。`health.evaluator: on` 且 meta 低于迁移 000009（在线 `migrate goto 7` 或 `8`，或进程在 schema 8 及以下启动）时，一轮内从内存打开 CRITICAL `HEALTH_STORE_UNAVAILABLE`（task `_cluster`，subject 为本节点），`/api/health` 返回 503 `degraded` 并写明 `schema N < 9, run ./migrate up`；`./migrate up` 之后不用重启即关闭，不负责任何任务的节点也一样。`shadow` 只打一次 WARN，`off` 不探。已经在 schema 9 以下开着评估器的部署，升级后会立刻 degraded：执行 `./migrate up`。`FLUSH BINARY LOGS` 时 checkpoint 和新文件取自同一快照，不再误报 CRITICAL `CHECKPOINT_AHEAD`；评估器取链锁最多等 2 秒（这一轮记 UNKNOWN，`TASK_NO_PROGRESS` 照常能报），checkpoint 读受 `meta.timeout.read` 约束。v0.5.74 在同样的 schema 上运行，回退安全。已知问题：#446（P3：schema 低于 9 时 rehasher INFO 日志刷屏）、#437、#438。
- **v0.5.74：配了上传时本地保留删除留下审计（#434），可选迁移 000010，没有配置变更：** 修复 #341 和 #353。配了上传时，本地保留每删一个文件都写 `RETENTION_REMOVED`，有可选迁移 000010（`binlog_files.retention_removed_at`；`minRequiredSchemaVersion` 仍为 6）时同时写标记；记录失败打开 `RETENTION_RECORD_FAILED`。带标记的行不报 `ORPHAN_ROW`；列举确认对象不在时报 CRITICAL `SEGMENT_MISSING#object`。在线把 000008 降下去再升回来后，封存事实不用重启就恢复写入，缺列期间由 `SEAL_FACTS_ABSENT` 报出。升级后第一轮保留会给已经删掉的文件（包括旧二进制删的）补写事件；没有 000010 时重启会再写一遍（重复的审计事件，不开 finding）。v0.5.73 能在 schema 10 上运行，回退二进制是安全的。已知问题：#436（P2：在线回滚到 000009 以下后评估器静默、health 仍是 ok；评估器开着时不要把 meta 回滚到 9 以下）、#437、#438、#441。
- **v0.5.73：meta 中断时有应答、有记录（#430），没有迁移和配置变更：** 修复 #427（P2）：meta 被黑洞（连接挂住而不是被拒绝）时，`/api/health` 不再挂住，所有节点、任何模式下都在约 1 秒内返回 503 `degraded` 并带 `META_UNREACHABLE`。`health.evaluator: on` 时，任何约 11 秒以上的中断，每个节点都记一条 CRITICAL `META_UNREACHABLE`，从第一次失败到第一次应答，时间为 UTC；集群里每次中断每个节点留一条 `_cluster` `FINDING_RESOLVED` 事件。健康存储时间改为 UTC（旧行不迁移）。已知 P3：连续两次中断后 persist/lease 类 finding 可能在恢复后约 35 秒仍打开；standalone 不写 `FINDING_RESOLVED` 事件。
- **v0.5.72：集群故障不再静默（#424），没有迁移，新增一个配置项：** 修复 P1 #421（接管时目录里的路径不在本节点 `data_dir` 下，现在以 `SEGMENT_NOT_ON_WORKER` 明确失败，不再拿着 lease 什么都不写）、#425（meta 只读后任务不再被静默写成 STOPPED）和 #426（worker 挂掉只剩 control-plane 节点时仍报 ok）。FAILED 会一直保持到操作员 Start。新增 CRITICAL `TASK_NO_PROGRESS`（`health.no_progress_after_sec`，默认 120），无主任务的 CRITICAL `TASK_FAILED` 通过 `_health` lease 在所有节点角色上评估；这些告警需要 `health.evaluator: on`（默认 `off`，集群里等所有节点都升到 v0.5.72 再打开）。仅 control-plane 的节点请各自配置不同的 `cluster.worker_id`。集群里运行任务的节点仍须共享同一个 `data_dir`。已知问题 #427（P2）：meta 连接挂住而不是被拒绝时，`/api/health` 不响应，也不记 finding。
- **v0.5.71：集群数据面 lease 栅栏（#417），没有迁移和配置变更：** 丢了 lease 的被冻结旧 owner 在接管后不能再写段文件、checkpoint 或目录行（不再出现 `STORAGE_INCONSISTENT` 脑裂）；同时修复 #360 和 #415。行为变化：meta 续约持续失败时，超过 `0.8 × lease_ttl_sec`（约 12 秒）就停止落盘，不再写到 `lease_grace_sec`（约 30 秒）。已知问题 #421（P1）：集群节点各用独立 `data_dir` 时接管后不写任何数据，修复前请使用共享 `data_dir`。
- **v0.5.70：修复评估器崩溃（#413），加入 P2-5.2/P2-5.3 类别，没有迁移。**
- **v0.5.69：遗留 failback 修复的问题已修复（#405），没有迁移和配置变更：** standalone + 元数据库下，修复旧版本跨 failback 写出的目录时，`/replay` 可能无提示地丢掉一段 stint（恢复报 `ERROR 1032`）；请先升级到 v0.5.69 或更高版本再对这类目录执行 Start，已用旧版本修复过的请检查 `/window` 与 `/replay`。集群模式修复后不再误报 `storage_alert`。`health.evaluator`（默认 `off`）还接管了 P2-5.1 链完整性类别（`SEGMENT_DAMAGED`、`CHAIN_INDEX_GAP`、`LEGACY_FAILBACK`、本地 `SEGMENT_MISSING`）。
- **v0.5.68：SIGTERM 关停有界，没有迁移和配置变更：** 任务 runner 归进程运行所有。收到 SIGINT/SIGTERM 后先停掉所有 runner（关好打开的段、写下最后状态），再停后台工作、flush finding，正常几秒内退出；30 秒未退出以退出码 2 结束，再发一次信号立即退出。编排系统的终止宽限期建议不低于 30 秒。关停保留期望状态 RUN，下次启动自动恢复（#401）。从 v0.5.66 升级仍按下面 v0.5.67 的须知。
- **v0.5.67：存活探针必须用 `/healthz`：** 有打开的 CRITICAL finding 时，`GET /api/health` 现在返回 503 `degraded`（`data_dir` 写满、finding 无法落盘时也一样，`FINDINGS_PERSIST_FAILED`）。`/healthz` 不变。存活探针指向 `/healthz`，`/api/health` 只用于告警或就绪检查。
- **standalone：升级重启之前配置任务密钥，之后每个任务 adopt 一次：** standalone 任务记录（ADR 0010，`{data_dir}/.tasks.enc`）默认开启，重启后自动恢复任务。停 v0.5.66 之前先用新二进制生成密钥（`./binlog-server task-key generate --out /etc/binlog-server/task.key`），并配置 `standalone.task_key_file`（或 `BINLOG_SERVER_TASK_KEY`）。没有密钥会打开 CRITICAL `TASK_RECORDS_FAILED/key_missing`。v0.5.66 不保存记录，所以升级重启后每个任务目录都是 STOPPED 的遗留目录，并打开 CRITICAL `TASK_UNADOPTED`（任何 `health.evaluator` 模式）。每个目录 adopt 一次，需要 `cluster_key` 和 source：批量用 `scripts/adopt-leftovers.sh`（在 release 压缩包里，需要 `curl` 和 `jq`），或 `POST /api/tasks/{id}/adopt`。之后重启会自动恢复。每个 `data_dir` 只能有一个 standalone 进程（`.tasks.lock` 上的 `flock`）。回滚到 v0.5.66 会忽略记录（任务又变成遗留目录）。
- **健康评估器，可选迁移 000009：** 新增 `health.*` 配置项；`health.evaluator` 默认 `off`。集群里所有节点升级到 v0.5.67 之前保持 `off`（滚动升级期间没有自动回退）。`000009` 只增且可选，只有带元数据 DSN 且为 `shadow`/`on` 时才需要。`minRequiredSchemaVersion` 仍是 6。
- **v0.5.66：能发现重复封存段，没有新迁移：** 同一封存源文件的第二份本地副本（如 `mysql-bin.000006` 与 `mysql-bin.000006.sealed.e3`）现在会打开 CRITICAL `SEGMENT_OVERLAP` finding 和 `STORAGE_INCONSISTENT` `storage_alert`；`/window` 断开，`/replay` 截到两份之前（#370）。升级后检查任务有没有 `SEGMENT_OVERLAP`，保留与源一致的那份，把另一份移出任务目录。API 和配置没有变化。
- **v0.5.65：ADR 0009 备份可信，两个可选迁移：** 失败现在会留下持久化 finding（`GET /api/findings`、`open_findings`、`binlog_server_finding_open`），包括 `DUMP_STALLED`、CRITICAL `METADATA_WRITE_BLOCKED`（元数据库只读：任务退避重试，绝不显示 `RUNNING`）、`SEGMENT_UNREADABLE` 和 `TASK_TRANSITION_STALLED`（STARTING/STOPPING 超过 60s）。操作先落库：元数据库只读时 Start/Stop/Delete 返回 400 且不做任何改变。dump 受租约约束。`000007_task_findings` 和 `000008_binlog_files_seal_facts` 只增且可选，建议 `./migrate up` 到 8。`minRequiredSchemaVersion` 仍是 6，地板仍是 v0.5.51。**MariaDB 11.4+：之前版本没有保存行事件（#359），升级后请重新全量备份。**
- **v0.5.64：新 Console 上线 `/ui/`，经典 Vue 在 `/ui-classic/`，没有新迁移：** `/ui/` 现在是 React + shadcn/ui 的新 Console（任务/告警、任务抽屉、新建/编辑/接管、批量创建、概览、数据源、Worker；界面里能用 `api_key` 模式）。`/ui/` 下的书签和深链接仍然可用。依赖 Vue 界面的用户请改用 `/ui-classic/`，它只保留这一个版本，之后会移除。按路径过滤的代理也要放行 `/ui-classic/`。API 和配置没有变化。

- **v0.5.62：凭证错误返回 401 而不是 403（兼容性变化），没有新迁移：** 凭证缺失、格式错误或不正确，现在一律返回 HTTP 401；v0.5.61 对错误的 token、错误的 API key、或没有 `Bearer ` 前缀的请求头返回 403。bearer 模式带 `WWW-Authenticate: Bearer realm="binlog-server"`。请把预期 403 的探针、脚本和代理改成 401。`Bearer` 前缀不再区分大小写。新增不需要凭证的 `GET /auth/config`（只写明鉴权请求头，不返回凭证）；按路径过滤的代理要放行它，控制台靠它选择请求头。`/ui/` 的 Vue 控制台现在支持 `api_key` 模式。`console/` 里的新控制台还没有嵌入。
- **不合法的 `/replay` limit 返回 HTTP 400，没有新迁移：** `limit` 为 0、负数、空、小数或文本时，`/replay` 和 `/replay/archive` 返回 HTTP 400 `invalid limit: must be a positive integer`，不再返回完整集合（#307）。要全部文件就去掉 `limit`。带 `stop_datetime`、`stop_gtid` 或 `start_gtid_set` 时 `limit` 仍不起作用，响应现在在 `warning`（tar 为 `X-Replay-Warning`）里写明。

- **早期版本的回切目录，没有新迁移：** 在 v0.5.57 或 0a84917a 上做过真实回切（A→B→A）的任务会显示 `storage_alert`（`STORAGE_INCONSISTENT`，`detail` 为 `legacy failback: ...`），`/replay` 和 `/window` 停在第一份有问题的文件之前。第一次 Start（包括升级后的自动续跑）在每份文件都能确定只属于一段时修复目录（后一段改名为 `{身份}~{n}.`，记 `STORAGE_REPAIRED`，不删任何文件）；否则以 `STORAGE_INCONSISTENT` 拒绝，磁盘、目录、对象存储都不改，这时对现在的主库新建任务，保留旧任务。`STORAGE_REPAIRED` 的 `orphaned_objects=` 列出服务不会删除的对象键，确认能恢复之后再手工删。见 [docs/guide/admin/troubleshooting.md](troubleshooting.md) 5.4。
- **dump 重连后不再静默丢事务，没有新迁移：** 在 v0.5.57 上，GTID 任务的 dump 连接断开后（代理或空闲超时断开、网络闪断、`KILL` dump 线程），任务可能保持 `RUNNING`、延迟 0，新事务却被丢掉。v0.5.58 从真正落盘的内容续传。从 v0.5.57 升级后，检查每个 GTID 任务有没有 `storage_alert`。显示它的任务已经损坏：不要再 Start，恢复时不要越过它的 `valid_segments`，在源清掉缺失事务之前从 `restart_gtid_set` 新建 GTID 任务。没有 `storage_alert` 的任务不需要处理。见 [docs/guide/admin/troubleshooting.md](troubleshooting.md)。
- **VIP 换主，没有新迁移：** 任务的 host:port 是 VIP 时，这个地址改指向另一台 MySQL 主库后，只要 GTID 能证明新主库持有这份备份已经存下的每一个事务，任务就继续拉。否则任务以 `SOURCE_SWITCHOVER` 停止。升级后第一次启动把当时这个地址连上的服务器记成已有、未加前缀文件的主人。升级前确认这个地址仍指向写下这些文件的那台服务器。仍然没有新迁移，`minRequiredSchemaVersion` 仍是 6。

## Schema 6 切换（迁移 000006）

执行 `./migrate up` 到 6 之前，确认每一台还在跑的进程都是 v0.5.51 或更新。v0.5.51 是第一版同时带上 ADR 0005 第 6 步和第 7 步的发布。v0.5.50 只有第 6 步。v0.5.51 和 v0.5.52 仍要求索引 `uk_task_file_epoch`。删掉这个索引之后，这两个二进制启动失败，日志含 `missing index` 和 `uk_task_file_epoch`。先停掉它们，再 `./migrate up`，确认 `schema_migrations` 为 `(6, 0)`，然后只启动这个二进制。`000006` 丢掉 `uk_task_file_epoch`。`file_name` 列还在。`uk_task_source_epoch` 还在。`SHOW INDEX FROM binlog_files` 有 `uk_task_source_epoch`，没有 `uk_task_file_epoch`。

## 添加说明（维护者）

每个版本的发版准备 PR（在打 tag 之前合入）在本文件和 [upgrade.md](upgrade.md) 的列表最上方各加一条。每份 README 里旧版本号的每一处都要改成新版本：「升级」一节的 `最新版本` 那一行，以及安装 pin（`VER=`、归档文件名和 `TestVersionPinsMatchVERSIONFile` 检查的其他 pin）。`最新版本` 后面的一行摘要也要重写。摘要里不能出现更早的版本号，所以写「支持从上一个版本原地升级」，不要写「从某个版本号升级」。出现下面任一情况时 `TestReadmeMatchesContract` 失败：

- 出现当前版本线上 `VERSION` 以外的版本号：以 `VERSION` 的主版本号.次版本号 `X.Y` 开头的三段数字，带不带 `v` 都算（`X.Y.N`、`vX.Y.N`、`X.Y.N-rc1`）。其他数字不受影响：其他软件的版本（MySQL 8.4.13、promtool v2.53.0）、`@` 后面的固定版本（`deadcode@v0.52.0`、`tool@vX.Y.N`）、地址这类四段数字、比例和分位数（0.5、0.99）以及日期。不带 `@` 的同一 `X.Y` 版本线上的第三方版本号（例如依赖表里的一行）会失败，请写成 `module@vX.Y.N`，或移到 docs/guide；
- 新增或改名一级/二级标题；
- 超出字节上限，或上限比实际大小多出 4 KB 以上。上限是大小再加 2048 字节，足够日常修改，例如加一个三级标题、一段安装命令、一段 FAQ 或一条检查清单。README 确实需要变长时，在同一个 PR 里调高 `readmeContracts` 中的 `maxBytes`；失败信息会写出文件名和超出的字节数；
- 「升级」一节不是 `最新版本` 那一行加上指向本指南的固定一行，或者带有小节标题。

带版本号的条目不是从新到旧、或最上面不是 `VERSION` 时，`TestUpgradeGuideNewestFirst` 失败。它只识别顶层条目：以版本号开头的列表项、标题和引用中的列表项，版本号前可以有粗体等强调、方括号、代码片段，或 `Release`、`Version`、`版本` 前缀（`- **vX.Y.Z:**`、`1. vX.Y.Z`、`### Release vX.Y.Z`、`> - [vX.Y.Z]`）。嵌套子条目和表格行（例如兼容性表）不算条目。`VERSION` 的说明写成其他格式时，失败信息会指出那一行并列出这些格式。两个测试都在 `internal/config/readme_doc_test.go`。

这个守卫用来防止 README 在日常修改中重新长出版本历史，不防刻意的绕过，例如用文字拼写版本号、用形似的数字或句点、用文字写日期。发布相关文件里的过期版本号由扫描上一个版本号的发布检查负责。这个守卫看不到的情况也归它：minor 或 major 升级后，旧版本线上漏改的版本号（`VERSION` 为 `X.(Y+1).0` 时的 `X.Y.N`）已经不在 `VERSION` 的版本线上。
