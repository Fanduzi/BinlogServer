# ADR 0011 PR-4: wire the transition model

This note is the operator contract for migration `000011`. It is not a published version bump.

## Why this upgrade stays least-privilege

The documented meta grant is `ALL` on the meta schema. That account has no `PROCESS`, `SUPER`, `CONNECTION_ADMIN`, or `log_bin_trust_function_creators`. A binlogged meta primary refuses `CREATE TRIGGER` and `CREATE PROCEDURE`, and a precheck that reads `information_schema.innodb_trx` refuses the migration. This build does not create those objects. A missing `PROCESS` privilege skips the long-transaction precheck with a warning. Correctness does not depend on killing another session.

## Order

Stop every old node first. Then `migrate up`. Then start the new nodes. A new binary refuses to start when `schema_migrations` is below 11 and tells the operator to run `./migrate up`.

`000011` checks `information_schema` and skips a column or table that is already there, so a failed up can be run again. MySQL 8 has no `ADD COLUMN IF NOT EXISTS`. The SQL precheck aborts when a worker registration is still live (`lease_expire_at > NOW(6)`). DDL then waits at most `lock_wait_timeout` of 10 seconds.

`./migrate` runs one more precheck before it crosses version 11. It counts rows in `information_schema.innodb_trx` older than 5 seconds. Five seconds is the longest idle cap this build publishes. A process may arm a shorter `idle_kill`. SQL cannot see that setting. When the account can read the view and the count is not zero, migrate exits before any DDL, so `schema_migrations` stays clean. When the account cannot read the view (`PROCESS` is missing; server errors 1227 and 1142), migrate prints a warning and continues. The trade-off: an open transaction older than 5 seconds will not block this migration. The DDL can still wait out `lock_wait_timeout` and leave `schema_migrations` dirty if a metadata lock is held. Stop writers and run `migrate up` again. Granting `PROCESS` makes this precheck fail closed.

There is no trigger and no procedure. `log_bin` does not change the grant this migration needs.

## row_generation

The store bumps `row_generation` in one place, the constant `rowGenerationBump`, used by the task upsert, the pending-dump save, the legacy desired reconcile, and `CommitYield`. The one-time backfill in the up file bumps the same way for stored `FAILED` rows whose `desired_run` is `STOP`, and sets `failed_reason` to `LEGACY_UNKNOWN`. An operator who still wanted that task stopped has to Stop it again after the migration. Do not change `LEGACY_UNKNOWN` back to `STOP`.

A hand-written `UPDATE` is no longer rejected. A stale owner's yield is fenced by `CommitYield`: `WHERE id = ? AND epoch = ? AND row_generation = ?`. Equality includes a loaded 0. A yield that has not read the column reads it first and does not send 0 in its place. Zero rows, or a missing `task_leases` row, means the lease moved. The caller does not follow that with an unfenced upsert. A standalone process keeps its lease in memory, so it does not call `CommitYield`; the task upsert writes the step.

## Optional session kill

`cluster.side_kill` still defaults to `off`. Session timeouts (`wait_timeout`, and `idle_transaction_timeout` on MariaDB) still drop a sleeping transaction. That is enough for correctness.

`auto` calls `binlog_server_kill_trx` only when that procedure is already installed and the drill passes. This migration does not create it. An operator who wants the optional kill installs the procedure and the privileges (`PROCESS`, and `CONNECTION_ADMIN` or `SUPER`) outside migrate. When `auto` is set and the drill does not pass, `/api/health` reports `side_kill=unavailable` and the process logs that once. `off` stays `off`. The client never sends a kill statement. `unavailable` is not a failed migration and not a failed sweep.

## Protocol fence

New nodes write `worker_registrations.cluster_protocol_version` 11. After the migration, a live registration still below 11 makes a new node refuse claims and open critical `MIXED_VERSION` on `_cluster`. That is the signal that an old node is still in the cluster. The claim query does not join `worker_registrations`.

`cluster.storage` is registered once in `cluster_storage`. A later node with a different mode does not claim.

## Down

Down drops `binlog_server_kill_trx` only when `information_schema.routines` already has it, then drops `backup_tasks_bu_generation` only when `information_schema.triggers` already has it. A database that never installed them runs `SELECT 1` instead, so a least-privilege account with `log_bin` on is not asked to `DROP` a routine. A database that still has the objects from an unreleased draft may need `SUPER` for that `DROP`; this migration never created them.

Down refuses to continue while a registration at protocol 11 or newer is still live, or while a `pending_delete` lease is still live. It then drops the new columns and tables. It does not write `LEGACY_UNKNOWN` rows back to desired `STOP`.

Stop the new nodes before `migrate down`. An older binary does not know schema 11.

## What stays desired RUN

`SOURCE_ACCESS_DENIED` and `SOURCE_LOG_BIN_OFF` retry for at least two minutes, then `FAILED`, and desired stays `RUN`. `SOURCE_SWITCHOVER` is `FAILED` on the first occurrence and desired stays `RUN`. The claim loop does not start it again: the address now reaches a different server, and opening another dump would mix that server into a backup that has no GTID set. An operator Start is what tries again. A `SOURCE_UNREACHABLE` streak that has used its 10 failures is `FAILED` on that occurrence, desired stays `RUN`, and the stored epoch is 0 so the claim loop does not Acquire again. `last_error` and the failure count stay on the row. A same-owner restart during the streak does not clear them and does not Acquire. A runner error outside that set still yields `LEASE_DEGRADED` and keeps desired `RUN`. ADR 0005's failure-policy section points here. The historical step text in 0005 is unchanged.

## Not in this change

#513 stays for PR-5. After a takeover, the resumed old owner's `CHECKPOINT_WRITE_FAILED` with `busy buffer` is the client driver reporting a busy connection buffer. It is not a generation-predicate miss, so this fence does not classify it as a lost lease. Treating every busy buffer as a lost lease would also hide a real checkpoint failure while this epoch still holds the lease.
