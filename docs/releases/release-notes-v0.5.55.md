# Binlog Server v0.5.55

Release date: 2026-10-07

Point-in-time restore can roll forward from the executed GTID set of a restored full backup. `GET /api/tasks/{id}/replay` and `GET /api/tasks/{id}/replay/archive` accept `start_gtid_set` together with the existing `stop_gtid` or `stop_datetime`. The set is `@@gtid_executed` on the restore instance, mysqldump `GTID_PURGED`, or the GTID set in `xtrabackup_binlog_info`. A segment whose transactions before the stop are already in that set is omitted from `paths` and from the tar. `command` is `TZ=UTC mysqlbinlog` with `--exclude-gtids` for that set, so those transactions are not applied again. The stop means the same thing as v0.5.54. A non-empty `start_datetime` cannot be set with `start_gtid_set`. Plain-text 400s are `invalid start_gtid_set`, `start_gtid_set is not supported for this flavor`, `start_gtid_set and start_datetime cannot both be set`, `stop_datetime or stop_gtid is required`, and `start_gtid_set has a gap before this task's backed-up range`. When every transaction up to the stop is already in the set, the response is HTTP 200 with `paths: []`, an empty `command`, and `note` `every transaction up to the stop is already in start_gtid_set`. The Console point-in-time form has an executed-GTID field,「已执行 GTID」. The parameter list is in `docs/guide/reference/api.md` section 5.9. Swagger was regenerated. No schema change. Schema stays 6. `minRequiredSchemaVersion` stays 6. ADR 0005 is unchanged. The floor stays v0.5.51. No new config key. Tip dogfood by BinlogServerQA passed on `9f1d9b8651971d1ed4196171f2d51938cd0f609d`. The v0.5.54 `stop_gtid` rule still holds (PR #279). The v0.5.49 sealed-position rule (#189) still holds. The v0.5.48 empty `task-<id>.binlog` rule (#205) still holds. The v0.5.52 `.takeover-*` cleanup still holds (#224, PR #273). The v0.5.53 drop of `uk_task_file_epoch` still holds (PR #276). `start_gtid_set` landed in PR #282.

## Highlights

- A restored full backup already contains transactions. xtrabackup, mysqldump, and clone record them as `SELECT @@gtid_executed` on the restore instance, mysqldump `SET @@GLOBAL.GTID_PURGED`, or the GTID set in `xtrabackup_binlog_info`. Pass that set as `start_gtid_set` with `stop_gtid` or `stop_datetime`. The published v0.5.54 package has no `start_gtid_set`. `start_datetime` is still the inclusive time bound from v0.5.54. It is not this set.
- `start_gtid_set` is one MySQL GTID set. A single `<server_uuid>:<seq>` is a one-transaction set. Spaces and newlines are removed. `--exclude-gtids` receives the canonical set. A canonical set that contains a comma is single-quoted. An empty value, whitespace only, MariaDB `domain-server-seq` such as `0-1-10`, a string that is not a MySQL GTID set, `<server_uuid>:0`, and `<server_uuid>:0-5` are plain-text 400 `invalid start_gtid_set` before the task is looked up.
- On any flavor other than `mysql`, a set that parsed as MySQL is plain-text 400 `start_gtid_set is not supported for this flavor`. This path does not parse a MariaDB GTID. A MariaDB shape is `invalid start_gtid_set` before that flavor check.
- `start_gtid_set` requires `stop_datetime` or `stop_gtid`. Neither stop is plain-text 400 `stop_datetime or stop_gtid is required`. An unparseable set is `invalid start_gtid_set` even when the stop is also missing or unparseable. `stop_datetime` and `stop_gtid` together, including when one of the values is empty, is `stop_datetime and stop_gtid cannot both be set`. That check runs first, including when `start_gtid_set` cannot be parsed. A non-empty `start_datetime` together with `start_gtid_set` is `start_gtid_set and start_datetime cannot both be set`. That check runs before the set is parsed. An empty `start_datetime` is omitted.
- The server reads each segment's `GTID_EVENT` rows in binlog order. The request scans those bytes. It does not add a column. `stop_datetime` still leaves out an event whose timestamp is greater than or equal to the stop. `stop_gtid` still stops at the starting byte of that `GTID_EVENT`. A transaction already in `start_gtid_set` is not one that still needs to be applied. A segment is omitted from `paths` and from the tar when every transaction in it before the stop is already in the set. A segment that still has a transaction to apply stays. A sealed `UPLOADED` object that exists only in the bucket uses the same rule as a local file.
- `command` begins with `TZ=UTC mysqlbinlog`. `--exclude-gtids=<canonical set>` comes first, so mysqlbinlog skips transactions already in the set and applies the ones that are not. When `stop_datetime` is set, `--stop-datetime='<UTC>'` comes next. When the file that contains `stop_gtid` is still the last path, `--stop-position=<N>` comes next. `N` is still that event's starting byte. Then the paths. The command does not include `--start-datetime`. When the file that contains the stop is omitted because nothing before that stop still needs to be applied, the command has no `--stop-position`. The earlier files that remain are applied in full. An empty path list makes `command` an empty string.
- When every transaction before the stop is already in the set, the response is still HTTP 200. `paths` is `[]`. `command` is an empty string. `note` is `every transaction up to the stop is already in start_gtid_set`. That is not an error. The response does not include a command that would apply those transactions again. When the stop is the first transaction and the window has no transaction to apply, `paths` and `command` are still empty and `note` is omitted.
- The first segment that still needs to be applied must not skip a transaction this task does not have. If that segment has previous-GTIDs, that set must be a subset of `start_gtid_set`. With or without previous-GTIDs, each UUID's smallest sequence `N` in that segment requires `1` through `N-1` to be covered by previous-GTIDs, `start_gtid_set`, and transactions in earlier retained segments. A GTID dump writes previous-GTIDs at the start of the source file and skips transactions that were written in that same file before the task started. Those sequence numbers are not in the segment. They must already be in the set. If they are not, the body is plain-text 400 `start_gtid_set has a gap before this task's backed-up range`. A backup older than the retained binlogs, with transactions missing in between, is rejected. It is not a silent skip. A set that does not intersect the transactions inside the segment, while `1` through `N-1` are already covered, continues from the start of the retained range. Those segments are still returned.
- `stop_gtid` that is not a `GTID_EVENT` in this task is still `stop_gtid is not in this task's backed-up range`. That sentence wins over the gap sentence. A missing task, when `start_gtid_set` is a MySQL set, is HTTP 404 `task not found`. A selected segment that cannot be opened is HTTP 404 `segment not found on this process`.
- `limit` is ignored when `start_gtid_set` is set. `GET /api/tasks/{id}/replay/archive` accepts the same `start_gtid_set` and the same stop. The tar members are those basenames. `--exclude-gtids` and the stop stay in the JSON `command`. They are not tar members. A window that is already fully covered is an empty tar. A missing, unsupported, or gapped set is the same plain-text error as the JSON route. The body is not a tar.
- Console task detail, on the point-in-time form, has an executed GTID field. The Chinese label is「已执行 GTID」. The English label is `Executed GTID set (start_gtid_set)`. A stop time or a stop GTID is still required to generate the command and to download `task-{id}-replay.tar`. Filling the executed GTID and a start time sends both parameters, and the page shows `start_gtid_set and start_datetime cannot both be set`. When `note` is set and `command` is empty, the page shows that note. That Console is in the embedded bundle a plain `go build` serves.
- No new config key. No schema migration. `minRequiredSchemaVersion` stays 6. `migrations/` is still `000001` through `000006`. There is no `000007`. ADR 0005 is unchanged. Steps 1–9 already shipped. Step 9 shipped in v0.5.53. This release is not a new ADR step.

## Upgrade Notes

No new migration. A database already on schema 6 from v0.5.54 stays on schema 6. Confirm `SELECT version, dirty FROM schema_migrations` is `(6, 0)`. `migrations/` is still `000001`, `000002`, `000003`, `000004`, `000005`, and `000006`. There is no `000007`.

`minRequiredSchemaVersion` remains 6. v0.5.55 does not start on schema 5. It exits with code 1 before it listens. The message contains `schema version too old` and `./migrate up`. That is the same refusal as v0.5.54. Schema 4 and schema 3 exit the same way.

Replace the binary after schema 6 is already in place. If the database is already v0.5.54 / schema 6, there is no `./migrate` step. If it is not schema 6 yet, follow the [v0.5.54 upgrade](release-notes-v0.5.54.md) first and confirm `(6, 0)`, then start v0.5.55.

The floor stays v0.5.51, the first release that ships both ADR 0005 step 6 and step 7. v0.5.50 shipped step 6 only. Stop every process that still requires `uk_task_file_epoch` before `./migrate up` to schema 6. v0.5.51 and v0.5.52 are those binaries. On schema 6 they refuse to start. The log contains `missing index` and `uk_task_file_epoch`. A process older than v0.5.51, including v0.5.50, is not the floor. Replace it before `000006`. Then stop v0.5.51 and v0.5.52. Then run `./migrate up`.

Schema 4 (`000004_pending_dump_cleanup`) is still in the chain. Before v0.5.50, schema 4 was optional for one process and required for cluster mode. That rule still applies when you upgrade stepwise and the binary you start is older than v0.5.50. v0.5.55 does not start on schema 4.

If this database is not already schema 3, follow the [v0.5.46 upgrade](release-notes-v0.5.46.md), then the v0.5.50 upgrade, then the v0.5.53 upgrade. Schema 2 to schema 3 (`000003_task_desired_and_retry_budget`) is online. Schema 1 to schema 2 still follows the [v0.5.34 upgrade](release-notes-v0.5.34.md): stop every binlog-server on that database, run `./migrate up`, then start only v0.5.34 or newer.

No new config key. Standalone with no metadata database does not run these migrations. `start_gtid_set` reads the segments this process can open, so standalone has the same query.

Do not run `./migrate down` past the schema the running binaries need. v0.5.55 needs schema 6. This release adds no migration, so there is no new down step. `./migrate down --steps 1` from schema 6 is still the v0.5.53 down: it adds `uk_task_file_epoch` back. It does not delete rows. It does not drop `file_name`. It does not drop `uk_task_source_epoch`. It returns to version 5. The `binlog_files` row count is unchanged. If two rows already share `(task_id, file_name, epoch)`, that down fails. Do not delete rows to make it pass. The writer keeps `file_name` equal to `source_file`. Do not run that down while v0.5.55 is running. v0.5.55 does not start on schema 5. Production `./migrate down` stays blocked unless `ALLOW_DESTRUCTIVE_MIGRATE=1`.

The v0.5.53 index rule still holds. `SHOW INDEX FROM binlog_files` lists `uk_task_source_epoch` and does not list `uk_task_file_epoch`. The `file_name` column stays. A second insert of the same `(task_id, source_file, epoch)` fails. The duplicate key is `uk_task_source_epoch`.

The v0.5.52 `.takeover-*` cleanup still holds. A worker still removes a regular `.takeover-*` left in a task directory. The v0.5.51 unknown-`end_pos` rule still holds. Unknown `end_pos` is JSON `null` on `GET /api/tasks/{id}/files`, and the Console cell is blank, when this process cannot read the local bytes. A readable local file shows the event span.

The v0.5.54 `stop_gtid` rule still holds. The v0.5.49 sealed-position rule (#189) and the v0.5.48 empty `task-<id>.binlog` rule (#205) still hold. `stop_datetime` is unchanged. It still leaves out an event whose timestamp is greater than or equal to the stop. Tip dogfood by BinlogServerQA passed on `9f1d9b86`.

This release is not an ADR 0005 step. Steps 1–9 already shipped. ADR 0005 is unchanged. v0.5.53 is the release that shipped step 9.

## Known behavior

#224 was fixed in v0.5.52. #189 was fixed in v0.5.49. #205 was fixed in v0.5.48. `stop_gtid` shipped in v0.5.54. This release does not change those earlier fixes. This release is not an ADR 0005 step. ADR 0005 is unchanged.

- `stop_datetime` still cuts on the event-header second. Transactions that share that second are still all in or all out on the datetime path. Use `stop_gtid` when the bad GTID is known. `start_gtid_set` does not change that stop.
- A set that does not cover the transactions before the first segment that would be applied is refused. The replay does not skip that hole.
- Schema stays 6. The floor stays v0.5.51. There is no `000007`. `file_name` stays a column.
