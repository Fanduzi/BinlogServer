# Binlog Server v0.5.36 中文发布说明

> 对应版本：`v0.5.36`

发布日期：2026-10-05

以 `start.mode=GTID` 创建的任务，第一次 checkpoint 落盘会丢掉这个 GTID。续传只向源库要文件和位点。这个 binlog 已经被清理时，MySQL 返回 1236（`Could not find first log file name in binary log index file`），任务停在 `RETRY_BACKOFF`。checkpoint 的 `gtid_set` 也停在创建任务时的集合，之后即便按 GTID 拉流也会从过早的位置开始。这一版在每次落盘时留下已执行集合，事务提交时把集合往前扩，源文件已经不在时再打开一次 `StartSyncGTID`。任务进入 `RUNNING`。跟踪为 #175、#197、#198。

## 核心变化

- 落盘的 checkpoint 带着 `gtid_set`。rotate 记到下一个文件时也带着。第一次落盘不再把空列写到起点集合上。
- 集合在事务提交时变大：XID、`COMMIT`、`ROLLBACK`，或一条自动提交语句。GTID 事件本身在这次提交之前不写进集合。`ROLLBACK TO` 不记入。
- 文件和位点就是存储的 checkpoint 时，`GET /api/tasks/{id}/checkpoint` 返回 `gtid_set`。epoch 大于 1、位点回拨到 4 时，这个响应不带 `gtid_set`。存储行里仍有这个集合。源文件已被清理时，仍用存储行里的集合。
- 续传仍先按文件和位点。源上还有这个文件时，继续按文件和位点拉。`StartSync` 在 MySQL 送出 1236 之前就返回。这个错误出现在第一条流读取上，此时还没有任何 dump 事件。checkpoint 有 GTID 时，本进程关掉这次 dump，再打开 `StartSyncGTID`。日志是 `file/pos resume hit MySQL 1236 before any event; opening GTID dump`。任务进入 `RUNNING`。
- GTID 流再返回 1236 时，这一轮把错误交给调度器。同一次尝试里不再打开那个已经不在的文件。
- 本来就没有 GTID 的文件位点任务，不会从流里编出一个集合。这种任务上的 1236 仍是 1236。

## 升级影响

二进制从 v0.5.35 滚动升级即可。这一版没有 schema migration。元数据 schema 仍是 v0.5.34 引入的版本 2。`schema_migrations` 已经是版本 2 时，不用执行 `./migrate up`。

还在 schema 1 上的库，要先迁移，这个二进制才会启动。按 [v0.5.34 升级说明](v0.5.34.zh-CN.md)：停掉这个元数据库上的每一台 binlog-server，执行 `./migrate up`，然后只启动 v0.5.34 或更新的二进制。

没有新的配置项。

源库对 checkpoint 文件执行 `PURGE BINARY LOGS` 之前，先看 `GET /api/tasks/{id}/checkpoint`，用 `GTID_SUBSET` 把 `gtid_set` 和源库 `GTID_EXECUTED` 比一下。清理之后的续传用的就是这个存储集合。

`gtid_set` 已经是空的 checkpoint，是 v0.5.35 或更早的落盘清掉的。这个二进制不会从本地文件把集合重建出来。源上还有这个 checkpoint 文件时，Start 仍从该文件和位点继续。下一次落盘的事件把任务配置的起点 GTID 写回去。这个二进制运行之后提交的事务再把集合往前扩。列是空的那段时间里已经复制过的事务，不会补进集合。源已经清掉这个文件、列仍是空的，Start 仍收到 MySQL 1236，任务留在 `RETRY_BACKOFF`。没有存储集合可以拿来打开 `StartSyncGTID`。

`gtid_set` 没有包含这个任务已经复制过的事务时，之后的清理会从这份不完整的集合续传。源库会把缺的事务再送一遍，这些事件会再次写进该任务的本地分段。源库已经把这些缺失的 GTID 清掉时，GTID 拉流返回 1236，任务进入 `RETRY_BACKOFF`。

## 已知行为

- `binlog_transaction_compression=ON` 时，MySQL 把提交写进事务载荷。本进程不打开这个载荷。被压缩的事务不进 `gtid_set`，集合也不会因此变大。CI 作业 `e2e-gtid-purge` 会先关掉 `binlog_transaction_compression`，让 GTID 和 XID 作为独立事件出现，结束时再打开。
- 故障切换之后，后一次封存的分段，例如 `mysql-bin.NNNNNN.sealed.e1`，`end_pos` 可能是 0。`size_bytes` 是文件大小。这一行仍可以是 `UPLOADED`，checksum 为 `match`。文件列表里仍有这一段，下载和回放仍能返回它。这是 v0.5.34 和 v0.5.35 已经记下的行为。跟踪为 #189。
- 停止过程中改了源库密码，然后再 Start，源库上可能短暂出现两条 Binlog Dump。之后再一次停到 `STOPPED`，仍可能留下一条 Binlog Dump，需要在源库上手动 `KILL`。控制面上一次普通停止，以及一体进程上的停止，源库进程列表里不再有该任务的 Binlog Dump。这是 v0.5.35 已经记下的行为。跟踪为 #193。
