# Binlog Server v0.5.43 中文发布说明

> 对应版本：`v0.5.43`

发布日期：2026-10-06

一体进程和集群上，认领循环以前大约每 2 秒会再次启动自己名下的 `RETRY_BACKOFF` 任务。这次启动把失败计数清掉，源库连不上时任务到不了 `FAILED`，租约 epoch 也会一直往上走。现在认领循环不再启动一条还活着的、已经归自己的运行。任务在退避间隔里保持 `RETRY_BACKOFF`，连续十次 `SOURCE_UNREACHABLE` 之后进入 `FAILED`，和没有元数据库的 standalone 同一份预算。`GET /api/tasks/{id}` 的 `last_error` 以 `SOURCE_UNREACHABLE:` 开头，租约被释放。本进程还在等退避时，epoch 不再往上走。本进程重启，`SIGTERM` 或 `kill -9`，这一串失败的计数会带过去。已经记下 4 次失败再重启，仍会在累计第 10 次失败时进入 `FAILED`。操作员 Start 会把计数清掉。ADR 0005 已接受。它是路线图：元数据 MySQL 是任务状态的唯一权威，分段键是 `(task_id, source_file, epoch)`。这条记录不改变运行时行为。跟踪为 #203（PR #234）、#237（PR #238）。

## 核心变化

- 一体进程和集群上，源库连不上的、已经归自己的任务，在退避间隔里保持 `RETRY_BACKOFF`。认领循环大约每 2 秒跑一次，本进程已经在等重试时，不再把这个任务再启动一遍。失败计数不会被清掉。连续十次 `SOURCE_UNREACHABLE` 之后任务进入 `FAILED`，和 standalone 同一份预算。`GET /api/tasks/{id}` 的 `last_error` 以 `SOURCE_UNREACHABLE:` 开头。租约被释放。
- 这段退避里租约 epoch 不再往上走。另一个 worker 接管一条已经过期的租约时，epoch 仍会变。拉流已经打开之后源库宕机，仍计入同一份预算。拉流连上时计数清掉，操作员 Start 时计数也清掉。
- 一体进程或集群 worker 在这一串失败中间重启，计数会带过去。已经记下 4 次失败，然后 `SIGTERM` 或 `kill -9`，仍会在累计第 10 次失败时进入 `FAILED`。本进程没有本地运行时的同主认领，以及过期租约的接管，都从该任务已经存下的 `TASK_RUNNER_ERROR` 事件续上计数。两边都按从旧到新读这些事件。200 条窗口仍是最新的那些行。
- ADR 0005（`docs/adr/0005-single-task-authority-and-segment-catalog.md`）已接受。元数据 MySQL 是期望任务状态和观察到的任务状态的唯一权威。分段按 `(task_id, source_file, epoch)` 标识。这份记录是路线图。这一版不因此改变运行时行为。

## 升级影响

从 v0.5.42 直接替换二进制即可。这一版没有 schema migration。#234 和 #238 都没有加迁移。元数据 schema 仍是 v0.5.34 引入的版本 2。`migrations/` 仍是 `000001` 和 `000002`。`schema_migrations` 已经是版本 2 时，不用执行 `./migrate up`。

还在 schema 1 上的库，要先迁移，这个二进制才会启动。按 [v0.5.34 升级说明](v0.5.34.zh-CN.md)：停掉这个元数据库上的每一台 binlog-server，执行 `./migrate up`，然后只启动 v0.5.34 或更新的二进制。

没有新的配置项。

v0.5.42 上因为认领循环反复启动、一直停在 `RETRY_BACKOFF` 的任务，换上这个二进制之后，连续十次 `SOURCE_UNREACHABLE` 会进入 `FAILED`。操作员 Start 会把计数清掉。这一串失败中间只重启一次进程，计数不会从头算。ADR 0005 不改变正在跑的进程。这份记录不带来新列，也不带来新的配置项。

## 已知行为

下面这些仍开着。#189、#193、#205、#224 在这一版之前就有。#203 和 #237 在这一版修好了。#239 在这一版仍开着。

- 同一串失败里重启两次，最多要到第 14 次失败才进入 `FAILED`。认领写下的 `TASK_STARTED` 和操作员 Start 分不出来，所以第二次重启只留下上一次认领之后的失败。重启之后退避从 1 秒重新起跳。结构性修复是 ADR 0005 第 3 步，把重试预算做成持久化列。跟踪为 #239。
- 故障切换后，同名封存段的 `end_pos` 写成 0。跟踪为 #189。
- 停止期间改密码再 Start 后，源库可能残留多余 Binlog Dump 连接。跟踪为 #193。
- GTID 启动或 1236 回退后写入无 CRC 的人工 Rotate，校验失败，并产生多余的 `task-N.binlog`。跟踪为 #205。
- 接管下载 `UPLOADED` 对象时进程崩溃，`.takeover-*` 临时文件会一直留在磁盘上。重启、重试成功后都不清理。跟踪为 #224。
