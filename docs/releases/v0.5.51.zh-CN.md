# Binlog Server v0.5.51 中文发布说明

> 对应版本：`v0.5.51`

发布日期：2026-10-07

`GET /api/tasks/{id}/files` 和 Console 文件表把未知的结束位点留空。未知的 `end_pos` 是 JSON `null`。不是 `0`，也不是恢复游标的拷贝。Console 单元格是空白。本地文件能读到事件时，`start_pos` 和 `end_pos` 是这段事件的跨度。结束位点是最后一个完整事件的 end log position，和 `DurableCursor` 返回的数字相同，也和 `binlog.EventSpan` 读到的跨度相同。已经存好的跨度，结束位点大于起始位点时，保持原样。只有对象、本地没有文件的行保持原样。历史上 `end_pos` 为 0、本进程读不到本地字节时，API 给出 JSON `null`。目录里的值保持 0，直到能读到这些字节的 worker 打开该任务目录。这次打开只修目录位点，不重新上传对象。没有元数据 DSN 的 standalone 遗留目录：文件能读到事件时用事件跨度，读不到时是 `null`。保留清理只删除 `binlog.ClassifySegment` 认作已封存分段的名字。`.takeover-*`、`notes.txt` 和 `task-<id>.binlog` 留在磁盘上。`file_name` 不变。没有迁移 `000006`。schema 仍是 5。`minRequiredSchemaVersion` 仍是 5。`uk_task_file_epoch` 仍在。没有新的配置项。这一版是 ADR 0005 的第 7 步，一共 9 步。第 8 步和第 9 步不在这一版。BinlogServerQA 的 tip dogfood 在 `a886271248c4a31ac4be3ee11e87b11ba896724e` 上为 PASS。这次没有新的问题。v0.5.49 的封存位点规则（#189）仍成立。v0.5.48 不留下空 `task-<id>.binlog` 的规则（#205）仍成立。

## 核心变化

- `GET /api/tasks/{id}/files` 对未知的 `end_pos` 返回 JSON `null`。Console 结束位点单元格是空白。这个值不是 `0`，也不是恢复游标。本进程能读到本地文件里的事件时，`start_pos` 和 `end_pos` 是这段事件的跨度。结束位点与 `DurableCursor` 和 `binlog.EventSpan` 一致。已经存好、结束位点大于起始位点的跨度保持原样。只有对象的行保持原样。
- 历史上 `end_pos` 为 0、本进程读不到文件时，这个 API 给出 JSON `null`。目录行保持 0，直到能读到本地字节的 worker 打开该任务目录。这次打开写入修好的 `start_pos` 和 `end_pos`。不重新上传对象。这一版不把 `end_pos` 写成 0。不知道结束位点的 upsert 不赋值 `end_pos`。
- 没有元数据 DSN 的 standalone，遗留目录在文件能读到事件时列出事件跨度，读不到时是 `null`。
- 保留清理删除 `binlog.ClassifySegment` 认作已封存、并且已经过期的名字。正在写的文件留下。打开中的分段留下。解析拒绝的名字留下，包括 `.takeover-*`、`notes.txt` 和 `task-<id>.binlog`。
- `file_name` 不变。schema 仍是 5。`migrations/` 仍是 `000001` 到 `000005`。没有 `000006`。`uk_task_file_epoch` 仍在。`minRequiredSchemaVersion` 仍是 5。没有新的配置项。ADR 0005 第 7 步已标为落地。第 8 步和第 9 步没有改。它们仍是后续工作。

## 升级影响

没有新迁移。已经从 v0.5.50 升到 schema 5 的库仍是 schema 5。确认 `SELECT version, dirty FROM schema_migrations` 是 `(5, 0)`。`migrations/` 仍是 `000001`、`000002`、`000003`、`000004` 和 `000005`。下一个新迁移仍是 `000006`。`000006` 不在这一版。

`minRequiredSchemaVersion` 仍是 5。v0.5.51 在 schema 4 上不会启动，以退出码 1 结束，还没开始监听。提示含 `schema version too old` 和 `./migrate up`。这和 v0.5.50 的拒绝一样。schema 3 和 schema 2 同样拒绝启动。v0.5.49 仍能在 schema 5 上启动，因为 `uk_task_file_epoch` 还在。

schema 5 已经就位再换这一版二进制。库已经是 v0.5.50 / schema 5 时，不需要 `./migrate`。还不是 schema 5 时，先按 [v0.5.50 中文发布说明](v0.5.50.zh-CN.md)，确认 `(5, 0)`，再启动 v0.5.51。

schema 4（`000004_pending_dump_cleanup`）仍在迁移链上。v0.5.50 之前，schema 4 是单进程可选、集群必须。分步升级、启动的仍是比 v0.5.50 旧的二进制时，这条规则还适用。v0.5.51 自己不能停在 schema 4。

如果这套库还不是 schema 3，先按 [v0.5.46 中文发布说明](v0.5.46.zh-CN.md)，再按 v0.5.50。schema 2 到 schema 3（`000003_task_desired_and_retry_budget`）在线。schema 1 到 schema 2 仍按 [v0.5.34 升级说明](v0.5.34.zh-CN.md)：停掉每一台进程，执行 `./migrate up`，然后只启动 v0.5.34 或更新的二进制。

没有新的配置项。没有元数据库的 standalone 不跑这些迁移。

不要 `./migrate down` 退过正在跑的二进制所需要的 schema。v0.5.51 需要 schema 5。这一版没有新迁移，所以没有新的 down。schema 5 上 `./migrate down --steps 1` 仍是 v0.5.50 的那次 down：只丢掉 `uk_task_source_epoch`，并恢复原来的空值约束。`source_file` 重新可空。`start_pos` 和 `end_pos` 重新 `NOT NULL`。回到 version 4。不删行。`start_pos` 或 `end_pos` 已经是 NULL 时，这次 down 会失败。不要把这个 NULL 填成 0。这一版在不知道结束位点时把该列写成 NULL。不写成 0。v0.5.51 还在跑时不要做这次 down。v0.5.51 在 schema 4 上不会启动。

历史上 `end_pos` 为 0、本进程读不到本地字节时，`GET /api/tasks/{id}/files` 给出 JSON `null`，Console 单元格是空白。能读到这些字节的 worker 打开该目录时，才修目录位点。这次修复不重新上传对象。

v0.5.49 的封存位点规则（#189）和 v0.5.48 的空 `task-<id>.binlog` 规则（#205）仍成立。BinlogServerQA 的 tip dogfood 在 `a8862712` 上为 PASS：未知 `end_pos` 是 JSON `null`；能读的封存文件给出 `EventSpan`；standalone 同样；历史上 `end_pos` 为 0 时 API 是 JSON `null`；保留清理留下 `.takeover-*`、`notes.txt` 和 `task-*.binlog`，并删除过期的封存分段；#189 和 #205 没有回退；schema 仍是 5，没有 `000006`。这次没有新的问题。

这一版是 ADR 0005 的第 7 步，一共 9 步。第 8 步和第 9 步仍是后续工作。
