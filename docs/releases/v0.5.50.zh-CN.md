# Binlog Server v0.5.50 中文发布说明

> 对应版本：`v0.5.50`

发布日期：2026-10-07

迁移 `000005_binlog_source_epoch_key` 用 `(task_id, source_file, epoch)` 作为一段的键。`source_file` 为 NULL 或空串时回填 `source_file = file_name`，然后把该列设为 `NOT NULL`，加上 `UNIQUE KEY uk_task_source_epoch (task_id, source_file, epoch)`，保留 `uk_task_file_epoch`，并把 `start_pos` 和 `end_pos` 改成可空。SQL 不改已有位点。`end_pos` 为 0 的行仍是 0。封存、登记和打开中分段的 upsert 按这同一个键识别一段。`file_name` 保持等于这个源文件名，所以两个唯一键打到同一行，v0.5.49 的 upsert 仍更新这一行。`minRequiredSchemaVersion` 是 5。schema 4 上这个二进制以退出码 1 结束，还没开始监听。提示含 `schema version too old` 和 `./migrate up`。这一版是 ADR 0005 的第 6 步，一共 9 步。第 7 到第 9 步不在这一版。没有新的配置项。BinlogServerQA 的 tip dogfood 在 `e122bd5f` 上为 PASS。这次没有新的问题。v0.5.49 的封存位点规则（#189）仍成立。v0.5.48 不留下空 `task-<id>.binlog` 的规则（#205）仍成立。

## 核心变化

- 迁移 `000005_binlog_source_epoch_key` 在 `source_file` 为 NULL 或空串时回填 `source_file = file_name`。然后把 `source_file` 设为 `NOT NULL`，加上 `UNIQUE KEY uk_task_source_epoch (task_id, source_file, epoch)`，并保留 `uk_task_file_epoch`。`start_pos` 和 `end_pos` 改为可空。SQL 不 `UPDATE` 已有位点。历史上 `end_pos` 为 0 的行仍是 0。这次迁移不删行。
- 封存、登记和打开中分段的 upsert 按 `(task_id, source_file, epoch)` 识别一段。`file_name` 保持等于这个源文件名。两个唯一键打到同一行。v0.5.49 的 upsert 仍更新这一行。
- `minRequiredSchemaVersion` 是 5。v0.5.50 在 schema 4 上不会启动，以退出码 1 结束，还没开始监听。提示含 `schema version too old` 和 `./migrate up`。schema 3 和 schema 2 同样拒绝启动。v0.5.49 仍能在 schema 5 上启动，因为 `uk_task_file_epoch` 还在。
- v0.5.49 的封存位点规则仍成立（#189）。新封存的分段，`start_pos` 和 `end_pos` 按文件里的事件来写。已经是 `UPLOADED` 的行保持原样，包括旧二进制写成 `end_pos` 0 的行。`e122bd5f` 上的 tip dogfood 核对过这条规则。
- 这一版封存的分段仍不会留下 `task-<id>.binlog`。`mysqlbinlog --verify-binlog-checksum` 退出码仍是 0。这是 v0.5.48（#205）的规则。这一版没有改它。

## 升级影响

启动 v0.5.50 之前先 `./migrate up` 到 schema 5。`minRequiredSchemaVersion` 是 5。确认 `SELECT version, dirty FROM schema_migrations` 是 `(5, 0)`。`migrations/` 是 `000001`、`000002`、`000003`、`000004` 和 `000005`。下一个新迁移是 `000006`。

schema 4 到 schema 5 就是 `000005_binlog_source_epoch_key`。它回填空的 `source_file`，把该列设为 `NOT NULL`，加上 `uk_task_source_epoch`，保留 `uk_task_file_epoch`，并把 `start_pos` 和 `end_pos` 改成可空。已有位点保持原样，包括 `end_pos` 0。这次迁移不删行。

v0.5.50 在 schema 4 上不会启动，以退出码 1 结束，还没开始监听。提示含 `schema version too old` 和 `./migrate up`。v0.5.49 仍能在 schema 5 上启动，因为 `uk_task_file_epoch` 还在。`schema_migrations` 到 `(5, 0)` 之后再启动 v0.5.50。

schema 4（`000004_pending_dump_cleanup`）仍在迁移链上。这一版之前，schema 4 是单进程可选、集群必须，规则和 v0.5.46、v0.5.47、v0.5.48、v0.5.49 一样。分步升级、启动的仍是比 v0.5.50 旧的二进制时，这条规则还适用。v0.5.50 自己不能停在 schema 4。

如果这套库还不是 schema 3，按 [v0.5.46 中文发布说明](v0.5.46.zh-CN.md)。schema 2 到 schema 3（`000003_task_desired_and_retry_budget`）在线。schema 1 到 schema 2 仍按 [v0.5.34 升级说明](v0.5.34.zh-CN.md)：停掉每一台进程，执行 `./migrate up`，然后只启动 v0.5.34 或更新的二进制。

没有新的配置项。没有元数据库的 standalone 不跑这些迁移。

不要 `./migrate down` 退过正在跑的二进制所需要的 schema。v0.5.50 需要 schema 5。schema 5 上 `./migrate down --steps 1` 只丢掉 `uk_task_source_epoch`，并恢复原来的空值约束。`source_file` 重新可空。`start_pos` 和 `end_pos` 重新 `NOT NULL`。回到 version 4。不删行。`binlog_files` 行数不变。`start_pos` 或 `end_pos` 已经是 NULL 时，这次 down 会失败。不要把这个 NULL 填成 0。这一版不把这两列写成 NULL。v0.5.50 还在跑时不要做这次 down。再往下的 `./migrate down --steps 1` 从 schema 4 只丢掉 `pending_dump_cleanup`，回到 version 3。集群 worker 还依赖这一列时不要做这次 down。比 v0.5.50 旧的单进程可以留在 schema 3。v0.5.50 在 schema 3 上不会启动。

库已经是 schema 5 再换这一版二进制。已有位点不改写，包括历史上 `end_pos` 为 0 的行。v0.5.49 的封存位点规则和 v0.5.48 的空 `task-<id>.binlog` 规则仍成立。BinlogServerQA 的 tip dogfood 在 `e122bd5f` 上为 PASS。这次没有新的问题。

这一版是 ADR 0005 的第 6 步，一共 9 步。第 7 到第 9 步仍是后续工作。
