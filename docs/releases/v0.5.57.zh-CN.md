# Binlog Server v0.5.57 中文发布说明

> 对应版本：`v0.5.57`

发布日期：2026-10-07

任务的 host:port 是 VIP、DNS 名或代理时，这个地址连上另一台 MySQL 的 `@@server_uuid`，任务可以继续，但只在这份备份已经有已执行 GTID 集合，并且新主库仍持有已经备份下来的每一个事务时。旧服务器的 open 分段被封存。之后的文件名是 `{server_uuid}.{binlog file}`，两台服务器不会共用一个文件名。`GET /api/tasks/{id}/events` 记下一条 `SOURCE_SWITCHOVER`。`GET /api/tasks/{id}/window` 报告这条链在切换点上是否连续。`GET /api/tasks/{id}/replay` 带 `stop_datetime` 或 `stop_gtid` 时，先列出旧服务器的文件。其他情况任务停在 `FAILED`。`last_error` 以 `SOURCE_SWITCHOVER` 开头，写出两台服务器，并告诉操作员对新主库新建任务、保留这份备份。这次停下覆盖已经存过字节、却没有 GTID 集合的备份，也就是 `LATEST`，以及没有存下集合的 `FILE_POS`，包括新主库对旧文件名返回 MySQL 1236；新主库缺少这份备份已经有的事务；新主库已经 purge 了这份备份还没有的事务；以及 MariaDB。已经有已执行 GTID 集合的 `FILE_POS` 走继续这条路，包括新主库对旧文件名返回 1236。没有新的配置项。没有 schema 迁移。schema 仍是 6。`minRequiredSchemaVersion` 仍是 6。ADR 0005 没有改。地板仍是 v0.5.51。升级前确认这个地址仍连到写下现有无前缀文件的那台服务器。升级后第一次启动把那台服务器记成这些文件的主人。BinlogServerQA 的 tip dogfood 在 `62f2251ad2bb70458d05f5524f78f075b9feabaf` 上为 PASS（evidence-289）。这次没有新的问题。v0.5.56 的可恢复窗口仍成立（PR #285）。v0.5.55 的 `start_gtid_set` 规则仍成立（PR #282）。v0.5.54 的 `stop_gtid` 规则仍成立（PR #279）。v0.5.49 的封存位点规则（#189）仍成立。v0.5.48 不留下空 `task-<id>.binlog` 的规则（#205）仍成立。v0.5.52 清理 `.takeover-*` 的规则仍成立（#224，PR #273）。v0.5.53 丢掉 `uk_task_file_epoch` 的规则仍成立（PR #276）。VIP 切换在 PR #289 落地。PR #288 只是 e2e 在 `RESET MASTER` 之前等到真正的恢复实例。不是给操作员的产品行为变更。

## 核心变化

- 比较的是任务 host 和 port 现在连上的身份。MySQL 上这个身份是 `@@server_uuid`。身份相同不是切换。同一台服务器重启，仍在最后一个真实事件处封存上一个文件，再在下一个文件上继续。身份不同才是切换。这次判断发生在：一次运行开始时 `{data_dir}/{task_id}/.source-chain` 已经记下另一台服务器；新的 dump 连接报出另一台服务器；dump 在下一个事件之前返回错误，包括 `StartSync` 或第一次读取返回的 MySQL 1236。发现切换的那条事件不会被追加进去。dump 出错时，身份读失败、身份为空，或身份相同，原来的错误保持不变。在写下一条事件之前身份读失败，错误就是这次读取的错误。
- `source.flavor` 为 `mysql`、这份备份已有已执行 GTID 集合、该集合对新主库 `@@gtid_executed` 的 `GTID_SUBSET` 为真，并且新主库多出来、这份备份还没有的事务仍在 binlog 里时，任务继续。一次运行开始时，这个集合是 checkpoint 的 `gtid_set`。它为空且任务模式是 `GTID` 时，用任务启动时的 `gtid_set`。dump 已经打开时，用的是从流里记下的已执行集合。旧的 open 分段按写下它的那台服务器封存，然后用 `COM_BINLOG_DUMP_GTID` 从这个集合重新打开 dump。任务保持 `RUNNING`。open 分段仍只有 4 字节 magic 头时被删掉。不封存，不上传。旧分段里已经有的字节留在那里。
- 第一台服务器的文件保持源文件名，例如 `mysql-bin.000003`。之后那台服务器的文件是 `{server_uuid}.{binlog file}`，例如 `<server_uuid>.mysql-bin.000001`。已经带这个前缀的名字不会再加一次。两台服务器都轮转到 `mysql-bin.000001` 时，不会共用一个文件。对象键仍是 `prefix/cluster_key/<写下该文件的身份>/<file name>`。封存旧分段用旧身份。之后的文件在键里和文件名里都用新身份。任务目录里的 `.source-chain` 一行一个身份。第一行是无前缀文件名的主人。这个文件留在原地。接管时这份名单跟分段放在一起，在分段目录里继续的 worker 不会给这些文件再记一个主人。继续还在打开新服务器时，`.source-resume-gtid` 放着已执行集合。checkpoint 的文件已经属于那台服务器之后，这个文件被删掉。
- `GET /api/tasks/{id}/events` 在 runner 返回之前追加一条 `SOURCE_SWITCHOVER`。继续时 `message` 是 `source switched from <old> to <new> at <where>; continuing from the executed GTID set`。源文件名有值、位点不是 0 时，`<where>` 是 `<file>:<pos> gtid_set=<set>`。`<file>` 是源 binlog 名，例如 `mysql-bin.000003`，不是带 `{server_uuid}.` 的磁盘名。否则 `<where>` 就是已执行集合。`detail` 是 `old=<old> new=<new> gtid_set=<set> file=<file> pos=<pos>`。没有新指标，Console 也没有新控件。
- 这份备份不能不把两台服务器混在一起才能继续时，任务停在 `FAILED`。不会进入 `RETRY_BACKOFF`。`last_error` 是 `SOURCE_SWITCHOVER: ` 加上 message。message 是 `source switched from <old> to <new>. <why>. Start a new task against the new primary and keep this backup. This task will not mix the two servers.` `<why>` 是下面之一：`This backup has no GTID set, so the old source file and position cannot be applied to the new source`；`The new primary is missing transactions this backup already has`；`The new primary has purged transactions this backup does not have yet, so they cannot be copied`；`MariaDB has no usable GTID path for a source switch`。事件顺序是 `SOURCE_SWITCHOVER`，然后 `TASK_RUNNER_ERROR`，然后 `TASK_FAILED`。`POST /api/tasks/{id}/start` 会再做一次同样的检查。不会把新服务器追加进旧文件。已经存下的分段字节保持原样。
- 已经存过字节、却没有 GTID 集合的备份走这次停下。这是常见的 `LATEST` 任务，以及 checkpoint 没有 `gtid_set` 的 `FILE_POS` 任务。新主库对旧文件名返回的 MySQL 1236 就是这次停下。它不会被改写成 `MySQL 1236: the source purged the binlog this task resumes from, and no GTID is stored`。已经有已执行 GTID 集合的 `FILE_POS` 任务，在新主库仍持有这个集合时继续，包括第一次 dump 的回答是 1236。同一台 `@@server_uuid`、又没有存下 GTID 的 1236，仍用那句 purged-binlog 文本。MariaDB 的身份是 `mariadb:<server_id>:<gtid_domain_id>`。这份备份已经存过事务或已有 GTID 集合之后，这个身份一变就停下。MariaDB 不会从 GTID 继续。
- `LATEST` 启动时还没有存过事务、也没有 checkpoint，地址已经是另一台服务器，就把新服务器记下来，并按配置的起点继续。message 含 `before any transaction was stored`。已经存过一条事件的 `LATEST` dump 再看到另一台服务器，因为这份备份没有 GTID 集合而停下。
- 把地址指回一台并不包含已存全部事务的服务器，是同一次停下。`last_error` 说明现在连上的这台缺少这份备份已经有的事务。封存文件不会被改写。
- `GET /api/tasks/{id}/window` 仍返回 `continuous`、`earliest`、`latest`、`breaks`，MySQL 链上有 GTID 事件时还有 `gtid_set`。缺源文件只在同一台服务器的文件名前缀里算缺口。新服务器的 `mysql-bin.000001` 接在旧服务器的 `mysql-bin.000009` 后面，不是 `missing source file`。同一台服务器内部的跳号仍是这种缺口，例如 `<server_uuid>.mysql-bin.000001` 之后是 `<server_uuid>.mysql-bin.000003`。两台服务器之间的 MySQL GTID 洞仍是 `gtid hole between <left> and <right>`。`breaks` 为空时 `continuous` 为 true。MariaDB 仍不增加 GTID 洞这种缺口。v0.5.56 的其他缺口句子没有改。
- `GET /api/tasks/{id}/files`、`GET /api/tasks/{id}/replay` 和 `GET /api/tasks/{id}/replay/archive` 把更早的服务器放在更晚的前面。更早的那台是最早的 `created_at` 更老的那台，所以旧服务器更高的序号仍在新服务器的 `mysql-bin.000001` 前面。同一台服务器内部仍按源序号，封存名在 open epoch 之前。`limit` 仍保留这个顺序的尾部。`stop_datetime` 和 `stop_gtid` 的 `paths` 和 `command` 用这个顺序。停止点本身没有改。`stop_datetime` 仍不含时间戳大于等于停止时间的事件。`stop_gtid` 仍停在那条 `GTID_EVENT` 的起始字节。
- 正在写的这台服务器上，GTID 重拉转回更早的文件时，不会另开第二份，也不会把那些事件再追加一次。位点不会往回退。新主库仍留着的更早文件，例如初始化时写下的文件，可以单独成为 `{server_uuid}.{binlog file}`。它不会替换旧服务器的无前缀文件。
- `smoke-source-switchover` 是可选场景：`./scripts/e2e/run-suite.sh --scenarios smoke-source-switchover`。不在 quick profile 里，也不在 full profile 里。两台 MySQL 8.0 做 GTID 复制。任务经过一个 TCP 代理。GTID 任务从建表前的 `GTID_EXECUTED` 启动。`LATEST` 任务从当时的尖端启动。副本提升、代理指到它之后，GTID 任务继续。旧分段封存，并且不含切换之后写入的行。新分段的文件名以新的 `server_uuid` 开头，并且含这些行。`SOURCE_SWITCHOVER` 写出两台身份。窗口是连续的。`stop_datetime` 和 `stop_gtid` 先列出旧服务器的文件，再列出新服务器的文件。把 `stop_datetime` 的命令回放到一台空的 MySQL 8.0，行和 `CHECKSUM TABLE` 与新主库一致。`stop_gtid` 停在最后一行之前，那一行不在恢复库里。`LATEST` 任务是 `FAILED`。`last_error` 以 `SOURCE_SWITCHOVER` 开头，写出两台身份，并说明没有 GTID 集合。把代理指回旧主库，并写入只有那台才有的一行，GTID 任务失败，因为现在连上的服务器缺少这份备份已经有的事务。已有分段的字节不变。场景不使用 MinIO。
- 没有新的配置项。没有 schema 迁移。`minRequiredSchemaVersion` 仍是 6。`migrations/` 仍是 `000001` 到 `000006`。没有 `000007`。ADR 0005 没有改。第 1 到第 9 步已经发出。第 9 步在 v0.5.53 发出。这一版不是新的 ADR 步骤。PR #288 只改了 `smoke-gtid-pitr` 和 `smoke-gtid-executed`。恢复实例要在 TCP 登录成功，并且 `RESET MASTER`（8.4 起为 `RESET BINARY LOGS AND GTIDS`）之后 `gtid_executed` 为空时才接收回放。对镜像里那个临时初始化进程的 socket 做 `SELECT 1` 不算这台服务器。操作员没有新的开关，也没有新的错误。

## 升级影响

换二进制之前，确认任务地址仍连到写下现有无前缀文件的那台 MySQL。这些名字是 `mysql-bin.NNNNNN`，没有 `server_uuid` 前缀。v0.5.57 第一次启动把当时连上的 `@@server_uuid` 记成这些文件的主人，写在 `{data_dir}/{task_id}/.source-chain`。VIP 已经切走时，不要在新主库上启动这条旧任务。对新主库新建任务，保留这份备份。删掉 `.source-chain` 会让下一次启动把现在这个地址连上的服务器记成主人。写好之后把这个文件留在原地。

没有新迁移。已经在 v0.5.56 / schema 6 上的库仍是 schema 6。确认 `SELECT version, dirty FROM schema_migrations` 是 `(6, 0)`。`migrations/` 仍是 `000001`、`000002`、`000003`、`000004`、`000005` 和 `000006`。没有 `000007`。

`minRequiredSchemaVersion` 仍是 6。v0.5.57 在 schema 5 上不会启动，以退出码 1 结束，还没开始监听。提示含 `schema version too old` 和 `./migrate up`。这与 v0.5.56 的拒绝相同。schema 4 和 schema 3 同样拒绝启动。

schema 6 已经就位之后再换二进制。库已经是 v0.5.56 / schema 6 时，没有 `./migrate` 这一步。还不是 schema 6 时，先按 [v0.5.56 中文发布说明](v0.5.56.zh-CN.md)，确认 `(6, 0)`，再启动 v0.5.57。

地板仍是 v0.5.51，它是第一版同时带上 ADR 0005 第 6 步和第 7 步的发布。v0.5.50 只发了第 6 步。`./migrate up` 到 schema 6 之前，先停掉仍要求 `uk_task_file_epoch` 的每一台进程。v0.5.51 和 v0.5.52 就是这些二进制。schema 6 上它们拒绝启动。日志含 `missing index` 和 `uk_task_file_epoch`。比 v0.5.51 旧的进程，包括 v0.5.50，都不是地板。`000006` 之前先换掉。然后停掉 v0.5.51 和 v0.5.52。然后执行 `./migrate up`。

schema 4（`000004_pending_dump_cleanup`）仍在迁移链上。v0.5.50 之前，schema 4 是单进程可选、集群必须。分步升级、启动的仍是比 v0.5.50 旧的二进制时，这条规则还适用。v0.5.57 自己不能停在 schema 4。

如果这套库还不是 schema 3，先按 [v0.5.46 中文发布说明](v0.5.46.zh-CN.md)，再按 v0.5.50，再按 v0.5.53。schema 2 到 schema 3（`000003_task_desired_and_retry_budget`）在线。schema 1 到 schema 2 仍按 [v0.5.34 升级说明](v0.5.34.zh-CN.md)：停掉每一台进程，执行 `./migrate up`，然后只启动 v0.5.34 或更新的二进制。

没有新的配置项。没有元数据库的 standalone 不跑这些迁移。切换用的是任务地址连上的身份，以及本进程数据目录里的分段，所以 standalone 上是同一条规则。`start_gtid_set` 仍读本进程打得开的分段。窗口仍读这些分段。

不要 `./migrate down` 退过正在跑的二进制所需要的 schema。v0.5.57 需要 schema 6。这一版没有新迁移，所以没有新的 down 步骤。schema 6 上 `./migrate down --steps 1` 仍是 v0.5.53 的那次 down：把 `uk_task_file_epoch` 加回来。不删行。不删 `file_name`。不删 `uk_task_source_epoch`。回到 version 5。`binlog_files` 行数不变。已经有两行共用 `(task_id, file_name, epoch)` 时，这次 down 会失败。不要为了让它通过而删行。写入方保持 `file_name` 等于 `source_file`。v0.5.57 还在跑时不要做这次 down。v0.5.57 在 schema 5 上不会启动。生产环境的 `./migrate down` 仍要 `ALLOW_DESTRUCTIVE_MIGRATE=1` 才放行。

v0.5.53 的索引规则仍成立。`SHOW INDEX FROM binlog_files` 列出 `uk_task_source_epoch`，不列出 `uk_task_file_epoch`。`file_name` 列还在。再插入相同的 `(task_id, source_file, epoch)` 会失败。重复键是 `uk_task_source_epoch`。

v0.5.52 清理 `.takeover-*` 的规则仍成立。worker 仍会删掉任务目录里留下的普通 `.takeover-*`。v0.5.51 的未知 `end_pos` 规则仍成立。本进程读不到本地字节时，`GET /api/tasks/{id}/files` 的未知 `end_pos` 是 JSON `null`，Console 单元格是空白。本地文件能读到事件时，给出事件跨度。

v0.5.56 的可恢复窗口仍成立。v0.5.55 的 `start_gtid_set` 规则仍成立。v0.5.54 的 `stop_gtid` 规则仍成立。v0.5.49 的封存位点规则（#189）和 v0.5.48 的空 `task-<id>.binlog` 规则（#205）仍成立。`stop_datetime` 没有改。时间戳大于等于停止时间的事件仍不进入那条命令。保留没有改。BinlogServerQA 的 tip dogfood 在 `62f2251a` 上为 PASS。

这一版不是 ADR 0005 的步骤。第 1 到第 9 步已经发出。ADR 0005 没有改。发出第 9 步的是 v0.5.53。

## 已知行为

#224 已在 v0.5.52 修好。#189 已在 v0.5.49 修好。#205 已在 v0.5.48 修好。`stop_gtid` 在 v0.5.54 发出。`start_gtid_set` 在 v0.5.55 发出。可恢复窗口在 v0.5.56 发出（PR #285）。这一版没有再改这些修复。这一版不是 ADR 0005 的步骤。ADR 0005 没有改。

- `stop_datetime` 仍按事件头的秒切开。同一秒里的事务在时间路径上仍是一起进或一起出。已经知道坏 GTID 时用 `stop_gtid`。`start_gtid_set` 不改变这个停止点。窗口也不改变这个停止点。源切换也不改变这个停止点。跨两台服务器时，更早的那台排在前面。
- 盖不住要应用的第一段之前那些事务的集合会被拒绝。回放不会跳过这个缺口。
- 缺源文件只在同一台服务器内部算缺口。新服务器的序号从 `mysql-bin.000001` 重新开始不是这种缺口。旧服务器和新服务器之间的 MySQL GTID 洞仍是缺口。回放仍返回打得开的分段。不会把缺掉的名字补回 `paths`。
- 任务从源文件中部接入不是 GTID 洞。第一件已存事件之前的序号不进 `gtid_set`。
- 同一个 `@@server_uuid` 不是切换。这台服务器上没有存下 GTID 的 MySQL 1236，仍是那句 purged-binlog 文本。另一台服务器、又没有存下 GTID，是 `SOURCE_SWITCHOVER`，包括错误是旧文件名的 1236。
- `SOURCE_SWITCHOVER` 不会把两台服务器混在一起。再次启动同一条任务会再做一次检查。停下之后要在新主库上继续复制，就新建任务，并保留这份备份。
- schema 仍是 6。地板仍是 v0.5.51。没有 `000007`。`file_name` 仍是一列。更晚那台服务器的 `file_name` 是 `{server_uuid}.{binlog file}`。
