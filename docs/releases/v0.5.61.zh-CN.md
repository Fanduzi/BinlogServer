# Binlog Server v0.5.61 中文发布说明

> 对应版本：`v0.5.61`

发布日期：2026-10-13

v0.5.61 让 `GET /api/tasks/{id}/replay` 和 `/replay/archive` 拒绝不合法的 `limit`，不再悄悄返回完整集合（#307，PR #311）。定点恢复请求里的 `limit` 被忽略时，响应也会写明。以前把 `limit=-1` 或 `limit=abc` 写错了，仍返回 HTTP 200 和完整回放集，看不出这个值被丢掉了；现在是 HTTP 400。其它没有变化。没有新配置项。没有 schema 迁移。schema 仍是 6。`minRequiredSchemaVersion` 仍是 6。地板仍是 v0.5.51。BinlogServerQA 对 main `5c18b1e4608418eec8c6adaecacd5ae639e4b3eb`（evidence-311）的 dogfood 通过，没有 P0、P1、P2。一个 P3 记为 #312。

**历史改写。** BinlogServer 的提交历史在 2026-10-12 改写过（见 v0.5.60 说明）。此前的提交哈希都变了。请按 tag 或 PR 号查找改动。

## 核心变化

- **不合法的 `limit` 返回 HTTP 400（#307，PR #311）。** `limit` 必须是正整数。`0`、负数、空值、小数（`1.5`、`1e3`）、文本、或服务端放不下的大数，都返回 HTTP 400，正文 `invalid limit: must be a positive integer`。JSON 的 `/replay` 和 `/replay/archive` 都这样，普通回放和带 `stop_datetime`、`stop_gtid`、`start_gtid_set` 的请求都这样。以前这些都返回 200 和完整集合。
- **定点恢复请求带 `limit` 时会提示。** 带 `stop_datetime`、`stop_gtid` 或 `start_gtid_set` 时，合法的 `limit` 仍不起作用：定点集合总是列出恢复需要的每个文件。JSON 的 `warning` 现在写 `limit is ignored with stop_datetime, stop_gtid or start_gtid_set: a point-in-time set always lists every file it needs.`，tar 在 `X-Replay-Warning` 里给同样的文字。不带 `limit` 时没有 warning，也没有这个响应头。
- **没有变化的部分。** 普通回放带合法 `limit` 时，路径、`omitted_files`、`warning` 和 tar 响应头与 v0.5.60 相同。不带 `limit` 的 `/replay` 仍返回全部文件。控制台不发送 `limit`。
- **文档。** API 参考（5.6 节和 archive 一节）写明了 400 和 warning。

## 升级影响

- 发送 `limit=0`、负数、空的 `limit=` 或非整数的脚本，现在拿到 HTTP 400，而不是完整集合。要全部文件就去掉这个参数，否则传正整数。
- 在 `stop_datetime`、`stop_gtid` 或 `start_gtid_set` 请求里带 `limit` 的工具，拿到的集合和以前一样，只是多了 `warning`（JSON）或 `X-Replay-Warning`（tar）。如果你的工具把任何 `warning` 当作失败，就别在定点恢复请求里传 `limit`，它在那里从来不起作用。

没有新迁移。已经在 schema 6 上的库仍是 schema 6。确认 `SELECT version, dirty FROM schema_migrations` 是 `(6, 0)`。`migrations/` 仍是 `000001` 到 `000006`，没有 `000007`。`minRequiredSchemaVersion` 仍是 6：v0.5.61 在 schema 5 上不会启动，以退出码 1 结束，还没开始监听，提示含 `schema version too old` 和 `./migrate up`。还不是 schema 6 时先按 [v0.5.56 升级](v0.5.56.zh-CN.md)。地板仍是 v0.5.51。没有新配置项。v0.5.60 的 `/replay` 规则、v0.5.59 的旧版回切规则和 v0.5.58 的 `storage_alert` 规则仍成立。

## 已知行为

- #312（P3）：`limit` 出现多次时只取第一个值，所以 `limit=5&limit=abc` 返回 200 和 5 个文件；`limit=abc&limit=5` 是 400。`+5`、` 5`（前面带空格）和 `9223372036854775807`（int64 最大值）被当作合法值接受。
- 服务端消息（包括新的 400 正文和 `warning`）只有英文。
- v0.5.60 和 v0.5.59 的已知行为仍适用，但 #307 已在这一版修复。

## QA 摘要

BinlogServerQA，main `5c18b1e`，对照 c7f3331（v0.5.60 文档提交）。通过，没有 P0/P1/P2。

- 不合法的 `limit`：`0`、`-1`、`abc`、空、`1.5`、`1e3`、`99999999999999999999` 和 `abc&limit=5`，在 JSON 和 tar、普通回放和三种定点恢复上都返回 400 `invalid limit: must be a positive integer`。对照版本返回 200 和完整集合。
- 定点恢复带合法 `limit`：路径和 tar 成员与不带 `limit` 的请求、与对照版本都相同。JSON `warning` 和 tar `X-Replay-Warning` 都有；不带 `limit` 时都没有。
- 普通回放不带 `limit` 以及 `limit` 为 1/200/201/366/367/100000：路径、`omitted_files`、`warning`、tar 成员和响应头与对照版本相同。
- 浸泡：`max_binlog_size` 128 KB 的 GTID 任务有 366 个回放文件。按默认 `/replay` 和 `/replay/archive`（366 个成员）恢复，两个版本的结果都与源库校验和一致。
- 回归：storage alert 和旧版回切的回放 warning 与对照版本相同。api/tasks 的 `go test` 通过。控制台资源没有变化，不发送 `limit`。
