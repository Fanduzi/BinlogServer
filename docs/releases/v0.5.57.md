# Binlog Server v0.5.57

Release date: 2026-10-07

A task whose host:port is a VIP, a DNS name, or a proxy continues when that address reaches a different MySQL `@@server_uuid`, and only when this backup already has an executed GTID set and the new primary still holds every transaction already stored. The open segment from the old server is sealed. Later files are named `{server_uuid}.{binlog file}`, so the two servers never share a file name. `GET /api/tasks/{id}/events` records one `SOURCE_SWITCHOVER`. `GET /api/tasks/{id}/window` reports whether the chain is continuous across that point. `GET /api/tasks/{id}/replay` with `stop_datetime` or `stop_gtid` lists the old server's files first. Otherwise the task stops as `FAILED`. `last_error` starts with `SOURCE_SWITCHOVER`, names both servers, and tells you to start a new task against the new primary and keep this backup. That stop covers a stored backup with no GTID set, which is `LATEST` and `FILE_POS` with no stored set, including MySQL 1236 for the old file name, a new primary that is missing transactions this backup already has, a new primary that has purged transactions this backup does not have yet, and MariaDB. A `FILE_POS` backup that already has an executed GTID set uses the continue path, including when the new primary returns 1236 for the old file name. No new config key. No schema migration. Schema stays 6. `minRequiredSchemaVersion` stays 6. ADR 0005 is unchanged. The floor stays v0.5.51. Before upgrading, confirm the address still reaches the server that wrote the existing unprefixed files. The first start after upgrade records that server as the owner of those files. Tip dogfood by BinlogServerQA passed on `62f2251ad2bb70458d05f5524f78f075b9feabaf` (evidence-289). That run did not open a new issue. The v0.5.56 recoverable window still holds (PR #285). The v0.5.55 `start_gtid_set` rule still holds (PR #282). The v0.5.54 `stop_gtid` rule still holds (PR #279). The v0.5.49 sealed-position rule (#189) still holds. The v0.5.48 empty `task-<id>.binlog` rule (#205) still holds. The v0.5.52 `.takeover-*` cleanup still holds (#224, PR #273). The v0.5.53 drop of `uk_task_file_epoch` still holds (PR #276). VIP switchover landed in PR #289. PR #288 only waits for the real e2e restore server before `RESET MASTER`. It is not a product behavior change.

## Highlights

- The check is the identity now reached at the task host and port. On MySQL that identity is `@@server_uuid`. The same identity is not a switch. A source restart of the same server still seals the previous file at the last real event and continues on the next file. A different identity is a switch. The decision runs at the start of a run when `{data_dir}/{task_id}/.source-chain` already names another server, when a new dump connection reports another server, and when the dump returns an error before the next event, including MySQL 1236 from `StartSync` or the first read. The event that discovered the switch is not appended. On a dump error, a failed identity read, an empty identity, or the same identity leaves that error unchanged. A failed identity read before an event is written is that read's error.
- Continue when `source.flavor` is `mysql`, this backup has an executed GTID set, `GTID_SUBSET` of that set against the new primary's `@@gtid_executed` is true, and any transaction the new primary has that this backup does not is still in the binlogs. At the start of a run the set is the checkpoint `gtid_set`. When that is empty and the task mode is `GTID`, the set is the task's start `gtid_set`. On a dump that is already open, the set is the executed set tracked from the stream. The old open segment is sealed under the server that wrote it, then the dump reopens with `COM_BINLOG_DUMP_GTID` from that set. The task stays `RUNNING`. An open segment that still has only the 4-byte magic header is deleted. It is not sealed and not uploaded. Bytes already in the old segment stay there.
- The first server's files keep the source basename, such as `mysql-bin.000003`. A later server's files are `{server_uuid}.{binlog file}`, such as `<server_uuid>.mysql-bin.000001`. A name that already has that prefix is not prefixed again. Two servers that both rotate through `mysql-bin.000001` do not share a file. The object key stays `prefix/cluster_key/<writer identity>/<file name>`. Sealing the old segment uses the old identity. A later file uses the new identity in both the key and the file name. `.source-chain` in the task directory is one identity per line. The first line owns the unprefixed names. Leave that file in place. Takeover keeps it next to the segments, so a worker that continues in that segment directory does not record a second owner for those files. While the continue is still opening the new server, `.source-resume-gtid` holds the executed set. It is removed once a checkpoint file belongs to that server.
- `GET /api/tasks/{id}/events` appends one `SOURCE_SWITCHOVER` before the runner returns. `message` on the continue path is `source switched from <old> to <new> at <where>; continuing from the executed GTID set`. When the source file name is set and the position is not 0, `<where>` is `<file>:<pos> gtid_set=<set>`. `<file>` is the source binlog name, such as `mysql-bin.000003`, not the `{server_uuid}.` disk name. Otherwise `<where>` is the executed set. `detail` is `old=<old> new=<new> gtid_set=<set> file=<file> pos=<pos>`. There is no new metric and no new Console control.
- The task stops as `FAILED` when the backup cannot continue without mixing the two servers. It does not enter `RETRY_BACKOFF`. `last_error` is `SOURCE_SWITCHOVER: ` plus the message. The message is `source switched from <old> to <new>. <why>. Start a new task against the new primary and keep this backup. This task will not mix the two servers.` `<why>` is one of: `This backup has no GTID set, so the old source file and position cannot be applied to the new source`; `The new primary is missing transactions this backup already has`; `The new primary has purged transactions this backup does not have yet, so they cannot be copied`; `MariaDB has no usable GTID path for a source switch`. The event list is `SOURCE_SWITCHOVER`, then `TASK_RUNNER_ERROR`, then `TASK_FAILED`. `POST /api/tasks/{id}/start` runs the check again. It does not append the new server into the old files. Stored segment bytes stay as they are.
- A stored backup with no GTID set takes that stop. That is the usual `LATEST` task, and a `FILE_POS` task whose checkpoint has no `gtid_set`. MySQL 1236 for the old file name on the new primary is this stop. It is not rewritten as `MySQL 1236: the source purged the binlog this task resumes from, and no GTID is stored`. A `FILE_POS` task that already has an executed GTID set continues when the new primary still has that set, including when the first dump answer is 1236. The same `@@server_uuid` and a 1236 with no stored GTID still use that purged-binlog text. MariaDB identity is `mariadb:<server_id>:<gtid_domain_id>`. A change of that identity stops once this backup has stored a transaction or has a GTID set. MariaDB does not continue from GTID.
- On a `LATEST` start that has not stored a transaction and has no checkpoint, a different server is recorded and the configured start continues. The message contains `before any transaction was stored`. A live `LATEST` dump that has already stored an event, and then sees another server, stops because that backup has no GTID set.
- Pointing the address back at a server that does not contain every transaction already stored is the same stop. `last_error` says the server now reached is missing transactions this backup already has. The sealed files are not rewritten.
- `GET /api/tasks/{id}/window` still returns `continuous`, `earliest`, `latest`, `breaks`, and, for a MySQL chain with GTID events, `gtid_set`. A missing source file is a break only inside one server's name prefix. The new server's `mysql-bin.000001` after the old server's `mysql-bin.000009` is not `missing source file`. A hole inside one server, such as `<server_uuid>.mysql-bin.000001` then `<server_uuid>.mysql-bin.000003`, is still that break. A MySQL GTID hole between the two servers is still `gtid hole between <left> and <right>`. `continuous` is true when `breaks` is empty. MariaDB still does not add a GTID-hole break. The other v0.5.56 break sentences are unchanged.
- `GET /api/tasks/{id}/files`, `GET /api/tasks/{id}/replay`, and `GET /api/tasks/{id}/replay/archive` put an earlier server before a later one. The earlier server is the one whose earliest `created_at` is older, so the old server's higher index stays ahead of the new server's `mysql-bin.000001`. Inside one server the order is still the source index, sealed name before open epochs. `limit` still keeps the tail of that order. `stop_datetime` and `stop_gtid` use that order for `paths` and `command`. The stop itself is unchanged. `stop_datetime` still leaves out an event whose timestamp is greater than or equal to the stop. `stop_gtid` still stops at the starting byte of that `GTID_EVENT`.
- A GTID redump that rotates back to an earlier file of the server already being written does not open a second copy of that file and does not append those events again. The cursor does not move backward. An earlier file the new primary still has, such as a file written at initialization, can be its own `{server_uuid}.{binlog file}`. It does not replace the old server's unprefixed file.
- `smoke-source-switchover` is opt-in: `./scripts/e2e/run-suite.sh --scenarios smoke-source-switchover`. It is not in the quick profile and not in the full profile. Two MySQL 8.0 servers replicate with GTID. The task connects through a TCP proxy. The GTID task starts from `GTID_EXECUTED` before the table is created. The `LATEST` task starts at the tip. After the replica is promoted and the proxy points at it, the GTID task continues. The old segment is sealed and does not contain the rows written after the switch. A new segment name starts with the new `server_uuid` and contains those rows. `SOURCE_SWITCHOVER` names both identities. The window is continuous. `stop_datetime` and `stop_gtid` list the old server's files, then the new server's files. Replaying the `stop_datetime` command onto an empty MySQL 8.0 matches the new primary's rows and `CHECKSUM TABLE`. `stop_gtid` stops before the last row, and that row is not on the restored server. The `LATEST` task is `FAILED`. `last_error` starts with `SOURCE_SWITCHOVER`, names both identities, and says there is no GTID set. Pointing the proxy back at the old primary, and writing a row only that server has, fails the GTID task because the server now reached is missing transactions this backup already has. Existing segment bytes stay. The scenario does not use MinIO.
- No new config key. No schema migration. `minRequiredSchemaVersion` stays 6. `migrations/` is still `000001` through `000006`. There is no `000007`. ADR 0005 is unchanged. Steps 1–9 already shipped. Step 9 shipped in v0.5.53. This release is not a new ADR step. PR #288 changes `smoke-gtid-pitr` and `smoke-gtid-executed` only. The restore server is accepted after TCP login and after `RESET MASTER` (`RESET BINARY LOGS AND GTIDS` on 8.4) leaves `gtid_executed` empty. A socket `SELECT 1` against the image's temporary init server is not that server. Operators do not get a new flag or a new error.

## Upgrade Notes

Before you replace the binary, confirm the task address still reaches the MySQL that wrote the existing unprefixed files. Those names are `mysql-bin.NNNNNN` with no `server_uuid` prefix. The first start of v0.5.57 records the `@@server_uuid` reached at that moment as the owner of those files, in `{data_dir}/{task_id}/.source-chain`. If the VIP has already moved, do not start this task on the new primary. Start a new task against the new primary and keep this backup. Deleting `.source-chain` makes the next start record whoever the address reaches now. Leave the file in place after it is written.

No new migration. A database already on schema 6 from v0.5.56 stays on schema 6. Confirm `SELECT version, dirty FROM schema_migrations` is `(6, 0)`. `migrations/` is still `000001`, `000002`, `000003`, `000004`, `000005`, and `000006`. There is no `000007`.

`minRequiredSchemaVersion` remains 6. v0.5.57 does not start on schema 5. It exits with code 1 before it listens. The message contains `schema version too old` and `./migrate up`. That is the same refusal as v0.5.56. Schema 4 and schema 3 exit the same way.

Replace the binary after schema 6 is already in place. If the database is already v0.5.56 / schema 6, there is no `./migrate` step. If it is not schema 6 yet, follow the [v0.5.56 upgrade](release-notes-v0.5.56.md) first and confirm `(6, 0)`, then start v0.5.57.

The floor stays v0.5.51, the first release that ships both ADR 0005 step 6 and step 7. v0.5.50 shipped step 6 only. Stop every process that still requires `uk_task_file_epoch` before `./migrate up` to schema 6. v0.5.51 and v0.5.52 are those binaries. On schema 6 they refuse to start. The log contains `missing index` and `uk_task_file_epoch`. A process older than v0.5.51, including v0.5.50, is not the floor. Replace it before `000006`. Then stop v0.5.51 and v0.5.52. Then run `./migrate up`.

Schema 4 (`000004_pending_dump_cleanup`) is still in the chain. Before v0.5.50, schema 4 was optional for one process and required for cluster mode. That rule still applies when you upgrade stepwise and the binary you start is older than v0.5.50. v0.5.57 does not start on schema 4.

If this database is not already schema 3, follow the [v0.5.46 upgrade](release-notes-v0.5.46.md), then the v0.5.50 upgrade, then the v0.5.53 upgrade. Schema 2 to schema 3 (`000003_task_desired_and_retry_budget`) is online. Schema 1 to schema 2 still follows the [v0.5.34 upgrade](release-notes-v0.5.34.md): stop every binlog-server on that database, run `./migrate up`, then start only v0.5.34 or newer.

No new config key. Standalone with no metadata database does not run these migrations. The switch uses the identity reached at the task address and the segments in this process's data directory, so standalone follows the same rule. `start_gtid_set` still reads the segments this process can open. The window still reads those segments.

Do not run `./migrate down` past the schema the running binaries need. v0.5.57 needs schema 6. This release adds no migration, so there is no new down step. `./migrate down --steps 1` from schema 6 is still the v0.5.53 down: it adds `uk_task_file_epoch` back. It does not delete rows. It does not drop `file_name`. It does not drop `uk_task_source_epoch`. It returns to version 5. The `binlog_files` row count is unchanged. If two rows already share `(task_id, file_name, epoch)`, that down fails. Do not delete rows to make it pass. The writer keeps `file_name` equal to `source_file`. Do not run that down while v0.5.57 is running. v0.5.57 does not start on schema 5. Production `./migrate down` stays blocked unless `ALLOW_DESTRUCTIVE_MIGRATE=1`.

The v0.5.53 index rule still holds. `SHOW INDEX FROM binlog_files` lists `uk_task_source_epoch` and does not list `uk_task_file_epoch`. The `file_name` column stays. A second insert of the same `(task_id, source_file, epoch)` fails. The duplicate key is `uk_task_source_epoch`.

The v0.5.52 `.takeover-*` cleanup still holds. A worker still removes a regular `.takeover-*` left in a task directory. The v0.5.51 unknown-`end_pos` rule still holds. Unknown `end_pos` is JSON `null` on `GET /api/tasks/{id}/files`, and the Console cell is blank, when this process cannot read the local bytes. A readable local file shows the event span.

The v0.5.56 recoverable window still holds. The v0.5.55 `start_gtid_set` rule still holds. The v0.5.54 `stop_gtid` rule still holds. The v0.5.49 sealed-position rule (#189) and the v0.5.48 empty `task-<id>.binlog` rule (#205) still hold. `stop_datetime` is unchanged. It still leaves out an event whose timestamp is greater than or equal to the stop. Retention is unchanged. Tip dogfood by BinlogServerQA passed on `62f2251a`.

This release is not an ADR 0005 step. Steps 1–9 already shipped. ADR 0005 is unchanged. v0.5.53 is the release that shipped step 9.

## Known behavior

#224 was fixed in v0.5.52. #189 was fixed in v0.5.49. #205 was fixed in v0.5.48. `stop_gtid` shipped in v0.5.54. `start_gtid_set` shipped in v0.5.55. The recoverable window shipped in v0.5.56 (PR #285). This release does not change those earlier fixes. This release is not an ADR 0005 step. ADR 0005 is unchanged.

- `stop_datetime` still cuts on the event-header second. Transactions that share that second are still all in or all out on the datetime path. Use `stop_gtid` when the bad GTID is known. `start_gtid_set` does not change that stop. The window does not change that stop. A source switch does not change that stop. Across two servers, the older source is listed first.
- A set that does not cover the transactions before the first segment that would be applied is refused. The replay does not skip that hole.
- A missing source file is a break only inside one server. The new server's index starting again at `mysql-bin.000001` is not that break. A MySQL GTID hole between the old server and the new server is still a break. Replay still returns the segments it can open. It does not put a missing name back into `paths`.
- A task that joins a source file in the middle is not a GTID hole. Sequences before the first stored event stay out of `gtid_set`.
- The same `@@server_uuid` is not a switch. MySQL 1236 on that server, with no stored GTID, is still the purged-binlog text. A different server with no stored GTID is `SOURCE_SWITCHOVER`, including when the error is 1236 for the old file name.
- `SOURCE_SWITCHOVER` does not mix the two servers. Start the same task again and the check runs again. To keep copying on the new primary after a stop, create a new task and keep this backup.
- Schema stays 6. The floor stays v0.5.51. There is no `000007`. `file_name` stays a column. A later server's `file_name` is `{server_uuid}.{binlog file}`.
