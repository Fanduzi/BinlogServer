# Binlog Server v0.5.10 中文发布说明

> 对应版本：`v0.5.10`

发布日期：2026-10-03

`v0.5.10` 是 `v0.5.9` 的运维补丁：standalone 没配 `meta_dsn` 时，用同一个 `data_dir` 重新启动后，能看到上次留下的 binlog 目录。

## 核心变化

- standalone 没配 `meta_dsn`，进程退出后，新进程用同一个 `data_dir` 启动：仍含封存文件或 `.open.e<epoch>` 分段的 `{data_dir}/{task_id}/` 会出现在 `GET /api/tasks` 和 Console 里，不必事先知道 id。id 就是目录名。`GET /api/tasks/{id}/files` 沿用已有的磁盘扫描约定。`file_name` 是源文件名。open 分段的 `file_path` 保留 `.open.e<epoch>`。`start_pos` 和 `end_pos` 是 0。顺序按源文件序号升序。checkpoint 仍是 404 `checkpoint not found`。这一行没有源库账号。Start 返回 400，正文是 `on-disk backup has no task metadata`，不会开始复制。配了 `meta_dsn` 时不会从磁盘发现目录。`binlog_files` 非空时仍以目录为准，磁盘上多出来的文件不会列出。没有新的配置键。不需要 schema migration。`3703c98` 的试用用的是自编译二进制，不是已发布的 v0.5.9 包。没配 meta 时，文件是 `mysql-bin.000004` 和 `mysql-bin.000005.open.e1`。`GET /api/tasks` 列出 id `1`，位点是 0，checkpoint 是 404，start 是 400。配了 meta 时，多出来的目录 `99` 没有列出。目录位点是 `mysql-bin.000005` start 478 end 806，以及 `mysql-bin.000006` start 4 end 479。磁盘上的 `mysql-bin.000099` 没有列出。
- 指南勘误：`docs/guide/admin/configuration.md` 不再写没配 `meta_dsn` 时 `GET /api/tasks/{id}/files` 返回 `[]`。已发布的 v0.5.9 压缩包里仍是那句。这是指南勘误，不是行为变化。
- Quick Start、落地页、部署文档、配置模板和 workers API 示例里的版本钉在 `v0.5.10`。

## 升级影响

- `v0.5.10` 不需要 schema migration。迁移仍只有 `000001_init_schema`。
- 配置键没有变化。`PRODUCTION=true` 仍要求非空 `--encryption-key`。
- standalone 没配 `meta_dsn`，进程退出后，新进程用同一个 `data_dir` 启动时，仍含封存文件或 `.open.e<epoch>` 分段的 `{data_dir}/{task_id}/` 会出现在 `GET /api/tasks` 和 Console 里，不必事先知道 id。`GET /api/tasks/{id}/files` 沿用已有的磁盘扫描约定（`file_name` 是源文件名，open 分段的 `file_path` 保留 `.open.e<epoch>`，`start_pos` 和 `end_pos` 是 0，按源文件序号升序）。checkpoint 仍是 404 `checkpoint not found`。这一行没有源库账号。Start 返回 400，正文是 `on-disk backup has no task metadata`，不会开始复制。配了 `meta_dsn` 时不会从磁盘发现目录。`binlog_files` 非空时仍以目录为准，磁盘上多出来的文件不会列出。
- `configuration.md` 不再写没配 `meta_dsn` 时 `GET /api/tasks/{id}/files` 返回 `[]`。已发布的 v0.5.9 压缩包里仍是那句。这是指南勘误，不是行为变化。
