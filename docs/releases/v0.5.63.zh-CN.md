# Binlog Server v0.5.63 中文发布说明

> 对应版本：`v0.5.63`

发布日期：2026-10-13

v0.5.63 修复 #322：RUNNING 任务在 binlog 轮转时封存 open 分段，此时 `GET /api/tasks/{id}/replay/archive`（以及带 `stop_datetime` / `stop_gtid` / `start_gtid_set` 的变体）和 JSON 的 `GET /api/tasks/{id}/replay` 可能返回 500（`lstat …/mysql-bin.0000NN.open.eN: no such file or directory` 或 `tar: write too long`）。现在不会了（PR #325）。`/ui/` 内置的 Vue 控制台也带上了 PR #320 的修复。没有新配置项。没有 schema 迁移。schema 仍是 6。`minRequiredSchemaVersion` 仍是 6。地板仍是 v0.5.51。除了这些 500 消失，API 返回码没有变化。BinlogServerQA 对 main `0ef91872a31d868eb076a3ba43f827105c08ff66` 的 tip dogfood 通过，没有发现问题。

**历史改写。** BinlogServer 的提交历史在 2026-10-12 改写过（见 v0.5.60 说明）。此前的提交哈希都变了。请按 tag 或 PR 号查找改动。

## 修复

- **轮转期间的 replay archive 和 replay（#322，PR #325）。**
  - 磁盘扫描会重读任务目录，直到两次一致。在读目录和 `stat` 之间消失的名字（封存时改名的 `.open.eN`，或保留期删掉的旧封存文件）会被丢掉，新出现的名字会补读，扫描不再报 `lstat … no such file`。
  - 打包成员按选择时的同一份清单打开。选中的 `.open.eN` 在这期间被封存时，读它封存成的文件（`name.sealed.eN`，或长度不短于、修改时间不早于清单所见 open 文件的 `name`）；找不到就从新的清单重新选择，最多 5 次。
  - `PITRReplay`、`GTIDReplay`、`ExecutedGTIDReplay` 按这一份清单打开分段，不再每个分段重读一次目录，规则相同。
  - 重试后 OPEN 成员仍不在本进程（例如别的 worker 的 OPEN catalog 行）时，返回原来的 404 `segment not found on this process`，不是 500。
  - 读取上限在 `io.Copy` 下也生效，open 分段打开后继续增长不会再导致 `tar: write too long`。
- **`/ui/` 的 Vue 控制台（PR #320）。**
  - `/auth/config`：只有 404（没有这个路由的旧服务端）才缓存 Bearer 回退。超时、网络错误或 5xx 只对这一次请求回退到 Bearer，下一次请求重新查询。以前在 `api_key` 模式下查询失败一次，页面会一直 401，要刷新才行。
  - 「留空表示不修改」的密码提示只在编辑任务时显示，新建时不显示。接管仍显示必填提示。

## 升级须知

- 替换二进制并重启即可。没有迁移，没有配置变化。
- 已经是 schema 6 的库保持 schema 6。确认 `SELECT version, dirty FROM schema_migrations` 是 `(6, 0)`。`migrations/` 仍是 `000001` 到 `000006`，没有 `000007`。v0.5.63 在 schema 5 上不会启动：以退出码 1 结束，还没开始监听，提示含 `schema version too old` 和 `./migrate up`。还不是 schema 6 时，先按 [v0.5.56 升级](release-notes-v0.5.56.md)。地板仍是 v0.5.51。
- v0.5.62 的 401 规则和 `/auth/config`、v0.5.61 的 `limit` 规则、v0.5.60 的 `/replay` 规则、v0.5.59 的 legacy failback 规则和 v0.5.58 的 `storage_alert` 规则仍成立。
- 从 v0.5.61 或更早版本升级，先读 [v0.5.62 说明](v0.5.62.zh-CN.md)：凭证错误返回 401，不再是 403。

## QA 摘要

BinlogServerQA，PR #325 与 main `0ef9187` 的 tip dogfood，2026-10-13，MySQL 8.0.46。通过，没有发现问题。

- #322 快速轮转（`max_binlog_size` 128 KB）：177 轮 × 4 种请求。PR #325 在 2120 次拉取中 0 错误。之前的 main `fd4c4dc` 有 36 次错误（archive 18/176，带 `stop_datetime` 的 archive 12/176，带 `stop_datetime` 的 JSON 6/176）：`500 tar write too long`、`500 lstat … open.e1` 和两次 404。tip `0ef9187` 上另外 960 次拉取 0 错误。
- 还原：PITR 还原、写入期间拉取的 20 个包（10 个全量、10 个 PITR）和最终 57 个文件的完整链都与源库校验一致。tip 上 4 次 PITR 还原，以及两个任务上 10.5 分钟的 soak（GTID 1-6404，无缺口）都与源库校验一致。
- 404：删掉 OPEN catalog 行后，`/files` 仍返回 404，replay/archive 不包含该文件。磁盘上缺失的封存文件返回干净的 404。
- 鉴权：两种模式共 66 个请求。凭证正确的 12 个返回 200（Bearer 不区分大小写），其余 54 个返回 401。
- Stop/Start 通过。有元数据库时 `kill -9` 后任务自动回到 RUNNING；没有时回到 STOPPED，adopt 从正确位点续传。
- `limit` 校验：16 个非法值全部 400。
- `tasks`、`api`、`binlog` 的 `go test` 通过；新的竞态测试在 `-race -count=3` 下通过。
- PR #320：浏览器实测两个控制台在 `/auth/config` 不再失败后都能在 `api_key` 模式下恢复；密码提示只在编辑时显示。
