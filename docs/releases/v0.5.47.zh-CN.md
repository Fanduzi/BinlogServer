# Binlog Server v0.5.47 中文发布说明

> 对应版本：`v0.5.47`

发布日期：2026-10-06

不在重试白名单上的错误，第一次就把任务打成 `FAILED`。主人租约清掉。写一条 `TASK_FAILED`。`desired_run` 写成 `STOP`，`failed_spec_revision` 写成当时的 `spec_revision`。`SOURCE_UNREACHABLE` 仍是连续 10 次。瞬时元数据错误没有任务级次数上限，元数据库恢复后回到 `RUNNING`，不用 Start。`OBJECT_PURGE_FAILED` 不是任务失败。没有已存 GTID 的 MySQL 1236 第一次就 `FAILED`，`last_error` 写明 1236 和 purged binlog。已经在停的任务保持 `STOPPED`，不写 `TASK_FAILED`。没有新的指标，也没有通知器。这是 ADR 0005 的第 5 步，一共 9 步。没有新的配置项。没有新的迁移。`minRequiredSchemaVersion` 仍是 3。

## 核心变化

- 任务仍应继续跑时，白名单之外的错误第一次就失败。`GET /api/tasks/{id}` 是 `FAILED`，并带 `last_error`。`task_events` 有一条 `TASK_FAILED`。`owner_worker_id` 为空。`desired_run` 是 `STOP`，`failed_spec_revision` 等于 `spec_revision`。这里面包括 `SOURCE_ACCESS_DENIED`、`SOURCE_LOG_BIN_OFF`、`SOURCE_IDENTITY_UNAVAILABLE`、`SEALED_FILE_EXISTS`、非瞬时的 `CHECKPOINT_WRITE_FAILED`、`SEGMENT_NOT_ON_WORKER`、`EPOCH_NOT_ACQUIRED`、没有已存 GTID 的 MySQL 1236，以及 `classifyRunError` 认不出的 runner 错误，包括本地 append 或 flush。租约移交不是失败，不写 `FAILED`。以前停在 `RETRY_BACKOFF` 的未分类错误，现在第一次就 `FAILED`。`FAILED` 之后操作员 Start 仍会重新武装任务。
- 白名单只有三项，仍在同一次所有权里重试。`SOURCE_UNREACHABLE` 仍记在 `consecutive_source_failures` 上，第 10 次才 `FAILED` 并放开租约。dump 连上之后写成 0。瞬时元数据错误的文本名单在 `tasks.IsTransientMetadataError`。`meta.IsTransientMySQLError` 调用这个函数，子串相同：deadlock、lock wait timeout、connection reset、connection refused、broken pipe、server has gone away、invalid connection、bad connection、read-only、read only、timeout、eof。没有任务级次数上限。元数据库恢复后任务回到 `RUNNING`，不经过 `FAILED`，也不用操作员 Start。`OBJECT_PURGE_FAILED` 不是任务失败。下次打开文件会再删一次对象。
- 按文件和位点续传时，如果没有已存 GTID，MySQL 1236 第一次就 `FAILED`，不再停在 `RETRY_BACKOFF`。`last_error` 写明 1236 和 purged binlog。写一条 `TASK_FAILED`。租约放开。
- 任务已经是 `STOPPING` 或 `STOPPED`，或者库里的行已经是更新的一次 Stop 时，这次 runner 错误不进白名单。任务收成 `STOPPED`，不写 `TASK_FAILED`。Stop 时 `KILL` 连不上源库，行仍是 `STOPPED`，并留下 `pending_dump_cleanup`。这条路径不变。迁移 `000004` 已经在 main 上。这一步不加 `000005`。
- 操作员 Stop 不再停在 `STOPPING`。以前 dump 退出时如果拿一份比这次 Stop 更旧的快照去写 `STOPPED`，较新的 `spec_revision` 会留下那一行，`GET /api/tasks/{id}` 一直是 `STOPPING`，owner 和 epoch 还在。现在按这次 Stop 的 spec 写成 `STOPPED`，库里仍是这次 Stop 时再写一次。

## 升级影响

没有新的迁移。`minRequiredSchemaVersion` 仍是 3。v0.5.47 在 schema 3 上可以启动。schema 4（`000004_pending_dump_cleanup`）仍是单进程可选、集群必须，规则和 v0.5.46 一样。`migrations/` 仍是 `000001`、`000002`、`000003` 和 `000004`。下一个新迁移是 `000005`。

v0.5.47 在 schema 2 上不会启动，以退出码 1 结束，还没开始监听。提示含 `schema version too old` 和 `./migrate up`。

如果这套库还不是 schema 3，按 [v0.5.46 中文发布说明](v0.5.46.zh-CN.md)。schema 2 到 schema 3（`000003_task_desired_and_retry_budget`）在线。schema 1 到 schema 2 仍按 [v0.5.34 升级说明](v0.5.34.zh-CN.md)：停掉每一台进程，执行 `./migrate up`，然后只启动 v0.5.34 或更新的二进制。

没有新的配置项。没有元数据库的 standalone 不跑这些迁移。内存里的任务同样按这条失败规则处理。

v0.5.47 还在跑时不要 `./migrate down` 回到 schema 2。schema 4 上 `./migrate down --steps 1` 只丢掉 `pending_dump_cleanup`，回到 version 3。集群 worker 还依赖这一列时不要做这次 down。单进程可以留在 schema 3。

以前会停在 `RETRY_BACKOFF` 的未分类错误，以及没有已存 GTID 的 MySQL 1236，现在停在 `FAILED`。先处理原因，再 Start。`SOURCE_UNREACHABLE` 仍要连续 10 次。瞬时元数据抖动仍会自己回到 `RUNNING`。

## 已知行为

下面这些仍开着。#189、#205、#224 在这一版之前就有。ADR 0005 的第 6 到第 9 步不在这一版。

- 故障切换后，同名封存段的 `end_pos` 写成 0。跟踪为 #189。
- GTID 启动或 1236 回退后写入无 CRC 的人工 Rotate，校验失败，并产生多余的 `task-N.binlog`。跟踪为 #205。
- 接管下载 `UPLOADED` 对象时进程崩溃，`.takeover-*` 临时文件会一直留在磁盘上。重启、重试成功后都不清理。跟踪为 #224。
