# ADR 0011 PR-2：会话杀与 META_LOCK_STALLED

这是会话杀这一步的运维约定，不是已发布版本。v0.5.76 的校验和不变。调度器接管、迁移 000011、以及 `CREATE PROCEDURE binlog_server_kill_trx` 都在后续变更。

## RTO

起点是最后一次成功续租的库时钟（`task_leases.renewed_at`，即那次语句里的 `NOW(6)`）。本 epoch 还没有成功续租时，起点是 `Acquire` 提交的库时钟。终点是新 owner 的 `DumpReady` 提交。

```
lease_ttl + max(idle_kill, lock_wait) + claim_interval + start_to_ready
```

`start_to_ready` 是 10 秒：从 `STARTING` 已提交、目录可读、源接受 dump，到 `DumpReady` 提交。宽限不进公式。`side_kill` 不进公式。另一个 `worker_id` 的注册 TTL 不进跨节点公式。

缺省：TTL 15 秒，`idle_kill` 5 秒，`lock_wait` 4 秒，认领间隔 2 秒，`start_to_ready` 10 秒。`max(idle_kill, lock_wait)` 仍是 5 秒，上界 32 秒。现场 TTL 60 秒时上界是 77 秒。

`idle_kill` 是真正武装的服务器超时：MySQL 8 的 `wait_timeout`（以及同一上界的 `net_read_timeout`、`net_write_timeout`）；MariaDB 再加上 `idle_transaction_timeout`。`lock_wait` 是 `innodb_lock_wait_timeout`。空闲上界是 `min(5 秒, lease_ttl/2)`，至少 1 秒。`lock_wait` 把这个上界向下取整，至少 1 秒。缺省空闲上界 5 秒时它是 4 秒。

每一条拿锁的语句各自有客户端期限，从这条语句开始时算起：`innodb_lock_wait_timeout` 再加上 2 秒。健康插入、租约的 `SELECT … FOR UPDATE`、健康行的 `FOR UPDATE` 和健康 `UPDATE` 各有这一份。事务里更早花掉的时间不会把它压短。InnoDB 大约每秒才检查一次锁等待，1205 最多晚大约 1 秒，所以 2 秒的余量让服务器的 1205 通常先返回。若这条语句自己的期限先到，并且它已经跑了至少 `innodb_lock_wait_timeout`，也按锁等待分类，和服务器 1205 一样，并记下这次是按已经过去的时间分类的。外层上下文取消，或者语句在 `innodb_lock_wait_timeout` 之前就被取消，不是锁等待。整次健康写入仍有一个外层期限，只做兜底。

从池里等连接，和等一条语句，分开计。连接等到超时，只有在池已满（在用数等于上限）并且至少有一条正在进行的元数据写入已经确认在等锁、或者已经超过它自己的语句期限时，才算卡住。原因是 pool starvation behind a lock wait。池只是慢、没有锁证据时，仍是未确认的期限，不算卡住。

健康详情写 `side_kill=off`，演练通过之后才是 `on`。

语句执行中被冻住、又没有打开 `auto` 的事务，不在这个上界里。活着的 owner 不往前走，仍用配置的 `no_progress_after`（缺省 120 秒）再加一轮 sweep，不用 RTO 去夹。

## 同节点重启（F10）

同一 `node_id` 的 `per_node` 重启上界是跨节点 RTO 加上本节点自己的注册 TTL（`SameNodeRestartBound`）。缺省是 32 秒 + 15 秒 = 47 秒。干净重启不拿走尚未过期的注册。这段等待是 ADR 0001 的会话所有权：新进程和 `SIGSTOP` 分不清。没有改成「注册一过期就走一条特殊接管」。

## 会话变量

集群启动在每一条池连接和每一次重连上设置：

- `wait_timeout`
- `net_read_timeout`
- `net_write_timeout`
- `innodb_lock_wait_timeout`（每条锁语句的客户端期限比它多 2 秒，见上）
- MariaDB 再加上 `idle_transaction_timeout`

服务器拒绝其中一条 `SET`，集群拒绝启动。单机不武装。`ConnMaxIdleTime` 不超过 2 秒，并且不超过 `wait_timeout` 的三分之一，池会先关掉空闲连接，不让服务器杀掉它。上界在 2 秒及以下时不保留空闲连接（`MaxIdle` 为 0）。更长的上界保留 8 条。这只是池卫生，不是 RTO 的证明。

ProxySQL 或 MaxScale 可能吞掉 `SET`。启动时在一条刚从池里取出的连接上回读每一个武装过的变量，早于第一次租约写入：`wait_timeout`、`net_read_timeout`、`net_write_timeout`、`innodb_lock_wait_timeout`，MariaDB 再加上 `idle_transaction_timeout`。每次租约获取和续租在那次租约事务上读同一组。不一致，或者这次读取失败，从看见的那一刻起 `/api/health` 就报 degraded，包括启动时，不拒绝启动。没有改成要求这些上界必须是服务器全局值。

## 元数据库账号

卡住检测不需要 `PROCESS`，也不需要 `performance_schema`。给元数据库账号 `GRANT ALL ON binlog_server_meta.*` 就够：每条锁语句的客户端期限比 `innodb_lock_wait_timeout` 多 2 秒，真实行锁以 MySQL 错误 1205 结束。这条语句的期限若在锁超时之后先到，也是同一种卡住。

点名持有者是另一项检查。启动时跑点名查询（`performance_schema.data_lock_waits` 连接 `threads`，以及 `information_schema.innodb_lock_waits`），并且读一行。`LIMIT 0` 不会填充 `information_schema`，MariaDB 因此跳过 `PROCESS` 检查，只有库权限的账号会被当成能点名。MySQL 错误 1227 或 1142 表示账号用不了那个视图。`SHOW GRANTS` 的文本不是权限。`information_schema.innodb_trx` 成功也不够：没有 `PROCESS` 时它只返回本会话，而且不是每台服务器都会报错。只授了 `PROCESS` 的 MySQL 8 同样点不出持有者。点名查询没有答上之前，`lock_detail` 保持 `reduced`。进程打一条警告，`/api/health` 带 `"lock_detail":"reduced"`。这个字段不是 degraded 的原因，也不改变 HTTP 状态。检测仍靠 1205 打开 `META_LOCK_STALLED`。

## side_kill

`cluster.side_kill` 是 `off` 或 `auto`，缺省 `off`。`auto` 表示操作员确认到 meta 的连接是直连。不要开在会解析 SQL 的代理后面（ProxySQL、MaxScale 以及同类）。这类代理会自己处理 `KILL`，也会丢掉 `CALL`。

客户端不发 `KILL`。演练和真杀都是 `CALL binlog_server_kill_trx`。本变更不安装过程和 `meta_canary`。它们还不存在时，`auto` 保持 off。过程缺失或演练失败保持 off，不让 sweep 失败。

过程存在时，演练锁本节点自己的 `meta_canary` 行。MariaDB 没有 `performance_schema.data_locks`，所以第三条连接先等这把锁再 `CALL`；否则锁视图看不见，`auto` 保持 off。MySQL 8 还要有 `PROCESS`，并且能读 `performance_schema.data_locks`，缺了就保持 off。过程的 DEFINER 在服务器里仍要 `PROCESS`。`binlog_server_kill_trx` 的 `EXECUTE` 只授给 binlog-server 账号，不作为给其他账号的库级授权。RDS 上过程内部点名 `mysql.rds_kill`（RDS MySQL、RDS MariaDB、Aurora MySQL），不是客户端发的语句。服务器内部先看锁再杀的缝隙可以接受。

演练成功会在错误日志留下 `Aborted connection`。把这一行放进告警白名单。

## META_LOCK_STALLED（F12、N6）

结论写在任务 `_cluster` 上，主题是任务 id，由观察到等待的节点写入。这条路径不锁 `task_leases`，也不走 `applyOnce`。写入失败时，`/api/health` 仍用进程内的观察返回 503。

F12：一次锁等待不是页面。第二次观察才打开结论和 503。这比「单次等待就 503」更严。第一次 1205 只记次数。

关闭：同一个观察者连续两次拿到这把锁，第二次落在第一次之后的 `lock_wait` 之内。别的节点不算。超过 `lock_wait` 从第一次重新计。观察者不能从仍握着锁的持有者手里把锁拿走。

N6：观察者心跳早于有效 `node_gone_after` 之后，由 `_health` 持有者用同样的两次拿锁关闭。`_cluster` 的 Reconcile 不关闭不是它派生的结论。`META_LOCK_STALLED` 不是受管种类。

健康事务不重试 MySQL 1205。1205 是一次锁等待观察，包括写事务之前那条 `task_health` 插入。它不依赖 `PROCESS`。会话期限只有在这条连接正等着 `task_leases` 或 `task_health` 时才算锁等待（`performance_schema.data_lock_waits`，或者 `information_schema.innodb_trx` 的状态是 `LOCK WAIT`）。1205 这条路径不需要这些视图。视图能读时，错误里会补上挡住的会话。慢语句不算锁等待。连接在已确认的锁等待后面等到超时，也是同一种卡住。插入或主事务上的 1213 各重试一次；第二次 1213 留给下一轮 sweep。

## stale_after

有效 `stale_after` 是 `max(2×sweep + lock_wait, min(S, RTO))`。配置为 0 时 `S` 是 `5×sweep`。缺省 125 秒，长于一轮 60 秒 sweep。不会夹到一轮 sweep 以下。

## 回滚

回滚二进制。本变更没有迁移。旧二进制若不认识 `cluster.side_kill`，启动前从配置里去掉这一键。本树只接受 `off` 和 `auto`。
