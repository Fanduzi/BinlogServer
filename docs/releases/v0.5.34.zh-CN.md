# Binlog Server v0.5.34 中文发布说明

> 对应版本：`v0.5.34`

发布日期：2026-10-05

`v0.5.34` 之前，`binlog_files` 的唯一键是 `(task_id, file_name)`，`file_name` 记的是源 binlog 文件名。同一个源文件名后来再打开 `<name>.open.eN`，会改这一行。封存路径、上传状态、checksum 和对象键都被换成当前打开文件的值。回放和定点恢复随后只列出这段短的打开文件。只存在于更早封存段里的事件，不会出现在打印出来的恢复命令里。同一源文件名再封一次时，对象键相同，桶里上一份对象被覆盖。已发布的 v0.5.33 包仍然这样。

## 核心变化

- 唯一键改为 `(task_id, file_name, epoch)`。`file_name` 仍是源 binlog 文件名。这个名字的每个 epoch 各占一行。
- 迁移 `000002_binlog_file_epoch_key` 只在操作者执行 `./migrate up` 时运行。进程启动时不会自己做迁移。改唯一键之前，`file_path` 结尾是 `.open.eN` 或 `.sealed.eN` 的行，`epoch` 写成 N。普通封存名，例如 `mysql-bin.000001`，保持 epoch 0。这些行上已经记下的对象键保持原样。已经在桶里的对象，这次升级不用再传一次。
- 后一次打开只写自己的行。更早的封存行保持原来的路径、`UPLOADED`、checksum 和对象键。
- 一个源文件名第一次封存，仍用原来的对象键，叶子是源文件名。这个名字的封存文件已经在磁盘上，或者目录里已经有这个源文件名的另一个 epoch 时，后一次封存的叶子是 `name.sealed.eN`。
- 不带 `stop_datetime` 时，`GET /api/tasks/{id}/replay` 和 `GET /api/tasks/{id}/replay/archive` 列出 `limit` 窗口里的每一段封存，再加上该源序号上最高的打开分段。窗口仍是按源序号、再按 epoch 排序后的末尾。`limit` 默认 200，每个 epoch 占一行。本机上的封存文件，和只在桶里的封存文件，都会列入。同一序号上更低的打开分段不列入。被保留的打开行带着同一个对象键时，说明这些字节已经拷进当前打开文件，对应的封存路径不列入，同一份对象不会列两次。`locations` 仍是 `local`、`bucket` 或 `both`，顺序和 `paths` 相同。`bucket` 路径在字节下载下来之前，不要交给 `mysqlbinlog`。
- 同一组路由上的 `stop_datetime` 是定点恢复窗口。这个路径不用 `limit`。先读完整目录，每一段封存都有资格，每个源序号上最高的打开分段也有资格。打印出来的命令保留复制事件盖住 `[start, stop)` 的分段。落在这个区间里、只在桶里的封存文件会列入。对象键相同、字节已经拷进当前打开文件的封存路径，仍会去掉。
- 保留仍按每一段自己的目录行计算。`UPLOADED` 且 checksum 为 `match` 的分段，本地窗口和桶窗口与 v0.5.33 相同。`UPLOAD_FAILED` 留在本地磁盘上，目录行也留下。checksum 不一致，或者 checksum 比对没有做完，仍记成 `UPLOAD_FAILED`。上传过程中崩溃留下的封存文件，下次启动仍会补进重试集合，包括租约接管。封存之后的 PUT 仍受 `meta.timeout.upload_sec` 限制。没配对象存储时，封存仍是 `LOCAL_ONLY`，对象键是空的。这种任务上 `POST /api/tasks/{id}/files/retry-upload` 仍返回 HTTP 400，正文 `upload retry is not available`。
- 这个 worker 打开一个 binlog 文件时，同一源文件名、另一个 epoch 上的 `OPEN` 行会被删掉。封存行留下。该任务目录里文件已经不在本机磁盘上的 `OPEN` 行也会被删掉。别的源文件名、路径又在另一个目录下的 `OPEN` 行留下。
- `GET /api/tasks/{id}/files` 每个 epoch 返回一行。`file_name` 是源文件名。`file_path` 是这一段自己的路径。每一行有自己的 `state`、`upload_state`、checksum 和对象键。Console 文件表按路径一行一段，显示这一行的大小、位点、位置、上传状态、checksum 和对象键。默认 `limit` 同样是 200，每个 epoch 占一行。

## 已知行为

- 故障切换之后，后一次封存的分段，例如 `mysql-bin.NNNNNN.sealed.e1`，`end_pos` 可能是 0。`size_bytes` 是文件大小。这一行仍可以是 `UPLOADED`，checksum 为 `match`。文件列表里仍有这一段，下载和回放仍能返回它。跟踪为 #189。
- checksum 仍是上传之后比对一次。已经比对为 `match` 的对象，之后在桶里被换掉，不会再比对。

## 升级影响

**先停掉每一台使用这个元数据库的 binlog-server 进程。然后执行 `./migrate up`。然后再只启动 v0.5.34 二进制。** 还有旧进程连着这个库时，不要改表。

- 迁移 `000002_binlog_file_epoch_key` 只由 `./migrate up` 执行。服务进程不会自己做迁移。设置 `META_DSN`，或者传入 `--dsn`。默认迁移目录是 `./migrations`。
- v0.5.34 二进制要求 `schema_migrations` 至少为 2，并且存在索引 `binlog_files.uk_task_file_epoch`。在 schema 1 上启动会拒绝启动。错误是 `schema version too old: current=1 required>=2`。版本已经记成 2、索引却不在时，启动失败，错误是 `metadata schema is not up to date`，并点名 `missing index binlog_files.uk_task_file_epoch`。
- v0.5.33 二进制对着 schema 2 会拒绝启动。它的版本检查接受 schema 2，因为它只要求版本至少为 1。它接着要求索引 `binlog_files.uk_task_file`，而 `000002` 已经删掉这个索引。启动失败，错误是 `metadata schema is not up to date`，并点名 `missing index binlog_files.uk_task_file`。
- 回滚：先停掉全部进程，执行 `./migrate down --steps 1`，再启动 v0.5.33 二进制。这次 down 会删掉每个 `(task_id, file_name)` 上除最小 `id` 以外的全部 `binlog_files` 行，然后恢复唯一键 `uk_task_file`。被删掉的行没有了。`ENV` 或 `MIGRATE_ENV` 是 `prod` 或 `production` 时，down 会拒绝执行，直到加上 `--allow-destructive` 或 `ALLOW_DESTRUCTIVE_MIGRATE=1`。错误以 `refusing destructive migrate command in production` 开头。
- 已经记下的对象键保持原样。这次升级不要为这些对象重新上传。
- 没有新的上传状态。没有新的配置项。`meta.timeout.upload_sec` 默认仍是 30 秒。`cluster.failover_policy` 仍然不是开关。`PRODUCTION=true` 仍要求非空 `--encryption-key`。30 秒阈值没有变化。
