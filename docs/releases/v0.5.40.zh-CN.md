# Binlog Server v0.5.40 中文发布说明

> 对应版本：`v0.5.40`

发布日期：2026-10-06

同一进程上，一个任务在读事件或写事件时，其它任务的 Stop、Start、租约续约和进度更新以前会一起等。打开下一个 binlog 会把该任务的整份文件目录读进来。接管一个很大的已上传分段时，会把整个对象读进内存。一体进程或集群上，Start 和 `GET /api/tasks/{id}` 抢在一起时，新的一轮以前会按 epoch 0 拉流。打开的文件是裸名 `mysql-bin.NNNNNN`，租约不续，`GET /api/tasks/{id}` 停在 `STARTING`。下一次 Stop 再 Start 会 `FAILED`，`last_error` 以 `SEGMENT_NOT_ON_WORKER` 开头，可文件已经在这台机器上。现在 Start 留着刚拿到的主人和 epoch。打开的文件是 `mysql-bin.NNNNNN.open.eN`，租约继续续，任务进入 `RUNNING`。旧二进制已经留在裸名文件上的任务，目录行仍是 `OPEN`、文件又在这台 worker 上时，再启动会从那个文件续上。跟踪为 #177（PR #219）、#220（PR #221）。QA 在 `05b49642` 上 dogfood 通过。

## 核心变化

- `GET /api/tasks/{id}/events` 在调度锁里确认任务还在，然后放开锁再读事件库。一个任务的事件读得慢，不会挡住另一个任务的 Stop、Start、租约续约和进度更新。
- 事件写入先在锁里改内存，再写事件库。同一个任务的事件顺序不变。任务 A 的一次慢写入不会挡住任务 B 的这些操作。事件库写失败不让这次状态转换失败。
- 进度更新只在这把锁里改内存。以前它会卡住，是因为它和事件读取、事件写入共用这把锁。
- 打开下一个 binlog、封存，以及按天数清理，每次读 `binlog_files` 200 行，按 `(file_name, epoch)` 排序。不再把该任务的每一行都读进来。本地窗口和桶窗口、`LOCAL_ONLY`、`UPLOAD_FAILED`、checksum 的 `match` 和 `mismatch` 都不变。
- `GET /api/tasks/{id}/files` 和回放仍会读该任务的整份目录，再在进程里取窗口，顺序和以前一样。文件列表的响应不变。租约接管在每次启动时仍会读每一行，因为它要看读不了的尾段，以及已经盖住 checkpoint 的已上传对象。
- 接管一个 `UPLOADED` 分段时，对象先流式写到任务目录里的 `.takeover-*`。复制的字节数和打开对象时报告的大小一致之后，才改名为 `mysql-bin.NNNNNN.open.eN`。读短了或下载失败会删掉这个临时文件，不会留下一段续传会当成有效的截断文件。目录里的 checksum 仍是 `match` 或 `mismatch`。这次复制不计算对象的哈希，也不改这个标记。
- 一体进程和集群上（配了 `meta_dsn`），Stop 和 Start 期间轮询 `GET /api/tasks/{id}`，不再让新的一轮按 epoch 0 启动。这一版之前，Start 过程中的一次刷新可能把上一轮 `STOPPED` 的行写回内存。
- Start 留着刚拿到的主人和 epoch。打开的文件是 `mysql-bin.NNNNNN.open.eN`。租约继续续。任务进入 `RUNNING`。
- 旧二进制已经留在裸名文件上的任务，目录行仍是 `OPEN`、文件又在这台 worker 上时，用 `POST /api/tasks/{id}/start` 再启动。裸名文件改名为 `mysql-bin.NNNNNN.open.eN`。文件真的不在这台机器上时，仍会失败，`last_error` 以 `SEGMENT_NOT_ON_WORKER` 开头，并写出要挂载或拷贝的路径。
- 一体进程和集群上，这一轮没有留住租约 epoch 时，任务进入 `FAILED`。`last_error` 以 `EPOCH_NOT_ACQUIRED:` 开头（正文是 `this start did not keep its lease epoch. Start the task again`）。租约放开。这一轮不拉流。再 Start 一次。没有元数据库的 standalone 仍然没有租约 epoch。

## 升级影响

二进制从 v0.5.39 滚动升级即可。这一版没有 schema migration。#219 和 #221 都没有加迁移。元数据 schema 仍是 v0.5.34 引入的版本 2。`migrations/` 仍是 `000001` 和 `000002`。`schema_migrations` 已经是版本 2 时，不用执行 `./migrate up`。

还在 schema 1 上的库，要先迁移，这个二进制才会启动。按 [v0.5.34 升级说明](v0.5.34.zh-CN.md)：停掉这个元数据库上的每一台 binlog-server，执行 `./migrate up`，然后只启动 v0.5.34 或更新的二进制。

没有新的配置项。

旧二进制已经留在裸名 `mysql-bin.NNNNNN` 上、目录行仍是 `OPEN`、文件又在这台 worker 上的任务，用 `POST /api/tasks/{id}/start` 再启动。文件改名为 `mysql-bin.NNNNNN.open.eN`，从该文件最后一个完整事件继续。文件真的缺失时，仍会 `SEGMENT_NOT_ON_WORKER`，并写出要挂载或拷贝的路径。已经 `FAILED`、`last_error` 以 `EPOCH_NOT_ACQUIRED:` 开头的那一轮没有拉流。再 Start 一次。

## 已知行为

QA 在 `05b49642` 上 dogfood 通过：上面的卡住、epoch 0 竞态，以及 v0.5.39 的回归 #204、#214、#213（standalone，以及一体进程上的短中断）。下面这些仍开着。#222、#223、#203、#189、#193、#205、#209 在这一版之前就有。#224 是这一版先写临时文件再改名才有的。

- 一体进程上，`LATEST` 任务已经连上并保存了 checkpoint，但还没有写入完整事件，再加上源库大约 20 秒的中断，任务可能永久 `FAILED`。`last_error` 以 `SEGMENT_NOT_ON_WORKER` 开头。认领循环大约每 2 秒会再次启动自己名下的 `RETRY_BACKOFF` 任务，epoch 会往上走。打开的文件仍在本机，里面只有 4 字节的 magic。中断期间已经提交的事务不会进备份。任务不会自己恢复。中断很短、epoch 还是 1 时恢复，以及同样的中断发生在 standalone 上，仍从保存的文件和位点续上。v0.5.39 上同样能复现。跟踪为 #222。
- 接管一个 `UPLOADED` 分段之后，同一个源文件会再封存成 `mysql-bin.NNNNNN.sealed.eN` 并再上传一次。`GET /api/tasks/{id}/replay` 和 `GET /api/tasks/{id}/replay/archive` 把这个 source index 列两次。归档里这些事务出现两次。两个对象的字节相同。v0.5.39 上同样能复现。跟踪为 #223。
- 接管还在下载对象时 `kill -9`，任务目录里会留下 `.takeover-*`。之后一次接管成功也不会删掉它。读短了或下载失败仍会删掉临时文件。启动和按天数清理都不会清掉残留的 `.takeover-*`。单个文件可以接近正在复制的那一段。这是这一版先写临时文件再改名才有的。跟踪为 #224。
- 一体进程和集群上，认领循环大约每 2 秒会再次启动自己名下的 `RETRY_BACKOFF` 任务，并把失败计数清掉，所以任务到不了 `FAILED`。没有元数据库的 standalone 仍会在连续十次失败后进入 `FAILED`。`last_error` 以 `SOURCE_UNREACHABLE:` 开头。拉流已经打开时源库宕机，也计入同一份预算。认领循环仍会把计数清掉。跟踪为 #203。
- 故障切换之后，后一次封存的分段，例如 `mysql-bin.NNNNNN.sealed.e1`，`end_pos` 可能是 0。`size_bytes` 是文件大小。这一行仍可以是 `UPLOADED`，checksum 为 `match`。文件列表里仍有这一段，下载和回放仍能返回它。这是 v0.5.34、v0.5.35、v0.5.36、v0.5.37、v0.5.38 和 v0.5.39 已经记下的行为。跟踪为 #189。
- 停止过程中改了源库密码，然后再 Start，源库上可能短暂出现两条 Binlog Dump。之后再一次停到 `STOPPED`，仍可能留下一条 Binlog Dump，需要在源库上手动 `KILL`。控制面上一次普通停止，以及一体进程上的停止，源库进程列表里不再有该任务的 Binlog Dump。这是 v0.5.35、v0.5.36、v0.5.37、v0.5.38 和 v0.5.39 已经记下的行为。跟踪为 #193。
- GTID 模式启动，以及文件位点续传在 MySQL 1236 之后打开 `StartSyncGTID`，会写入一条没有 CRC 的人工 Rotate。`mysqlbinlog --verify-binlog-checksum` 在这条事件上报 `Event crc check failed!`。不加这个参数时文件可以读完。已经复制的事件本身是完整的。GTID 启动还会留下一个多余的 `task-N.binlog`。目录把它记成 `SEALED` 并上传。跟踪为 #205。
- 没有配置上传时，按天数清理会删掉本地封存文件，目录行仍是 `SEALED` / `LOCAL_ONLY`，`file_path` 还是旧路径。`GET /api/tasks/{id}/files` 仍列出这个名字，响应里没有 `location`。`GET /api/tasks/{id}/files/{name}` 返回 404。文件列表和磁盘对不上。这是在 `4477d19e` 的 dogfood 上看到的。这一版的保留代码仍会删掉那个本地文件并留下目录行。跟踪为 #209。
