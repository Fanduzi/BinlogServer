# Binlog Server v0.5.30 中文发布说明

> 对应版本：`v0.5.30`

发布日期：2026-10-05

`v0.5.30` 上，从源 binlog 中部开始的备份会把 MySQL 最先下发的 format description 写一次，放在第一个被复制的事件前面。`LATEST` 从源上当前文件的中部开始。起点落在文件内部的 `FILE_POS` 也一样。到 `v0.5.29` 为止，这条 description 会被丢掉。`mysqlbinlog` 会拒绝这第一段，报 `does not contain any Format_description_log_event`，这一段里的行事件无法解析。已发布的 v0.5.29 包仍然丢掉这条 description。

## 核心变化

- 从文件中部开始时，源库会先下发 format description。它的 `end_log_pos` 是 0，或者是文件头原来的位置（MySQL 8 上是 126），小于当时的 dump 位点。`v0.5.30` 保留源库下发的原文，只写一次，放在 4 字节 magic header 之后、第一个被复制的事件之前。`mysqlbinlog --verify-binlog-checksum` 能读这个文件。
- checkpoint 停在被复制的事件上。description 自己的结束位置（MySQL 8 上是 126，或者 0）不是 checkpoint，它的时间戳也不算延迟。
- 源库还没有后续事件时，分段仍只有这 4 个字节的 magic header。停止后再启动不会退回位置 126。
- 已经有事件的分段，下次 start 不会再写第二条 description。
- 没有新的配置项。不需要 schema migration。

## 升级影响

- `v0.5.30` 不需要 schema migration。迁移仍只有 `000001_init_schema`。
- 没有新的配置项。`cluster.failover_policy` 仍然不是开关。`PRODUCTION=true` 仍要求非空 `--encryption-key`。30 秒阈值没有变化。
- 在 `v0.5.29` 或更早版本上，由 `LATEST` 或文件内部的 `FILE_POS` 写出的分段，仍然没有 format description。这个版本不会回填，也不会修复。下次 start 看到分段里已经有事件，就不会插入 description。
- 怎么看：对那第一段跑 `mysqlbinlog`。它会报 `does not contain any Format_description_log_event`。
- 真实 rotate 之后、从位置 4 打开的后续文件不受影响。在那个文件里，format description 的结束位置在 4 之后（MySQL 8 上是 126），大于当时的位点，所以 `v0.5.29` 和更早版本会把它和文件里的其它事件一起复制。丢掉 description 只发生在它的结束位置落后于 dump 位点时，也就是从文件中部开始的那第一段。这段被 rotate 封存时只是改名，字节不变，封存名上 `mysqlbinlog` 仍会报缺少 `Format_description_log_event`。
