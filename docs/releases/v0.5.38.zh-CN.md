# Binlog Server v0.5.38 中文发布说明

> 对应版本：`v0.5.38`

发布日期：2026-10-05

任务处于 `RUNNING`、`STARTING`、`LEASE_DEGRADED` 或 `RETRY_BACKOFF` 时，`PUT /api/tasks/{id}` 要改源库、起点、保留或 `cluster_key`，返回 HTTP 400。正文是纯文本 `stop the task before changing source, start, storage, or cluster_key: state <STATE>`。`<STATE>` 是该任务的当前状态。已经保存的行不动，所以 `GET /api/tasks/{id}` 仍是这次拉流正在用的源库、起点、保留和 `cluster_key`。这一版之前，接口把新值写进去了，正在跑的 dump 仍用启动时抄下的那份，GET 和实际生效的配置对不上。只改名字的 PUT 仍然成功。要改源库、起点、保留或 `cluster_key`：先 Stop，再 PUT，再 Start。任务从 checkpoint 续上，并用新的配置。跟踪为 #179（PR #208）。在从源码编出的 MySQL 8.0.46 上、提交 `4477d19e` 核对过。

## 核心变化

- 会拒绝这次修改的状态是 `RUNNING`、`STARTING`、`LEASE_DEGRADED`、`RETRY_BACKOFF`。`RETRY_BACKOFF` 也在里面，因为下一轮用的是本进程已经拿着的那份配置。它不读 PUT 刚写进行里的值。
- 改动指源库、起点、保留或 `cluster_key` 和当前值不一样。源库包括 host、port、user、password、flavor、`server_id`、`semi_sync`。起点包括 mode、file、position、`gtid_set`。保留包括 `dir`、`retention_days`、`local_retention_days`、`bucket_retention_days`。省略的字段保持原值。空的 `source.password` 保留原密码。把相同的源库、起点、保留和 `cluster_key` 再提交一次可以通过。
- 只改 `name` 的 PUT 在这些状态下仍返回 HTTP 200。拉流继续。
- `CREATED`、`STOPPING`、`STOPPED`、`FAILED` 仍可以 PUT 修改源库、起点、保留或 `cluster_key`。行还在 `STOPPING` 时写上的密码，是下一次 Start 用的密码。
- HTTP 400 时，已保存的密码、保留和其它被锁住的字段都不变。
- 先 Stop，等到行变成 `STOPPED`，再 PUT，再 `POST /api/tasks/{id}/start`。Start 读更新后的行，并从 checkpoint 续上。
- 任务停在 `RETRY_BACKOFF` 是因为 host 或 port 写错时，以前一次 PUT 就能改过去。现在这个 PUT 返回 HTTP 400，正文是 `stop the task before changing source, start, storage, or cluster_key: state RETRY_BACKOFF`。先 Stop，再 PUT host 或 port，再 Start。
- 监听地址、上传端点、租约 TTL、加密密钥是进程配置。它们不是这次 PUT 的字段。改这些仍要重启进程。

## 升级影响

二进制从 v0.5.37 滚动升级即可。这一版没有 schema migration。元数据 schema 仍是 v0.5.34 引入的版本 2。`schema_migrations` 已经是版本 2 时，不用执行 `./migrate up`。

还在 schema 1 上的库，要先迁移，这个二进制才会启动。按 [v0.5.34 升级说明](v0.5.34.zh-CN.md)：停掉这个元数据库上的每一台 binlog-server，执行 `./migrate up`，然后只启动 v0.5.34 或更新的二进制。

没有新的配置项。

## 已知行为

下面这些在这一版之前就有。这个构建在从源码编出的 MySQL 8.0.46 上、提交 `4477d19e` 核对过。这一版没有改它们。

- 同一进程上每个任务的 Stop、Start、租约续约和进度更新，跟事件读取、事件写入共用一把锁。一次慢的元数据写入，或 Console 在读事件，会把其它任务的这些操作挡住。打开下一个 binlog 时，在拉流路径上读该任务的整份文件目录。接管一个很大的已上传分段时，会把整个对象读进这个 worker 的内存。跟踪为 #177。
- 故障切换之后，后一次封存的分段，例如 `mysql-bin.NNNNNN.sealed.e1`，`end_pos` 可能是 0。`size_bytes` 是文件大小。这一行仍可以是 `UPLOADED`，checksum 为 `match`。文件列表里仍有这一段，下载和回放仍能返回它。这是 v0.5.34、v0.5.35、v0.5.36 和 v0.5.37 已经记下的行为。跟踪为 #189。
- 停止过程中改了源库密码，然后再 Start，源库上可能短暂出现两条 Binlog Dump。之后再一次停到 `STOPPED`，仍可能留下一条 Binlog Dump，需要在源库上手动 `KILL`。控制面上一次普通停止，以及一体进程上的停止，源库进程列表里不再有该任务的 Binlog Dump。这是 v0.5.35、v0.5.36 和 v0.5.37 已经记下的行为。跟踪为 #193。
- 一体进程和集群角色上，`SOURCE_UNREACHABLE` 的十次上限不会触发。认领循环大约每 2 秒会再次启动自己名下的 `RETRY_BACKOFF` 任务，并把连续失败计数清掉，任务一直停在 `RETRY_BACKOFF`。没有元数据库的 standalone 仍会在连续十次失败后进入 `FAILED`，`last_error` 以 `SOURCE_UNREACHABLE:` 开头。跟踪为 #203。
- 拉流已经打开时源库宕机，任务可能仍显示 `RUNNING`。租约继续续。dump 库日志是 `retry sync err, wait 1s`。调度器看不到这个错误，任务不进 `RETRY_BACKOFF`，也不累计 `SOURCE_UNREACHABLE`。源库恢复后任务继续，位点能对齐。跟踪为 #204。
- GTID 模式启动，以及文件位点续传在 MySQL 1236 之后打开 `StartSyncGTID`，会写入一条没有 CRC 的人工 Rotate。`mysqlbinlog --verify-binlog-checksum` 在这条事件上报 `Event crc check failed!`。不加这个参数时文件可以读完。已经复制的事件本身是完整的。GTID 启动还会留下一个多余的 `task-N.binlog`。目录把它记成 `SEALED` 并上传。跟踪为 #205。
- 没有配置上传时，按天数清理会删掉本地封存文件，目录行仍是 `SEALED` / `LOCAL_ONLY`，`file_path` 还是旧路径。`GET /api/tasks/{id}/files` 仍列出这个名字，响应里没有 `location`。`GET /api/tasks/{id}/files/{name}` 返回 404。文件列表和磁盘对不上。这是在 `4477d19e` 的 dogfood 上看到的。这一版的保留代码和之前一样。跟踪为 #209。
