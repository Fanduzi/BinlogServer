# Binlog Server v0.5.65 中文发布说明

> 对应版本：`v0.5.65`

发布日期：2026-10-14

v0.5.65 交付 ADR 0009 第 0 和第 1 阶段（备份可信，#326）：以前只留一行日志的失败，现在会留下持久化的 finding；备份链在一处（`internal/assurance`）按不变量 I1–I7 检查；封存段带封存事实；binlog dump 受任务租约约束；所有操作员状态转换都先落库，并有转换卡住的看门狗。两个新迁移（`000007`、`000008`）只增不改且可选：`minRequiredSchemaVersion` 仍是 6，地板仍是 v0.5.51。没有配置变化。BinlogServerQA 对 main `b5c97c9fff2ecdcbdc531c5e3a14a72332c3d249` 的 tip dogfood 通过。

**历史改写。** BinlogServer 的提交历史在 2026-10-12 改写过（见 v0.5.60 说明）。此前的提交哈希都变了。请按 tag 或 PR 号查找改动。

## 亮点

- **Finding（ADR 0009 第 0 阶段；PR #336、#337、#338、#339、#340）。**
  - finding sink：每条 finding 持久化（`task_findings`，迁移 `000007`；无元数据库时写 `{data_dir}/.findings.json`），同时留下 `FINDING_REPORTED` 任务事件和指标，条件消失后自动 resolve。
  - 类型包括 `TASK_PERSIST_FAILED`、`EVENT_PERSIST_FAILED`、`EVENT_READ_FAILED`、`DUMP_CLEANUP_PERSIST_FAILED`、`DISK_LIST_FAILED`、`RETRY_LOOP_FAILED`、`UPLOAD_RECORD_FAILED`、`UPLOAD_UNVERIFIED`、`RETENTION_RECORD_FAILED`、`OPEN_TAIL_CUT_FAILED`、`METRIC_SOURCE_FAILED`。
  - API：`GET /api/tasks/{id}/findings`（`all=1` 包含已 resolve）和 `GET /api/findings`。`/api/tasks`、`/api/tasks/{id}`、`/api/dashboard` 带 `open_findings`。Console 告警视图会列出有 `storage_alert` 或未关闭 finding 的任务。
  - 指标：`binlog_server_finding_open{task_id,kind,severity}`、`binlog_server_findings_reported_total{kind}`、`binlog_server_finding_sink_errors_total`、`binlog_server_finding_sink_pending`、`binlog_server_finding_store_active`、`binlog_server_metric_source_up{task_id,source}`、`binlog_server_upload_retry_pass_last_ts`。元数据库不可用时 `/metrics` 仍然应答，不再返回 500。
  - `internal/lintguard`：备份数据路径中新增被忽略的错误会让 `go test ./...` 失败。
- **`DUMP_STALLED`。** Binlog Dump 连接有 45s 读超时（错过 3 次心跳）。静默会打开 `DUMP_STALLED`（WARNING）、结束本次运行并在退避后重连；下一次会话收到首个事件即 resolve。所有到源库的 SQL 连接都走 `connectSource`（拨号 5s、读写 5s），源库被黑洞时 dump 循环不再卡死。半同步事件也会重置静默计时。
- **`METADATA_WRITE_BLOCKED`。** 元数据库拒绝写入（例如 `super_read_only`）时，dump 停止并退避重试，而不是写下目录不知道的 binlog。会打开 CRITICAL `METADATA_WRITE_BLOCKED` finding；任务显示 `RETRY_BACKOFF`/`STARTING`（绝不是 `RUNNING`），元数据库恢复可写后自动恢复。只认元数据存储边界的错误，源端超时不会误报。
- **备份链与不变量（ADR 0009 第 1 阶段；PR #347、#348、#349、#350、#354）。** `internal/assurance` 构建唯一的链（`ChainOf`）并检查 I1–I7。`GET /window`、存储健康判定和 `/replay` 截断都由它派生。行为用 v0.5.64 上录制的 golden 冻结。
- **`SEGMENT_UNREADABLE`（PR #361、#358）。** 事件长度损坏的封存段不再让进程分配约 4 GiB 内存，而是报为不可读：`SEGMENT_UNREADABLE` finding、`storage_alert` `STORAGE_INCONSISTENT`，window 在它之前截止。
- **封存事实（PR #351）。** 迁移 `000008_binlog_files_seal_facts` 给 `binlog_files` 增加可空的 `first_event_at`、`last_event_at`、`sha256`；每次封存单遍流式写入。可选：schema 6 或 7 上会跳过写入直到重启。
- **租约栅栏（PR #355、#346）。** dump 打开前，Start 会校验并续租（owner + epoch CAS），清理残留 dump 的时间计入租约。租约已过期的 worker 不能打开 dump，丢失租约后的停止也不会覆盖新 owner 的行。每个任务最多一个 dump。
- **先落库的状态转换与 `TASK_TRANSITION_STALLED`（PR #364）。** Create、Start、Stop、Delete、Update、Adopt 和所有 Configure* 都先写库；写成功后才改内存、事件和 dump。被拒绝的操作返回错误、记录 `*_REJECTED` 事件，任务、行和 dump 都不变（被拒的 Start 保留 RETRY_BACKOFF 循环；被拒的 Delete 让 dump 继续运行）。任务处于 STARTING 或 STOPPING 超过 60s 会报 `TASK_TRANSITION_STALLED`，收敛后关闭。

## 修复

- **MariaDB 11.4+ 行事件现在会被保存（PR #362、#359，P1）。** 之前版本对 MariaDB 11.x 只保存了 GTID 和 XID 事件，恢复出来是空的且不报错。10.11 不受影响。**如果你备份的是 MariaDB 11.4 或更新版本，升级后请重新做全量备份，并把该源在 v0.5.64 及更早版本下的 binlog 备份视为不能用于行回放。**
- **无元数据库模式下 adopt 从最后一个完整事件的末尾续传（PR #357、#356，P1）。** 之前 `kill -9` 后 adopt 按文件大小续传，对续写段和截断尾部是错的。
- Stop 先记录意图再取消 dump（被拒时为 `TASK_STOP_REJECTED`），不再留下没有 dump 的 RUNNING 行。

## 升级说明

- 替换二进制并重启。没有配置变化。
- 迁移：`migrations/` 新增 `000007_task_findings` 和 `000008_binlog_files_seal_facts`，都是只增且可选。建议 `./migrate up` 到 8：schema 6 上 finding 只保存在内存和 `/metrics`（`binlog_server_finding_store_active 0`），没有 8 就不写封存事实。`minRequiredSchemaVersion` 仍是 6；v0.5.65 在 schema 5 上不启动（`schema version too old`、`./migrate up`）。地板仍是 v0.5.51。v0.6.0 会把地板提到 7。
- 建议告警 `binlog_server_finding_open{severity="CRITICAL"} > 0`，特别是 `METADATA_WRITE_BLOCKED`、`TASK_TRANSITION_STALLED`、`SEGMENT_UNREADABLE`。
- 元数据库只读时，Start、Stop、Delete 现在返回 400 且不做任何改变。元数据库恢复可写后重试。
- MariaDB 11.4+：见上面的修复，升级后重新全量备份。
- v0.5.64 的 `/ui-classic/` 规则和 v0.5.63 到 v0.5.58 的规则仍然有效。从 v0.5.61 或更早升级，请先读 [v0.5.62 说明](v0.5.62.zh-CN.md)：错误凭据返回 401 而不是 403。

## 已知行为

- 同一目录下同一源文件的重复段（例如 `mysql-bin.000006` 与 `mysql-bin.000006.sealed.e3`）运行时不会被检出：没有 finding，window 看起来连续，`/replay` 会同时列出两者。v0.5.64 相同；计划在 ADR 0009 第 2 阶段处理。
- #365（P3）：元数据库只读时 PUT 和 Create 返回 500 而不是 400（状态不变，已记录 `*_REJECTED`）。
- #366（P3）：集群模式下 kill -9 旧 worker 后，已 STOPPED 的任务上 `DUMP_STALLED` 可能保持 40s 以上。
- #367、#368（P3）：Console 对从未启动的任务请求 `/checkpoint`；事件时间线按写入时间排序。
- #312、#341–#345、#352、#353、#360、#363（P3）仍未关闭。
