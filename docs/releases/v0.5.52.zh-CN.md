# Binlog Server v0.5.52 中文发布说明

> 对应版本：`v0.5.52`

发布日期：2026-10-07

worker 会删掉进程崩溃时、接管正在下载 `UPLOADED` 对象留下的 `.takeover-*` 临时文件。清理在 worker 启动时、认领任务之前，扫数据目录下每一个任务目录。`materializeUploaded` 在该任务下一次下载之前、`CreateTemp` 之前，再清一次这个任务目录。本进程还在写的临时文件留下。已封存分段、打开中的分段、正在写的文件、`task-<id>.binlog`、`notes.txt`，以及其他名字都留下。直接放在数据目录里的文件留下。这次 materialize 不碰另一个任务的 `.takeover-*`。只删除名字匹配 `.takeover-*` 的普通文件。日志是 `takeover: removed stale temp <name> task=<id> size=<bytes>`。保留清理仍然跳过 `.takeover-*`。没有迁移 `000006`。schema 仍是 5。`minRequiredSchemaVersion` 仍是 5。`uk_task_file_epoch` 仍在。没有新的配置项。这一版是 ADR 0005 的第 8 步，一共 9 步。第 9 步不在这一版。BinlogServerQA 的 tip dogfood 在 `dbf9f5c62a08a2868a1b6d2545b2d7cdac7bb7ab` 上为 PASS。这次没有新的问题。v0.5.49 的封存位点规则（#189）仍成立。v0.5.48 不留下空 `task-<id>.binlog` 的规则（#205）仍成立。#224 在这一版修好（PR #273）。

## 核心变化

- worker 启动时，在认领任务之前，删除数据目录下每一个任务目录里的普通 `.takeover-*` 文件。只有控制面的进程不跑这次清理。直接放在数据目录里的文件留下，包括 `.worker-id`。删除失败时，进程在开始监听之前退出。提示含 `remove stale takeover temps`。
- `materializeUploaded` 在打开 `UPLOADED` 对象之前、`CreateTemp` 之前，删除该任务目录里的 `.takeover-*`。旁边那个任务目录不动，包括它自己的 `.takeover-*`。删除失败时，下载还没开始就返回。
- 本进程还在写的 `.takeover-*` 留下。旁边那个崩溃留下的临时文件会被删掉。进程还活着时，下载失败仍会删掉这次创建的临时文件。`kill -9` 仍然跳过这次删除。下一次 worker 启动，或该任务下一次 `materializeUploaded`，会删掉 `kill -9` 留下的文件。
- 其他名字留下：已封存分段、打开中的分段、正在写的文件、`task-<id>.binlog`、`notes.txt`，以及任何其他文件。不是普通文件的名字留下。保留清理仍然跳过 `binlog.ClassifySegment` 拒绝的每一个名字，包括 `.takeover-*`。保留清理不是这次的清理器。目录里不会为这个临时文件名增加一行。
- 日志是 `takeover: removed stale temp <name> task=<id> size=<bytes>`。`<name>` 是文件基名。`<bytes>` 是字节数。
- `file_name` 不变。schema 仍是 5。`migrations/` 仍是 `000001` 到 `000005`。没有 `000006`。`uk_task_file_epoch` 仍在。`minRequiredSchemaVersion` 仍是 5。没有新的配置项。ADR 0005 第 8 步已标为落地。第 9 步没有改。它仍是后续工作。#224 在这一版修好。

## 升级影响

没有新迁移。已经在 v0.5.51 / schema 5 上的库仍是 schema 5。确认 `SELECT version, dirty FROM schema_migrations` 是 `(5, 0)`。`migrations/` 仍是 `000001`、`000002`、`000003`、`000004` 和 `000005`。下一个新迁移仍是 `000006`。`000006` 不在这一版。

`minRequiredSchemaVersion` 仍是 5。v0.5.52 在 schema 4 上不会启动，以退出码 1 结束，还没开始监听。提示含 `schema version too old` 和 `./migrate up`。这和 v0.5.51、v0.5.50 的拒绝一样。schema 3 和 schema 2 同样拒绝启动。v0.5.49 仍能在 schema 5 上启动，因为 `uk_task_file_epoch` 还在。

schema 5 已经就位再换这一版二进制。库已经是 v0.5.51 / schema 5 时，不需要 `./migrate`。还不是 schema 5 时，先按 [v0.5.50 中文发布说明](v0.5.50.zh-CN.md)，确认 `(5, 0)`，再启动 v0.5.52。旧二进制留在任务目录里的 `.takeover-*`，会在跑这一版的 worker 启动时删掉。

schema 4（`000004_pending_dump_cleanup`）仍在迁移链上。v0.5.50 之前，schema 4 是单进程可选、集群必须。分步升级、启动的仍是比 v0.5.50 旧的二进制时，这条规则还适用。v0.5.52 自己不能停在 schema 4。

如果这套库还不是 schema 3，先按 [v0.5.46 中文发布说明](v0.5.46.zh-CN.md)，再按 v0.5.50。schema 2 到 schema 3（`000003_task_desired_and_retry_budget`）在线。schema 1 到 schema 2 仍按 [v0.5.34 升级说明](v0.5.34.zh-CN.md)：停掉每一台进程，执行 `./migrate up`，然后只启动 v0.5.34 或更新的二进制。

没有新的配置项。没有元数据库的 standalone 不跑这些迁移。standalone 自己是 worker，启动时仍会删除 `.takeover-*`。

不要 `./migrate down` 退过正在跑的二进制所需要的 schema。v0.5.52 需要 schema 5。这一版没有新迁移，所以没有新的 down。schema 5 上 `./migrate down --steps 1` 仍是 v0.5.50 的那次 down：只丢掉 `uk_task_source_epoch`，并恢复原来的空值约束。`source_file` 重新可空。`start_pos` 和 `end_pos` 重新 `NOT NULL`。回到 version 4。不删行。`start_pos` 或 `end_pos` 已经是 NULL 时，这次 down 会失败。不要把这个 NULL 填成 0。v0.5.51 在不知道结束位点时把该列写成 NULL。不写成 0。v0.5.52 还在跑时不要做这次 down。v0.5.52 在 schema 4 上不会启动。

v0.5.51 的未知 `end_pos` 规则仍成立。本进程读不到本地字节时，`GET /api/tasks/{id}/files` 的未知 `end_pos` 是 JSON `null`，Console 单元格是空白。本地文件能读到事件时，给出事件跨度。保留清理仍然只删除 `binlog.ClassifySegment` 认作已封存分段的名字。

v0.5.49 的封存位点规则（#189）和 v0.5.48 的空 `task-<id>.binlog` 规则（#205）仍成立。BinlogServerQA 的 tip dogfood 在 `dbf9f5c6` 上为 PASS。这次没有新的问题。

这一版是 ADR 0005 的第 8 步，一共 9 步。第 9 步仍是后续工作。
