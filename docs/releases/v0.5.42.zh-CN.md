# Binlog Server v0.5.42 中文发布说明

> 对应版本：`v0.5.42`

发布日期：2026-10-06

没有配置上传时，按天数清理会删掉本地封存文件，目录行仍是 `SEALED` / `LOCAL_ONLY`，`file_path` 还是旧路径。`GET /api/tasks/{id}/files`、Console 文件表、`GET /api/tasks/{id}/replay` 和 `GET /api/tasks/{id}/replay/archive` 仍列出这个名字。按列表做恢复时，`GET /api/tasks/{id}/files/{name}` 会在恢复中途返回 404。这是在 `4477d19e` 的 dogfood 上看到的。现在这次清理会删掉本任务目录里没有远端副本、本地文件已经不在的封存行。`GET /api/tasks/{id}/events` 记一条点名该文件的 `RETENTION_REMOVED`，日志里也写同一条删除。旧二进制留下的、文件已经不在的目录行，下一次清理会删掉，包括 Start。`UPLOADED` 行留下。本地文件已经不在时 `location` 是 `bucket`，下载仍从对象读。跟踪为 #209（PR #231）。

## 核心变化

- 没有配置上传时，按天数清理仍会删掉超过本地保留窗口的封存文件。当前打开的文件和其他打开分段都留下。同一轮里，本任务目录中没有远端副本的那条封存目录行会被删掉。`GET /api/tasks/{id}/files` 和 Console 文件表不再列出这个名字。`GET /api/tasks/{id}/replay` 和 `GET /api/tasks/{id}/replay/archive` 不再包含它。
- `GET /api/tasks/{id}/events` 每删掉一行记一条 `RETENTION_REMOVED`。消息是 `<name> removed by local retention`。日志行是 `retention: removed <name> task=<id> upload_state=<state>`。第二轮不会再写这条事件，因为目录行已经不在。
- 旧二进制留下的目录行，仍是 `SEALED` / `LOCAL_ONLY`，`file_path` 已经不在磁盘上，会在下一次清理时删掉。这次清理由本进程打开 binlog 时执行，包括 Start。不用手工删行。
- `file_path` 不在本任务目录的行留下。打开中的行留下。还在保留窗口里的封存文件留下。没有元数据库的 standalone 仍按天数删掉本地封存文件。那里没有目录行可删。
- 带 object key 的 `UPLOADED` 行不会删。配了对象存储时，超过本地窗口、仍在桶窗口里的封存文件只删本地文件。目录行留下，`location` 是 `bucket`。`GET /api/tasks/{id}/files/{name}`、回放和归档仍返回这个对象。这一行不写 `RETENTION_REMOVED`。

## 升级影响

从 v0.5.41 直接替换二进制即可。这一版没有 schema migration。#231 没有加迁移。元数据 schema 仍是 v0.5.34 引入的版本 2。`migrations/` 仍是 `000001` 和 `000002`。`schema_migrations` 已经是版本 2 时，不用执行 `./migrate up`。

还在 schema 1 上的库，要先迁移，这个二进制才会启动。按 [v0.5.34 升级说明](v0.5.34.zh-CN.md)：停掉这个元数据库上的每一台 binlog-server，执行 `./migrate up`，然后只启动 v0.5.34 或更新的二进制。

没有新的配置项。

没有配置上传时，旧二进制已经删掉、目录里仍列着的封存文件，不用手工删行。下一次清理，包括 Start，会删掉那一行。`UPLOADED` 行留下。本地副本已经不在的文件仍可从桶里下载。

## 已知行为

下面这些仍开着。#203、#205、#224、#189、#193 在这一版之前就有。#209 在这一版修好了。#203 每次重试仍会把 epoch 往上抬。

- 一体进程和集群上，认领循环大约每 2 秒会再次启动自己名下的 `RETRY_BACKOFF` 任务，并把失败计数清掉，所以任务到不了 `FAILED`。这些重试里租约 epoch 会一直往上走。没有元数据库的 standalone 仍会在连续十次失败后进入 `FAILED`。`last_error` 以 `SOURCE_UNREACHABLE:` 开头。拉流已经打开时源库宕机，也计入同一份预算。认领循环仍会把计数清掉。这一版不改这条路径。跟踪为 #203。
- GTID 模式启动，以及文件位点续传在 MySQL 1236 之后打开 `StartSyncGTID`，会写入一条没有 CRC 的人工 Rotate。`mysqlbinlog --verify-binlog-checksum` 在这条事件上报 `Event crc check failed!`。不加这个参数时文件可以读完。已经复制的事件本身是完整的。GTID 启动还会留下一个多余的 `task-N.binlog`。目录把它记成 `SEALED` 并上传。跟踪为 #205。
- 接管还在下载对象时 `kill -9`，任务目录里会留下 `.takeover-*`。之后一次接管成功也不会删掉它。读短了或下载失败仍会删掉临时文件。启动和按天数清理都不会清掉残留的 `.takeover-*`。单个文件可以接近正在复制的那一段。跟踪为 #224。
- 故障切换之后，后一次封存的分段，例如 `mysql-bin.NNNNNN.sealed.e1`，`end_pos` 可能是 0。`size_bytes` 是文件大小。这一行仍可以是 `UPLOADED`，checksum 为 `match`。文件列表里仍有这一段，下载和回放仍能返回它。这是 v0.5.34、v0.5.35、v0.5.36、v0.5.37、v0.5.38、v0.5.39、v0.5.40 和 v0.5.41 已经记下的行为。跟踪为 #189。
- 停止过程中改了源库密码，然后再 Start，源库上可能短暂出现两条 Binlog Dump。之后再一次停到 `STOPPED`，仍可能留下一条 Binlog Dump，需要在源库上手动 `KILL`。控制面上一次普通停止，以及一体进程上的停止，源库进程列表里不再有该任务的 Binlog Dump。这是 v0.5.35、v0.5.36、v0.5.37、v0.5.38、v0.5.39、v0.5.40 和 v0.5.41 已经记下的行为。跟踪为 #193。
