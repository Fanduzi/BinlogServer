# Binlog Server v0.5.27 中文发布说明

> 对应版本：`v0.5.27`

发布日期：2026-10-05

`v0.5.27` 在 `v0.5.26` 上，可以对已有备份任务要一段盖住某个 UTC 停止时间的 binlog 窗口。已发布的 v0.5.26 包仍是按 `limit` 的回放：`flavor`、`client`、`client_hint`、`paths`，没有 `command` 字段。先自己恢复全量备份，再执行打印出来的命令。Binlog Server 不恢复那份备份。

## 核心变化

- `GET /api/tasks/{id}/replay` 接受 `stop_datetime`（UTC）和可选的 `start_datetime`。同一个查询打在 `GET /api/tasks/{id}/replay/archive` 上下载这组分段。窗口是半开区间 `[start, stop)`。`stop_datetime` 不包含在内。设置了 `start_datetime` 时，这个时刻包含在内。时间是 UTC。`YYYY-MM-DD HH:MM:SS` 和 `YYYY-MM-DDTHH:MM:SS` 按 UTC 理解。带时区的 RFC3339 先换算成 UTC。每个源序号仍是一条路径，封存名和 open 的取舍与按 `limit` 的回放相同。这条路径不使用 `limit`。路径是事件头时间盖住这个窗口的分段。
- 只有带了 `stop_datetime` 时，响应才包含 `command`。`flavor`、`client`、`client_hint`、`paths` 仍在。`source.flavor` 为 `mysql` 时用 `mysqlbinlog`，`mariadb` 时用 `mariadb-binlog`。命令以 `TZ=UTC` 开头，这样这两个客户端用事件头时间戳比较这些参数。命令里有 `--stop-datetime`；设置了开始时间时还有 `--start-datetime`。命令写的是服务器上的路径。tar 成员是同一选择的 basename，顺序一致，文件名是 `task-{id}-replay.tar`。
- 两个时间都不传时，仍是按 `limit` 的回放：`flavor`、`client`、`client_hint`、`paths`，没有 `command` 字段。这时归档也仍是那个 `limit` 窗口。
- `start_datetime` 与 `stop_datetime` 相等是空窗口：HTTP 200，`paths` 为空，`command` 为空。这不是 400。没有盖住任何分段的窗口也是这个结果。时间无法解析，或开始时间晚于停止时间，是纯文本 400（`invalid stop_datetime`、`invalid start_datetime` 或 `start_datetime is after stop_datetime`）。只给了 `start_datetime` 是纯文本 400 `stop_datetime is required`。任务不存在是 404 `task not found`。空窗口的归档是 HTTP 200，空的 tar。某个已选分段在本进程打不开是 404 `segment not found on this process`，响应不是半个 tar。
- Console 任务详情有同一个窗口：UTC 停止时间、可选的开始时间、生成、复制，以及下载 `task-{id}-replay.tar`。这个 Console 在普通 `go build` 提供的嵌入包里。

## 升级影响

- `v0.5.27` 不需要 schema migration。迁移仍只有 `000001_init_schema`。
- 没有新的配置项。`cluster.failover_policy` 仍然不是开关。`PRODUCTION=true` 仍要求非空 `--encryption-key`。30 秒阈值没有变化。
- 先自己恢复全量备份，再使用打印出来的命令。按 `limit` 的回放、后台补传、保留和租约接管保持 `v0.5.26` 的行为。
