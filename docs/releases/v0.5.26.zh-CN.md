# Binlog Server v0.5.26 中文发布说明

> 对应版本：`v0.5.26`

发布日期：2026-10-04

`v0.5.26` 在 `v0.5.25` 上，本进程是 worker 且配置了对象存储时，在后台重试已封存的 `UPLOAD_FAILED` 分段。已发布的 v0.5.25 包把这些行留在 `UPLOAD_FAILED`，直到调用 `POST /api/tasks/{id}/files/retry-upload`。

## 核心变化

- 配置了对象存储的 worker 在后台重试已封存的 `UPLOAD_FAILED` 分段。单机和 all-in-one 都是 worker，所以会跑这个循环。集群里的 worker 也会跑。只跑控制面的进程不跑。没有配置对象存储的进程不跑这个循环。
- 这个循环走和现有手动补传同一条路径。成功的行变成 `UPLOADED`，并写入 checksum，和手动补传一样。
- open 分段保持不上传。封存文件不在这台机器上时跳过，目录行保持原样。
- 上传失败仍然不停止 binlog 拉取，也不改变任务状态。
- `POST /api/tasks/{id}/files/retry-upload` 和 `RetryFailedUploads(taskID string, limit int)` 保持不变。某个任务的后台这一轮还在跑时，对该任务的手动补传仍返回已有的进行中错误 `upload retry already in progress`。
- 默认节奏是每 15 秒一次，每个任务每一轮最多 100 条已封存的 `UPLOAD_FAILED`。

## 升级影响

- `v0.5.26` 不需要 schema migration。迁移仍只有 `000001_init_schema`。
- 没有新的配置项。`cluster.failover_policy` 仍然不是开关。`PRODUCTION=true` 仍要求非空 `--encryption-key`。30 秒阈值没有变化。
- 保留、租约接管，以及 v0.5.25 从对象读回的行为不变。
