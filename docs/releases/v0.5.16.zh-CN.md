# Binlog Server v0.5.16 中文发布说明

> 对应版本：`v0.5.16`

发布日期：2026-10-04

`v0.5.16` 是 `v0.5.15` 的运维补丁。备份还在 `RUNNING` 时杀掉进程，认领这份磁盘备份但不启动，再启动它，会从 open 分段里最后一个完整事件接着拉。已发布的 v0.5.15 压缩包在 `kill -9` 之后仍会新开一个 epoch，`mysqlbinlog` 读不了这个新文件。

## 核心变化

- 备份处于 `RUNNING` 时杀掉进程。这不是 API 停止。磁盘上的备份这时没有任务元数据。先认领、不启动，再启动。dump 从该 open 分段最后一个完整事件的结束位点续传。不会跳到当前 `SHOW MASTER STATUS`。也不会从位置 4 重来。
- 这个 open 分段的最后一个完整事件已经结束在续传位点上时，分段会改名到新 epoch，再往后面追加，所以同一个源文件名跨过这次崩溃。文件开头仍是 format description，进程死之前写下的事件还在。进程挂掉期间源库提交的事件写进这个文件，每条一次。边界上没有空洞，也没有重复事件。
- `v0.5.15` 对干净停止已经这样做。已发布的 v0.5.15 压缩包在 `kill -9` 之后做不到：认领再启动会新开一个 epoch，文件开头是 magic，后面是位点之后的事件。format description 和崩溃前的事件留在旧分段里，`mysqlbinlog` 无法重放这个新文件。
- 认领之前直接启动这份备份，仍会因为没有任务元数据被拒绝。干净停止再恢复没有变化。`delay_seconds` 为 `0`、没有样本就省略字段、dump 文件头不算延迟、真实延迟的 30 秒阈值，都与 `v0.5.15` 相同。

## 升级影响

- `v0.5.16` 不需要 schema migration。迁移仍只有 `000001_init_schema`。
- 没有新的 API，没有新的配置键。`PRODUCTION=true` 仍要求非空 `--encryption-key`。30 秒阈值没有变化。
