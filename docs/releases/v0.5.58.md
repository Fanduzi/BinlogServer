# Binlog Server v0.5.58

Release date: 2026-10-09

v0.5.58 fixes silent GTID loss after a dump reconnect (PR #293). The bug is present in v0.5.57. A GTID task whose dump connection dropped (a proxy or idle-timeout disconnect, a network blip, or a `KILL` of the dump thread) could go `RUNNING` with lag 0 while new transactions were dropped as "already written", and the checkpoint `gtid_set` and `/window` could still look continuous. Resume now starts from what is really on disk. The two P1 regressions QA found on the unreleased fix (a false `STREAM_REGRESSION` after a reconnect, restart, or upgrade, and false failures on GTID holes or out-of-order GTIDs) are fixed by resume reconciliation in PR #294. A damaged directory is reported through `storage_alert`, which names the damaged segment, the missing GTIDs, the segments that still restore, and the GTID set to start a new task from. The Console and `GET /metrics` show a VIP source switch (PR #292). The build moves to Go 1.26.9 and `golang.org/x/net` v0.60.0 for published vulnerabilities. No new config key. No schema migration. Schema stays 6. `minRequiredSchemaVersion` stays 6. The floor stays v0.5.51. Tip dogfood by BinlogServerQA passed on the PR #294 code (b6454f46 plus the P2 deltas in 9777c823), including a 34-minute soak of 78,520 transactions under dump kills, `FLUSH`, proxy drops, and idle disconnects with 0 `FAILED`, 0 `STREAM_REGRESSION`, 0 `storage_alert`, byte-identical segments, and replays equal to the source checksum.

## Highlights

- **No silent GTID loss after a reconnect (PR #293).** go-mysql in raw mode does not advance its GTID set, so its built-in reconnect re-dumped from the start set of that `StartSyncGTID`, not from what was stored. The Rotate at the end of the previous file was appended to the current segment and the resume position jumped to the length of the previous file. The task first failed with `SEALED_FILE_EXISTS`; after another Start it showed `RUNNING` with lag 0 while new transactions were dropped. go-mysql's auto-reconnect is now off. After a disconnect this process starts the dump again from the stored GTID set (or, in file/pos mode, the stored file and position). A transaction is skipped only when its GTID is already in the stored set, and a GTID that is not on disk is never written into the checkpoint.
- **Resume reconciliation (PR #294).** Before every Start of a GTID task computes its resume position, it reads the highest `.open.eN` segment. The GTIDs of complete transactions in it (XID, XA `PREPARE`, `TRANSACTION_PAYLOAD`, DDL, `COMMIT` / `ROLLBACK` / `XA COMMIT` queries, MariaDB standalone GTIDs) and the segment's `Previous_GTIDs` are added to the checkpoint's set. An unfinished trailing transaction is cut where the last complete one ended and fetched again whole, only when the cut is exact; otherwise its GTID is carried as in progress and recorded on commit. Adopted directories (`KeepLocalSegments`), damaged directories, and non-GTID tasks are never cut. The server log has one `open tail reconciled ... changed=<true|false> checkpoint_gtid=... resume_gtid=...` line per resume and an `open tail cut unfinished transaction` line when a tail was cut. A dropped dump ends the run, and the scheduler retries it as a full Start, so every such reconnect runs this reconciliation. Only a `SOURCE_UNREACHABLE` error inside a run reopens the dump in process (`dump reconnect` in the log); that reopen resumes by the flushed file and position and keeps the executed GTID set as the MySQL 1236 fallback.
- **`STREAM_REGRESSION` is a real regression only.** It is a permanent error when the stream rotates to the open file or an older one, or a transaction event is behind the stored position. A GTID hole, out-of-order GTIDs (a replica with parallel workers and `replica_preserve_commit_order=OFF`, or a manual `GTID_NEXT`), and several interleaved UUIDs never fail a task. A file header the source re-sends behind the cursor is ignored.
- **`storage_alert` says what is damaged and what still restores.** A directory with a hard trace of damage (a Rotate inside a segment that points to itself or an earlier file, or an `end_log_pos` that goes backward inside a segment) shows `storage_alert` on the task list, the dashboard, and `GET /api/tasks/{id}`, and Start refuses it with `STORAGE_INCONSISTENT`. New optional fields: `segment` (first damaged segment), `detail`, `missing_gtids` (MySQL GTIDs the checkpoint lists that the start set and every segment lack), `valid_segments` (segments before the damage), and `restart_gtid_set` (start a new GTID task from this set to continue right after those segments). A `FAILED` task whose `last_error` holds an older build's `STORAGE_INCONSISTENT` text shows the current message. The Console shows the alert line by line in Chinese or English.
- **Replay and window stop before damage.** `GET /api/tasks/{id}/replay`, `stop_datetime`, `stop_gtid`, `start_gtid_set`, and `/replay/archive` leave out the damaged segment, every other copy of that binlog index, and every later segment, and add `warning`. `GET /api/tasks/{id}/window` and the Console recoverable window use the same cutoff: they cover only the segments before the damage, are not `continuous`, and add one break naming the damaged segment and every later segment left out.
- **`GET /api/tasks/{id}/checkpoint`** shows `gtid_set` including the complete transactions already in the open segment, which is the set Start resumes from. When Start would cut an unfinished trailing transaction, `pos` is that cut. The GET never changes the file. `updated_at` is omitted until a checkpoint row exists instead of `0001-01-01T00:00:00Z`.
- **VIP source switch in the Console and on a metric (PR #292).** `GET /api/tasks/{id}` adds optional `source_chain` (each server identity, the current one, and each switch with `old`, `new`, `file`, `pos`, `gtid_set`, `continued`, and a stop `reason` of `no_gtid`, `missing_transactions`, `purged`, `mariadb`, or `gtid_unreadable`). `GET /api/tasks/{id}/files` adds computed `source_identity`. `GET /metrics` adds gauge `binlog_server_source_switchovers{task_id,outcome}` with `outcome` `continued` or `stopped`. The Console shows the chain and, for a stopped switch, the reason and next step. Switch, window, replay, and stop behavior from v0.5.57 is unchanged.
- **Security.** Go 1.26.9 (GO-2026-6599, 6600, 6605, 6607, 6608, 6609, 6613 in `net/http`, `crypto/tls`, `mime/multipart`, `html/template`) and `golang.org/x/net` v0.60.0 (GO-2026-6603, 6610, 6611, 6612, 6617). Building from source requires Go 1.26.9+.
- **Tests.** `smoke-gtid-redump` is in the quick profile. On MySQL 8.0 it runs GTID and `LATEST` tasks through 10 dump kills, a kill storm during 3000-row transactions, a `kill -9` server restart mid-load with writes while it is down, a rotation, an out-of-order `GTID_NEXT` hole, and a second UUID. Both tasks must stay `RUNNING` and replay to the source checksum.

## Upgrade Notes

After you upgrade from v0.5.57, check every GTID task for `storage_alert` (task list, dashboard, or `GET /api/tasks/{id}`). A task damaged this way under v0.5.57 shows it, because the stray Rotate stays in the segment. Do not Start that task again and do not restore past its `valid_segments`. Create a new GTID task from `restart_gtid_set` before the source purges the missing transactions, and keep the original directory for comparison. QA restored the source checksum this way. The steps are in `docs/guide/admin/troubleshooting.md`. A task without `storage_alert` needs no action.

A task that went `FAILED` with `STREAM_REGRESSION: gtid ... is ahead of stored set ...` on an unreleased main build after PR #293 (for example 0a84917a) is not damaged. `POST /api/tasks/{id}/start` (or Start in the Console) and it continues. v0.5.57 has no `STREAM_REGRESSION` code, so a direct upgrade from v0.5.57 never needs this step.

No new migration. A database already on schema 6 stays on schema 6. Confirm `SELECT version, dirty FROM schema_migrations` is `(6, 0)`. `migrations/` is still `000001` through `000006`. There is no `000007`. `minRequiredSchemaVersion` remains 6: v0.5.58 does not start on schema 5 and exits with code 1 before it listens, with `schema version too old` and `./migrate up` in the message. If the database is not on schema 6 yet, follow the [v0.5.56 upgrade](release-notes-v0.5.56.md) first. The floor stays v0.5.51. No new config key. Standalone with no metadata database follows the same rules for the segments in its data directory.

This release is not an ADR 0005 step. ADR 0005 is unchanged.

## Known behavior

- Only an error classified as `SOURCE_UNREACHABLE` inside a run reopens the dump in process; QA did not exercise that path. Every other dropped dump is retried as a full Start, which runs resume reconciliation.
- `GET /api/tasks/{id}/checkpoint` for a task that was never started still answers 404 `checkpoint not found`; Start begins at the task's start position.
- `stop_datetime` still cuts on the event-header second. Use `stop_gtid` when the bad GTID is known. The v0.5.57 source switchover rules, the v0.5.56 recoverable window, the v0.5.55 `start_gtid_set` rule, and the v0.5.54 `stop_gtid` rule still hold, except that a damaged segment now ends the window and the replay as described above.
