# Binlog Server v0.5.32 中文发布说明

> 对应版本：`v0.5.32`

发布日期：2026-10-05

`v0.5.32` 上，封存的 binlog 只有在桶里的对象和本地文件一致时，才是一份可依赖的已上传副本。对象和本地字节对不上，或者比对没有做完，记为 `UPLOAD_FAILED`。配了对象存储并且有目录时，保留清理因此留下本地文件和目录行。到 `v0.5.31` 为止，同样的行仍可能是 `UPLOADED`，保留清理可以删掉这份本地拷贝。已发布的 v0.5.31 包仍然这样。复制继续跑。没有新的状态。没有新的配置项。不需要 schema migration。

## 核心变化

- 已封存文件上传后，桶里的对象和本地字节不一致时，状态是 `UPLOAD_FAILED`。`upload_error` 是 `checksum mismatch`。`checksum` 仍是 `mismatch`。空值不是 `match`，也不是 `mismatch`。
- 比对没有做完时，状态是 `UPLOAD_FAILED`，`checksum` 是空的。这是对象 HEAD 出错。`upload_error` 以 `checksum verify failed:` 开头。
- 配了对象存储并且有目录时，保留清理不删这份本地文件，也不删目录行。`GET /api/tasks/{id}/events` 里有一条 `RETENTION_SKIPPED_NOT_UPLOADED`。复制继续跑。
- 后台补传和 `POST /api/tasks/{id}/files/retry-upload` 会把 checksum 为 `mismatch` 的文件再上传一次。没做完的比对会再比对一次，这次不会再上传。后面这次比对一致时，这一行变成 `UPLOADED`，`checksum` 为 `match`，再下一次保留清理才可以删它。后面这次比对发现字节不同时，`checksum` 变成 `mismatch`，再下一次补传会上传这个文件。
- 只有 `UPLOADED` 且 `checksum` 为 `match` 时，保留清理才会删本地文件。`checksum` 已是 `match` 的清理和以前一样：仍会删对象、目录行和本地文件，包括桶保留更长、只删本地文件的那条路径。本地文件已经不在时，按时间点恢复、下载和回放仍读这份已封存的 `UPLOADED` 对象。`LOCAL_ONLY` 的保留没有变化。本地文件已经不在、只留在桶里的 `UPLOADED` 行，仍按原来的年龄清理。
- 已经记成 `UPLOADED`、`checksum` 是 `mismatch` 或空、本地文件还在磁盘上的行会留下。下一次保留清理把它记成 `UPLOAD_FAILED`，同一条补传就可以再上传 `mismatch`，或再比对一次没做完的检查。
- checksum 在上传之后比对一次。已经比对为 `match` 的对象，如果之后在桶里被换掉，不会再比对。保留清理仍把 `checksum` 为 `match` 的行当成可以删除本地文件的那一份。
- 没有新的上传状态。没有新的配置项。不需要 schema migration。Console 本来就会显示 `upload_state` 和 `checksum`。已有的重试按钮在 `UPLOAD_FAILED` 上出现。

## 升级影响

- `v0.5.32` 不需要 schema migration。迁移仍只有 `000001_init_schema`。
- 没有新的状态。没有新的配置项。`cluster.failover_policy` 仍然不是开关。`PRODUCTION=true` 仍要求非空 `--encryption-key`。30 秒阈值没有变化。
- 在 `v0.5.31` 及更早版本上，对象和本地字节不一致、或 checksum 从未核对过的封存文件，保留清理可能已经删掉本地拷贝。看 `GET /api/tasks/{id}/files`，找出 `UPLOADED` 且 `checksum` 为 `mismatch` 或空的行。本地文件还在磁盘上时，`v0.5.32` 的下一次保留清理会留下它，并把这一行记成 `UPLOAD_FAILED`。本地文件已经不在时，这个版本不会把它找回来。那个对象仍按原来的年龄清理；这一行还是 `UPLOADED` 时，按时间点恢复、下载和回放仍读它。
- checksum 在上传之后比对一次。对象在比对一致之后又在桶里被改过，不会重新核对。
