# Binlog Server v0.5.29

Release date: 2026-10-05

On Binlog Server `v0.5.29`, local disk and the bucket can keep a sealed binlog for different numbers of days, on top of `v0.5.28`. The published v0.5.28 package has no split and still uses one cutoff.

## Highlights

- `storage.retention_days` stays required. The range is still 1..3650. Two optional keys are `storage.local_retention_days` and `storage.bucket_retention_days`. Omitted or 0 means the same as `retention_days`. Those zero keys are omitted from the task JSON. When the effective local days and the effective bucket days are equal, that shared number is the one cutoff. A task that sets only `retention_days` is this case, and so is a task that sets the two new keys to the same effective number. An expired uploaded segment that is still on disk is removed from the object, the catalog row, and the local file together, as in v0.5.28. On that one-cutoff path, a catalog row whose local file is already gone stays. That path does not use `sealed_at` or `uploaded_at`.
- Create and update compare the effective days. `POST /api/tasks` and `PUT /api/tasks/{id}` reject a bucket window shorter than the local window. The message contains `shorter than local retention` and names both numbers. Create returns JSON with `code` `INVALID_REQUEST` and that sentence in `error`. Update returns the sentence as plain text. Both are HTTP 400. Equal windows are accepted. A non-zero `local_retention_days` or `bucket_retention_days` outside 1..3650 is HTTP 400. An omitted key uses `retention_days` for that window. `local_retention_days` above `retention_days`, with `bucket_retention_days` omitted, is rejected. `local_retention_days` below `retention_days`, with `bucket_retention_days` omitted, leaves the bucket window at `retention_days`. That bucket window is longer, so the longer-bucket purge below applies when object storage and a catalog are configured. Omitting `local_retention_days` and setting `bucket_retention_days` above `retention_days` does the same: the local window stays at `retention_days`, and the bucket window is longer.
- The longer bucket window is applied only when object storage and a catalog (`meta_dsn`) are both configured. A sealed `UPLOADED` segment with an object key, older than the local window and still inside the bucket window, loses only the local file. The object and the catalog row stay. `file_path` stays the catalog path. While the file is still on disk, both windows use the local file modification time. Retention still runs when the replication loop opens a binlog file. The active open segment stays. Every other open segment stays, and retention does not delete an object for one.
- `GET /api/tasks/{id}/files` reports `location` as `local`, `bucket`, or `both`. `both` means the local file and the uploaded object are both present. `local` means the file is on this process and there is no uploaded object. `bucket` means a sealed `UPLOADED` object with an object key, and the file is not on this process. `GET /api/tasks/{id}/files/{name}` streams that object's bytes when the local file is absent and this process has object storage configured. `{name}` is the basename. The response does not open `file_path`. `GET /api/tasks/{id}/replay` does this for the limit window and for `stop_datetime`. `GET /api/tasks/{id}/replay/archive` does this for the same selections. Replay `locations` is the same order as `paths`. A `bucket` value means that path is the catalog `file_path` and is not on this process. Download the segment or the replay archive, then use those bytes. Do not pass that path to `mysqlbinlog` until the file is downloaded. The `stop_datetime` command still prints the catalog path. A process with no object storage configured still returns 404 `segment not found on this process` for a file that is not on disk.
- While a sealed file is still on disk, both windows use its modification time. If that time is older than the bucket window, the object, the catalog row, and the local file are removed together. After the local file is gone, and only when the bucket window is longer than the local window, bucket age is `sealed_at`. When `sealed_at` is empty, age is `uploaded_at`. When both are empty, the object and the catalog row stay. Once that timestamp is older than the bucket window, the object and the catalog row are removed. An object delete that fails leaves the local file, leaves `checksum` as it was (`match`, `mismatch`, or empty), and sets `last_error` beginning `OBJECT_PURGE_FAILED`. The next file open tries the delete again. Removing only the local file, while the segment is still inside the bucket window, does not delete the object or the catalog row.
- With object storage and a catalog, a sealed `UPLOAD_FAILED` or `LOCAL_ONLY` segment older than the local window stays on disk with its catalog row. Age is the local file modification time, compared with the local window. Replication keeps running. It does not set `last_error` and does not enter `RETRY_BACKOFF`. `GET /api/tasks/{id}/events` gets one `RETENTION_SKIPPED_NOT_UPLOADED` per kept file. The message names the file and its `upload_state`, for example `mysql-bin.000003 upload_state=LOCAL_ONLY`. Opening another binlog does not append that event again for the same file while this process stays up. After a restart, the next retention pass that still keeps the file appends that event once more. The process that runs retention exposes `binlog_server_retention_blocked_files{task_id}` on `GET /metrics`: how many of those expired files the latest successful pass is still keeping. The gauge drops when a later pass deletes them. After a restart it stays 0 until the next retention pass. A control-plane-only process does not run retention, so the gauge stays 0 there. The event remains on `GET /api/tasks/{id}/events`. A sealed `UPLOAD_FAILED` row is still picked up by the background upload retry and by `POST /api/tasks/{id}/files/retry-upload`. Either path can make that row `UPLOADED`. After it is `UPLOADED`, the next retention pass uses the windows above.
- `LOCAL_ONLY` is not picked up by the background upload retry. The manual retry selects only sealed `UPLOAD_FAILED` rows, so it does not upload a `LOCAL_ONLY` row. Configuring object storage later does not upload that row. Without upload configured, local retention still deletes the sealed file by the local window. A catalog row, when one exists, stays. No `RETENTION_SKIPPED_NOT_UPLOADED` event is written, and the gauge stays 0.
- Standalone without `meta_dsn` still deletes the local sealed file by the local age, including one that never reached the bucket. A longer `bucket_retention_days` is not applied without a catalog. Upload still deletes the object together with the local file at the local window. Do not use that mode as the only copy when the bucket can be down longer than the local retention.
- Console task detail shows the effective local days and the effective bucket days. Each omitted key is shown there as `retention_days`. The file table shows `location`. The API value is `local`, `bucket`, or `both`. The English Console shows those words. The Chinese Console shows 本地, 桶, or 本地和桶. A segment whose location is `bucket` shows the hint that the path is not on this machine: download the segment or the replay set, and do not pass that path to `mysqlbinlog` until the file is downloaded. That Console is in the embedded bundle a plain `go build` serves.

## Upgrade Notes

- No schema migration is required for `v0.5.29`. Migrations are still `000001_init_schema` only. The new keys are stored in the existing task storage JSON.
- `storage.retention_days` is unchanged. `cluster.failover_policy` is still not a switch. `PRODUCTION=true` still requires a non-empty `--encryption-key`. The 30-second threshold is unchanged.
- A task that already sets only `retention_days` keeps the v0.5.28 purge. The split starts when the effective bucket window is longer than the effective local window, and this process has object storage and `meta_dsn`.
