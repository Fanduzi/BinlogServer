# Binlog Server v0.5.58 中文发布说明

> 对应版本：`v0.5.58`

发布日期：2026-10-09

v0.5.58 修复 dump 重连后静默丢失 GTID 事务的问题（PR #293），v0.5.57 有这个问题。GTID 任务的 dump 连接断开后（代理或空闲超时断开、网络闪断、`KILL` dump 线程），任务可能显示 `RUNNING`、延迟 0，新事务却被当成“已经写过”丢掉，checkpoint 的 `gtid_set` 和 `/window` 仍可能显示连续。现在续传从真正落盘的内容开始。QA 在未发布的修复上发现的两个 P1（重连、重启或升级后误报 `STREAM_REGRESSION`，以及 GTID 空洞或乱序时误判失败）由 PR #294 的续传对账修好。损坏的目录通过 `storage_alert` 报告：写明损坏的分段、缺失的 GTID、仍可恢复的分段，以及新建任务应从哪个 GTID 集合开始。Console 和 `GET /metrics` 能看到 VIP 换源（PR #292）。构建升级到 Go 1.26.9 和 `golang.org/x/net` v0.60.0，修复已公布的漏洞。没有新配置项。没有 schema 迁移。schema 仍是 6。`minRequiredSchemaVersion` 仍是 6。地板仍是 v0.5.51。BinlogServerQA 对 PR #294 的代码（b6454f46 加 9777c823 里的 P2 改动）做的 tip dogfood 通过，其中 34 分钟、78,520 个事务的浸泡测试在 dump KILL、`FLUSH`、代理断开和空闲断开下，`FAILED`、`STREAM_REGRESSION`、`storage_alert` 都是 0，分段与源逐字节一致，回放校验和与源一致。

## 核心变化

- **重连后不再静默丢事务（PR #293）。** go-mysql 在 RawMode 下不推进 GTID 集合，库内自动重连从这次 `StartSyncGTID` 的起点集合重拉，而不是已经落盘的集合。上一个文件末尾的 Rotate 被追加进当前分段，续传位点跳到上一个文件的长度。任务先以 `SEALED_FILE_EXISTS` 失败；再 Start 一次后显示 `RUNNING`、延迟 0，新事务却被丢掉。现在关掉 go-mysql 的自动重连，断线后由本进程从已落盘的 GTID 集合（file/pos 模式下是已落盘的文件和位点）重新拉流。只有 GTID 已在落盘集合里才跳过该事务，没落盘的 GTID 不会写进 checkpoint。
- **续传对账（PR #294）。** GTID 任务每次 Start 计算续传位置之前，先读编号最大的 `.open.eN` 分段。分段里完整事务的 GTID（XID、XA `PREPARE`、`TRANSACTION_PAYLOAD`、DDL、`COMMIT` / `ROLLBACK` / `XA COMMIT` 语句、MariaDB 独立 GTID）和分段的 `Previous_GTIDs` 并入 checkpoint 的集合。末尾没写完的事务只在切点精确时，才从上一个完整事务结束处截掉、整笔重拉；否则它的 GTID 记为进行中，提交时再记录。接管的目录（`KeepLocalSegments`）、损坏的目录和非 GTID 任务不会被截断。服务日志每次续传有一行 `open tail reconciled ... changed=<true|false> checkpoint_gtid=... resume_gtid=...`，截断时还有一行 `open tail cut unfinished transaction`。dump 断开时本次运行结束，调度器重试并完整 Start 一次，所以每次这样的重连都会做对账。只有运行中被归为 `SOURCE_UNREACHABLE` 的错误会在进程内重开 dump（日志里是 `dump reconnect`），这种重开按已刷盘的文件和位点续传，并保留已执行 GTID 集合作为 MySQL 1236 的后备。
- **`STREAM_REGRESSION` 只表示真正的倒退。** 拉流 Rotate 到当前打开的文件或更早的文件，或事务事件的位点落在已存位点之后，才是永久错误。GTID 空洞、乱序 GTID（并行回放且 `replica_preserve_commit_order=OFF` 的副本，或手工 `GTID_NEXT`）、多个 UUID 交错，都不会让任务失败。源在游标之前重发的文件头事件会被忽略。
- **`storage_alert` 写明坏在哪里、什么还能恢复。** 目录里有损坏的硬痕迹（某个分段里的 Rotate 指向自己或更早的文件，或 `end_log_pos` 在一个分段里变小）时，任务列表、dashboard 和 `GET /api/tasks/{id}` 显示 `storage_alert`，Start 以 `STORAGE_INCONSISTENT` 拒绝。新增可选字段：`segment`（第一个损坏的分段）、`detail`、`missing_gtids`（checkpoint 里有、起点集合和所有分段都没有的 MySQL GTID）、`valid_segments`（损坏之前的分段）、`restart_gtid_set`（从这个集合新建 GTID 任务，紧接着这些分段继续）。`last_error` 还是旧构建 `STORAGE_INCONSISTENT` 文本的 `FAILED` 任务，显示当前的提示。Console 用中文或英文逐行显示这条告警。
- **回放和窗口停在损坏之前。** `GET /api/tasks/{id}/replay`、`stop_datetime`、`stop_gtid`、`start_gtid_set` 和 `/replay/archive` 不包含损坏的分段、该 binlog 序号的其他副本以及之后的所有分段，并返回 `warning`。`GET /api/tasks/{id}/window` 和 Console 的可恢复窗口用同样的截止点：只覆盖损坏之前的分段，`continuous` 为否，并有一个缺口写明损坏的分段和被排除的后续分段。
- **`GET /api/tasks/{id}/checkpoint`** 显示的 `gtid_set` 包含打开分段里已有的完整事务，也就是 Start 续传用的集合。Start 会截掉末尾未完成事务时，`pos` 就是那个切点。GET 从不修改文件。checkpoint 行存在之前不返回 `updated_at`，不再是 `0001-01-01T00:00:00Z`。
- **Console 和指标里的 VIP 换源（PR #292）。** `GET /api/tasks/{id}` 增加可选 `source_chain`（每个服务器身份、当前身份，以及每次切换的 `old`、`new`、`file`、`pos`、`gtid_set`、`continued` 和停止原因 `reason`：`no_gtid`、`missing_transactions`、`purged`、`mariadb`、`gtid_unreadable`）。`GET /api/tasks/{id}/files` 增加计算出的 `source_identity`。`GET /metrics` 增加 gauge `binlog_server_source_switchovers{task_id,outcome}`，`outcome` 是 `continued` 或 `stopped`。Console 显示这条链；停止的切换会写明原因和下一步。v0.5.57 的切换、窗口、回放和停止行为不变。
- **安全。** Go 1.26.9（`net/http`、`crypto/tls`、`mime/multipart`、`html/template` 的 GO-2026-6599、6600、6605、6607、6608、6609、6613）和 `golang.org/x/net` v0.60.0（GO-2026-6603、6610、6611、6612、6617）。从源码构建需要 Go 1.26.9+。
- **测试。** `smoke-gtid-redump` 在 quick 档。它在 MySQL 8.0 上同时跑 GTID 和 `LATEST` 任务，经历 10 次 dump KILL、3000 行大事务期间的 KILL 风暴、写入中途 `kill -9` 重启服务器且宕机期间继续写、一次轮转、一个乱序 `GTID_NEXT` 空洞和第二个 UUID。两个任务都必须保持 `RUNNING`，回放结果与源的校验和一致。

## 升级影响

从 v0.5.57 升级后，检查每个 GTID 任务有没有 `storage_alert`（任务列表、dashboard 或 `GET /api/tasks/{id}`）。在 v0.5.57 上这样损坏的任务会显示它，因为那条多出来的 Rotate 留在分段里。不要再 Start 这个任务，恢复时不要越过它的 `valid_segments`。在源清掉缺失事务之前，从 `restart_gtid_set` 新建 GTID 任务，并保留原目录供核对。QA 用这个办法恢复出了与源一致的校验和。步骤见 `docs/guide/admin/troubleshooting.md`。没有 `storage_alert` 的任务不需要处理。

在 PR #293 之后的未发布 main 构建（例如 0a84917a）上以 `STREAM_REGRESSION: gtid ... is ahead of stored set ...` 进入 `FAILED` 的任务没有损坏，`POST /api/tasks/{id}/start`（或在 Console 里 Start）即可继续。v0.5.57 没有 `STREAM_REGRESSION` 这个错误码，从 v0.5.57 直接升级不需要这一步。

没有新迁移。已经在 schema 6 的数据库保持 schema 6。确认 `SELECT version, dirty FROM schema_migrations` 是 `(6, 0)`。`migrations/` 仍是 `000001` 到 `000006`，没有 `000007`。`minRequiredSchemaVersion` 仍是 6：v0.5.58 在 schema 5 上不启动，监听之前以退出码 1 退出，信息里有 `schema version too old` 和 `./migrate up`。数据库还不是 schema 6 时，先按 [v0.5.56 升级](release-notes-v0.5.56.md) 操作。地板仍是 v0.5.51。没有新配置项。不连元数据库的单机模式对自己数据目录里的分段遵循同样的规则。

这一版不是 ADR 0005 的步骤。ADR 0005 没有改。

## 已知行为

- 只有运行中被归为 `SOURCE_UNREACHABLE` 的错误会在进程内重开 dump；QA 没有覆盖这条路径。其他 dump 断开都按完整 Start 重试，会做续传对账。
- 从未启动过的任务，`GET /api/tasks/{id}/checkpoint` 仍返回 404 `checkpoint not found`；Start 从任务的起始位置开始。
- `stop_datetime` 仍按事件头的秒截断。知道出问题的 GTID 时用 `stop_gtid`。v0.5.57 的换源规则、v0.5.56 的可恢复窗口、v0.5.55 的 `start_gtid_set` 规则和 v0.5.54 的 `stop_gtid` 规则仍然成立，只是损坏的分段现在会像上面说的那样结束窗口和回放。
