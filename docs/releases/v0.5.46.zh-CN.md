# Binlog Server v0.5.46 中文发布说明

> 对应版本：`v0.5.46`

发布日期：2026-10-06

有元数据库时，dump 由 `desired_run` 和 `spec_revision` 驱动。`STOPPED` 只在 dump 连接 `Close()` 返回之后写入。一条任务最多一条 Binlog Dump。`KILL` 用任务当前密码。`minRequiredSchemaVersion` 仍是 3。迁移 `000004_pending_dump_cleanup` 只加一列，在线。单进程可以不跑。集群必须跑。这是 ADR 0005 的第 4 步，一共 9 步。没有新的配置项。

## 核心变化

- `backup_tasks.desired_run` 是 `RUN` 或 `STOP`。`spec_revision` 是操作修订号。Start 写 `RUN` 并加一。Stop 写 `STOP` 并加一。改源、起点、保留或 `cluster_key` 也加一。Worker 的控制回路是唯一负责拉起和停止的地方。它拉起 dump、停掉 dump、规格变化后关掉再开一条，期望和已经打开的 dump 一致时不动这一行。只有所有权真正变化才 `Acquire`。同一个 worker 续租不增加 epoch。
- `STOPPED` 只在 `Close()` 返回之后写入，`owner_worker_id` 这时清空。源库可达的 Stop 在源上不留这条任务的 Binlog Dump。没有元数据库的 standalone 同样等 `Close()` 返回再写 `STOPPED`。
- `KILL` 用任务当前密码（#193）。Stop 期间改源密码再 Start，源上留下一条 Binlog Dump。再 Stop 一次，变成零条。
- 元数据 schema 低于 3 时，拒绝原因写进配置的日志文件，然后进程退出。提示含 `schema version too old` 和 `./migrate up`（#245）。
- 源库不可达时 Stop 仍写成 `STOPPED`（#249）。`GET /api/tasks/{id}` 带 `pending_dump_cleanup`（`connection_id`、`host`、`port`、`warning`）。警告是 `source Binlog Dump connection <id> may still be open; will KILL when source is reachable`。Console 任务详情显示这条警告。`STOPPED` 之后警告还在。标记写下时记一条 `DUMP_CLEANUP_PENDING`，清掉时记一条 `DUMP_CLEANUP_CLEARED`。源库可达后，worker 用当前密码自动 `KILL`，先等 5 秒，失败则加倍，最长 30 秒，直到线程消失或任务被删。MySQL 返回 `ER_NO_SUCH_THREAD`，或 processlist 里这条已经不是 Binlog Dump，都算清掉。不等这次 `KILL` 才写 `STOPPED`。重试还在写自己打开时的那份快照时，不会盖掉更新的操作员 Stop。
- schema 3 上，这个标记留在拉过这条 dump 的进程里，runner 拆掉之后还在（#252）。`GET /api/tasks/{id}` 的 `process_local` 为 true。别的进程看不到。重启就没了。跑完 `000004` 之后，同一份标记写在 `backup_tasks` 上，重启还在。
- 对端收到 FIN 或 RST 时，大约一个 `master_heartbeat_period`（15 秒）拆掉 dump。实测 FIN 大约 26–29 秒。半开路径（包被丢掉，没有 FIN/RST）上，心跳很小，写进发送缓冲区就返回，`net_write_timeout` 不会拆掉这条线程。源库要等多久取决于那台主机自己的 TCP 重传。Linux `tcp_retries2` 默认约 15 分钟（实测半开大约 957 秒）。路径一直不通时，本进程缩短不了这段等待。警告和 `KILL` 重试会留到确认线程消失。DBA 可以在源上按 `connection_id` 手动 `KILL`（#253）。
- 一条任务最多一条 Binlog Dump（#255）。Start 先 `KILL` 旧连接，processlist 或 `ER_NO_SUCH_THREAD` 确认旧连接已经不在，才开新的 dump。确认不了就停在 `RETRY_BACKOFF`，留下警告，不开 dump。拉着 dump 的 worker 在 `Close()` 返回前一直续租，租约丢了就停掉自己的 dump。没拉过这条 dump 的进程不会把它写成 `STOPPED`。连接还开着时，schema 4 把连接号记成 `held`，API 不把它显示成警告。

## 升级影响

启动 v0.5.46 之前，先停掉连着这套元数据库的全部 v0.5.44 和 v0.5.45 worker。不要和这两个版本混跑。那两个版本不维护 `desired_run`。混跑会让任务被一边拉起、另一边停掉。

`minRequiredSchemaVersion` 仍是 3。v0.5.46 在 schema 2 上不会启动，以退出码 1 结束，还没开始监听。提示含 `schema version too old` 和 `./migrate up`，写进配置的日志文件（#245）。

如果这套库还不是 schema 3，schema 2 到 schema 3（`000003_task_desired_and_retry_budget`）在线。旧进程保持运行时执行 `./migrate up`。这次迁移不需要重启。确认 `SELECT version, dirty FROM schema_migrations` 是 `(3, 0)`。schema 1 到 schema 2 仍按 [v0.5.34 升级说明](v0.5.34.zh-CN.md)：停掉每一台进程，执行 `./migrate up`，然后只启动 v0.5.34 或更新的二进制。

迁移 `000004_pending_dump_cleanup` 只给 `backup_tasks` 加一列 `pending_dump_cleanup VARCHAR(512) NOT NULL DEFAULT ''`。在线。单进程可以不跑，标记留在内存里（`process_local` 为 true）。集群必须跑。集群还在 schema 3 时，日志写 `cluster mode needs migration 000004 (pending_dump_cleanup) before another worker can finish a dump it did not close; run ./migrate up`，不会接管别的 worker 的 dump。`./migrate up` 之后 `schema_migrations` 是 `(4, 0)`。已经在跑的进程，迁移之后要重启，才会读这一列。`migrations/` 是 `000001`、`000002`、`000003` 和 `000004`。

启动时，认领循环也会再跑一次，只改 `spec_revision=0` 且 `applied_spec_revision=0` 的行。`RUNNING`、`STARTING`、`RETRY_BACKOFF`、`LEASE_DEGRADED`、`REBUILDING_FILE` 的 `desired_run` 写成 `RUN`，其余写成 `STOP`。修订号保持 0。已经对齐的行再跑一次不会被改。本版本 Start、Stop 或改规格之后 `spec_revision>0`，不会被这次对齐盖掉。旧二进制留下的、状态仍是 `RUNNING` 但 `desired_run=STOP` 的任务在升级后继续跑。

v0.5.46 还在跑时不要 `./migrate down` 回到 schema 2。schema 4 上 `./migrate down --steps 1` 只丢掉 `pending_dump_cleanup`，回到 version 3。集群 worker 还依赖这一列时不要做这次 down。单进程可以留在 schema 3。

没有新的配置项。没有元数据库的 standalone 不跑这些迁移。

## 已知行为

下面这些仍开着。#189、#205、#224 在这一版之前就有。#193 在这一版修好。

- 故障切换后，同名封存段的 `end_pos` 写成 0。跟踪为 #189。
- GTID 启动或 1236 回退后写入无 CRC 的人工 Rotate，校验失败，并产生多余的 `task-N.binlog`。跟踪为 #205。
- 接管下载 `UPLOADED` 对象时进程崩溃，`.takeover-*` 临时文件会一直留在磁盘上。重启、重试成功后都不清理。跟踪为 #224。
