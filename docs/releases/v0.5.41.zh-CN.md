# Binlog Server v0.5.41 中文发布说明

> 对应版本：`v0.5.41`

发布日期：2026-10-06

接管一个已经 `UPLOADED` 的分段之后，转到下一个源文件时，以前会把同一份源文件再封存成 `mysql-bin.NNNNNN.sealed.eN` 并再上传一次。`GET /api/tasks/{id}/replay` 和 `GET /api/tasks/{id}/replay/archive` 把这个 source index 列两次。目标库没有开 GTID，或者客户端带了 `--skip-gtids` 时，恢复会把这些事务执行两遍。现在这次轮转会丢掉接管出来的那份副本。回放和归档每个源序号只留一条路径，目录里已经有这条重复行的旧数据也一样。`GET /api/tasks/{id}/files` 仍会列出这条重复行。一体进程上，`LATEST` 任务的打开文件里只有 4 字节 magic，源库中断久到认领循环把 epoch 抬上去之后，以前会永久 `FAILED`，`last_error` 以 `SEGMENT_NOT_ON_WORKER` 开头。文件就在本机。中断期间提交的事务拉不回来。现在任务回到 `RUNNING`。这些事务按顺序各复制一次，本地文件里的 GTID 序列保持连续。standalone，以及 epoch 还是 1 时就恢复的重试，本来就会这样。跟踪为 #223（PR #226）、#222（PR #228）。

## 核心变化

- 接管一个 `UPLOADED` 分段时，仍把对象读回来，打开为 `mysql-bin.NNNNNN.open.eN`。转到下一个源文件时，如果同一源文件上另一条已经校验过的 `UPLOADED` 行盖住了续传位点，而且本地文件没有写出更靠后的完整事件，就不再封存、不再上传。这次接管打开的目录行和本地副本会被删掉。已经上传那一行的 checksum 仍是 `match` 或 `mismatch`。
- `GET /api/tasks/{id}/replay` 和 `GET /api/tasks/{id}/replay/archive` 每个源序号只返回一条路径。`start_pos` 和 `end_pos` 是同一个大于 0 的位点、并且同一源序号上另一条封存行已经盖住这个点的那一行，不会进回放。旧版本已经写下这条重复行的目录也一样，不用手工删行。`end_pos` 为 0 的行仍留下。还在接收新事件的 binlog 仍会封存并上传一次。
- `GET /api/tasks/{id}/files` 仍列出每一条目录行，包括旧版本留下的那条重复封存行。文件列表的响应不变。
- 一体进程和集群上（配了 `meta_dsn`），`LATEST` 任务已经连上并保存了 checkpoint，但打开的文件只有 4 字节 magic，或者只有 `end_log_pos` 为 0、并且停在事件边界上的文件头，源库中断之后不再永久 `FAILED`。以前 `last_error` 以 `SEGMENT_NOT_ON_WORKER` 开头。认领循环仍大约每 2 秒再次启动自己名下的 `RETRY_BACKOFF` 任务，epoch 仍会往上走（#203）。epoch 大于 1 之后，Start 沿用已保存的文件和位点。`gtid_set` 仍为空。打开的文件改名为当前 epoch 的 `mysql-bin.NNNNNN.open.eN`。任务回到 `RUNNING`。
- 中断期间提交的事务按顺序各复制一次。本地文件里的 GTID 序列保持连续。中断很短、epoch 还是 1 时就恢复，以及同样的中断发生在 standalone 上，本来就从这条锚点续上。这条路径不变。
- 文件真的不在本机、源文件名对不上、或者尾部是撕掉的字节，仍会失败，`last_error` 以 `SEGMENT_NOT_ON_WORKER` 开头，并写出路径。

## 升级影响

二进制从 v0.5.40 滚动升级即可。这一版没有 schema migration。#226 和 #228 都没有加迁移。元数据 schema 仍是 v0.5.34 引入的版本 2。`migrations/` 仍是 `000001` 和 `000002`。`schema_migrations` 已经是版本 2 时，不用执行 `./migrate up`。

还在 schema 1 上的库，要先迁移，这个二进制才会启动。按 [v0.5.34 升级说明](v0.5.34.zh-CN.md)：停掉这个元数据库上的每一台 binlog-server，执行 `./migrate up`，然后只启动 v0.5.34 或更新的二进制。

没有新的配置项。

旧二进制接管之后，目录里已经把同一个源文件列了两行的，不用手工删行。回放和归档只留一条路径。文件列表仍显示两行。已经 `FAILED`、`last_error` 以 `SEGMENT_NOT_ON_WORKER` 开头、原因是打开文件里只有 magic 的任务，用 `POST /api/tasks/{id}/start` 再启动。Start 从已保存的文件和位点继续，并把中断期间提交的事务拉回来。

## 已知行为

下面这些仍开着。#203、#205、#209、#224、#189、#193 在这一版之前就有。#222 和 #223 在这一版修好了。#203 每次重试仍会把 epoch 往上抬。

- 一体进程和集群上，认领循环大约每 2 秒会再次启动自己名下的 `RETRY_BACKOFF` 任务，并把失败计数清掉，所以任务到不了 `FAILED`。这些重试里租约 epoch 会一直往上走。没有元数据库的 standalone 仍会在连续十次失败后进入 `FAILED`。`last_error` 以 `SOURCE_UNREACHABLE:` 开头。拉流已经打开时源库宕机，也计入同一份预算。认领循环仍会把计数清掉。这一版不改这条路径。跟踪为 #203。
- GTID 模式启动，以及文件位点续传在 MySQL 1236 之后打开 `StartSyncGTID`，会写入一条没有 CRC 的人工 Rotate。`mysqlbinlog --verify-binlog-checksum` 在这条事件上报 `Event crc check failed!`。不加这个参数时文件可以读完。已经复制的事件本身是完整的。GTID 启动还会留下一个多余的 `task-N.binlog`。目录把它记成 `SEALED` 并上传。跟踪为 #205。
- 没有配置上传时，按天数清理会删掉本地封存文件，目录行仍是 `SEALED` / `LOCAL_ONLY`，`file_path` 还是旧路径。`GET /api/tasks/{id}/files` 仍列出这个名字，响应里没有 `location`。`GET /api/tasks/{id}/files/{name}` 返回 404。文件列表和磁盘对不上。这是在 `4477d19e` 的 dogfood 上看到的。这一版的保留代码仍会删掉那个本地文件并留下目录行。跟踪为 #209。
- 接管还在下载对象时 `kill -9`，任务目录里会留下 `.takeover-*`。之后一次接管成功也不会删掉它。读短了或下载失败仍会删掉临时文件。启动和按天数清理都不会清掉残留的 `.takeover-*`。单个文件可以接近正在复制的那一段。跟踪为 #224。
- 故障切换之后，后一次封存的分段，例如 `mysql-bin.NNNNNN.sealed.e1`，`end_pos` 可能是 0。`size_bytes` 是文件大小。这一行仍可以是 `UPLOADED`，checksum 为 `match`。文件列表里仍有这一段，下载和回放仍能返回它。这是 v0.5.34、v0.5.35、v0.5.36、v0.5.37、v0.5.38、v0.5.39 和 v0.5.40 已经记下的行为。跟踪为 #189。
- 停止过程中改了源库密码，然后再 Start，源库上可能短暂出现两条 Binlog Dump。之后再一次停到 `STOPPED`，仍可能留下一条 Binlog Dump，需要在源库上手动 `KILL`。控制面上一次普通停止，以及一体进程上的停止，源库进程列表里不再有该任务的 Binlog Dump。这是 v0.5.35、v0.5.36、v0.5.37、v0.5.38、v0.5.39 和 v0.5.40 已经记下的行为。跟踪为 #193。
