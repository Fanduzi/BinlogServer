# Binlog Server v0.5.54 中文发布说明

> 对应版本：`v0.5.54`

发布日期：2026-10-07

定点恢复可以按 GTID 停在某一条 MySQL 事务之前。`GET /api/tasks/{id}/replay` 和 `GET /api/tasks/{id}/replay/archive` 接受 `stop_gtid=<server_uuid>:<seq>`。响应列出的分段收到包含这条 `GTID_EVENT` 的那一段为止。`command` 是 `TZ=UTC mysqlbinlog`，`--stop-position` 指到该事件在最后一个文件里的起始字节。这个字节之前的内容会应用。这条事务和它后面的内容不会。可选的 `start_datetime` 仍是含该时刻的下界，包括与这条 GTID 事件同一秒。`stop_datetime` 和 `stop_gtid` 不能同时出现。两个停止参数都不出现时，`limit` 不变。纯文本 400 是 `invalid stop_gtid`、`stop_gtid is not in this task's backed-up range`、`stop_gtid is not supported for this flavor`、`stop_datetime and stop_gtid cannot both be set` 和 `start_datetime is after stop_gtid`。Console 的定点恢复表单有停止 GTID 字段。参数表在 `docs/guide/reference/api.md` 第 5.8 节。Swagger 已重新生成。没有 schema 变更。schema 仍是 6。`minRequiredSchemaVersion` 仍是 6。ADR 0005 没有改。地板仍是 v0.5.51。没有新的配置项。BinlogServerQA 的 tip dogfood 在 `8646266e1b9ac99abd620a9e9df241dd51899d5f` 上为 PASS。这次没有新的问题。v0.5.49 的封存位点规则（#189）仍成立。v0.5.48 不留下空 `task-<id>.binlog` 的规则（#205）仍成立。v0.5.52 清理 `.takeover-*` 的规则仍成立（#224，PR #273）。v0.5.53 丢掉 `uk_task_file_epoch` 的规则仍成立（PR #276）。`stop_gtid` 在 PR #279 落地。

## 核心变化

- 同一秒里可以有很多事务。`stop_datetime` 按事件头的秒切开，这一秒里坏事务前面的好事务会一起被丢掉，或者坏事务也被放进去。坏事务的 GTID 已经从 `mysqlbinlog -v`、BinlogViz 或 `SHOW BINLOG EVENTS` 里知道时，传 `stop_gtid`。已发布的 v0.5.53 包没有 `stop_gtid`。
- `stop_gtid` 是一条 MySQL GTID，形状是 `<server_uuid>:<seq>`。UUID 不区分大小写。序号是正整数。不能是 0。不能有前导 0。不能是区间，也不能是 GTID 集合。两端空白会去掉。空值，以及既不是这个形状也不是 MariaDB `domain-server-seq` 的字符串，在查任务之前就是纯文本 400 `invalid stop_gtid`。
- MariaDB 的形状是 `domain-server-seq`，例如 `0-1-10`。`source.flavor` 为 `mysql` 时，这个形状是 `invalid stop_gtid`。其他 flavor 上，MySQL 形状和 MariaDB 形状都是 `stop_gtid is not supported for this flavor`。这条路径不解析 MariaDB GTID。
- 服务端按 binlog 顺序找第一个 `GTID_EVENT`，UUID 和序号都相同才算命中。previous-GTIDs 不是这条事务。UUID 或序号不是这份备份里的一条 `GTID_EVENT` 时，纯文本 400 `stop_gtid is not in this task's backed-up range`。
- `paths` 用和 `limit` 回放相同的清单：全部分封存分段，再加上每个源序号 epoch 最大的 open。然后留下收到这条 GTID 所在文件为止的分段，后面的文件不进清单。这条 GTID 在封存文件、`.open.e*`、或只存在于桶里的对象上，用的是同一条规则。本地文件优先。本地没有时，只读封存且 `UPLOADED`、`object_key` 非空的对象。`location` 为 `bucket` 的路径仍是目录里的 `file_path`。先下载，再交给 `mysqlbinlog`。
- `command` 以 `TZ=UTC mysqlbinlog` 开头。设置了 `start_datetime` 时先写 `--start-datetime='<UTC>'`。然后是 `--stop-position=<N>`。然后是这些路径。`N` 是这条 `GTID_EVENT` 在最后一个文件里的起始字节。它不是事件头里的 `end_log_pos`。中部复制进来的分段前面有一段格式描述，这两个数不一样。`mysqlbinlog` 只对命令行上的最后一个文件使用 `--stop-position`。从 `N` 开始的事件不解码。这条命令放进该 GTID 之前的每一个事务。不放进该事务。也不放进它后面的事务。
- `start_datetime` 仍是第 5.7 节那个含该时刻的下界。它等于这条 GTID 事件的时间戳时可以一起用。比这条事件的时间戳更晚是纯文本 400 `start_datetime is after stop_gtid`。更早的分段如果复制事件都在开始时间之前，不进入 `paths`。这条 GTID 所在的分段留下。
- 设置了 `stop_gtid` 或 `stop_datetime` 时，`limit` 不起作用。两个停止参数都不出现时，`limit` 窗口与 v0.5.53 相同，响应里没有 `command` 字段。只给了 `start_datetime` 仍是纯文本 400 `stop_datetime is required`。`start_datetime` 无法解析是 `invalid start_datetime`。
- `stop_datetime` 和 `stop_gtid` 同时出现，包括其中一个值为空，是纯文本 400 `stop_datetime and stop_gtid cannot both be set`。这个检查在查任务之前。
- `stop_gtid` 是 MySQL 形状或 MariaDB 形状、任务又不存在时，是 HTTP 404 `task not found`。已选分段打不开是 HTTP 404 `segment not found on this process`。
- `GET /api/tasks/{id}/replay/archive` 接受同一个 `stop_gtid` 和可选的 `start_datetime`。tar 的成员是这些 basename。停止位置留在 JSON 的 `command` 里。它不是 tar 成员。GTID 缺失、flavor 不支持、或不在备份范围内时，错误句子与 JSON 路由相同。正文不是 tar。
- Console 任务详情的定点恢复表单有停止 GTID 字段。停止时间和停止 GTID 至少填一个就可以生成命令，也可以下载 `task-{id}-replay.tar`。两个都填时，请求同时带上 `stop_datetime` 和 `stop_gtid`，页面显示 `stop_datetime and stop_gtid cannot both be set`。这个 Console 在普通 `go build` 打进去的嵌入包里。
- 没有新的配置项。没有 schema 迁移。`minRequiredSchemaVersion` 仍是 6。`migrations/` 仍是 `000001` 到 `000006`。没有 `000007`。ADR 0005 没有改。第 1 到第 9 步已经发出。第 9 步在 v0.5.53 发出。这一版不是新的 ADR 步骤。

## 升级影响

没有新迁移。已经在 v0.5.53 / schema 6 上的库仍是 schema 6。确认 `SELECT version, dirty FROM schema_migrations` 是 `(6, 0)`。`migrations/` 仍是 `000001`、`000002`、`000003`、`000004`、`000005` 和 `000006`。没有 `000007`。

`minRequiredSchemaVersion` 仍是 6。v0.5.54 在 schema 5 上不会启动，以退出码 1 结束，还没开始监听。提示含 `schema version too old` 和 `./migrate up`。这与 v0.5.53 的拒绝相同。schema 4 和 schema 3 同样拒绝启动。

schema 6 已经就位之后再换二进制。库已经是 v0.5.53 / schema 6 时，没有 `./migrate` 这一步。还不是 schema 6 时，先按 [v0.5.53 中文发布说明](v0.5.53.zh-CN.md)，确认 `(6, 0)`，再启动 v0.5.54。

地板仍是 v0.5.51，它是第一版同时带上 ADR 0005 第 6 步和第 7 步的发布。v0.5.50 只发了第 6 步。`./migrate up` 到 schema 6 之前，先停掉仍要求 `uk_task_file_epoch` 的每一台进程。v0.5.51 和 v0.5.52 就是这些二进制。schema 6 上它们拒绝启动。日志含 `missing index` 和 `uk_task_file_epoch`。比 v0.5.51 旧的进程，包括 v0.5.50，都不是地板。`000006` 之前先换掉。然后停掉 v0.5.51 和 v0.5.52。然后执行 `./migrate up`。

schema 4（`000004_pending_dump_cleanup`）仍在迁移链上。v0.5.50 之前，schema 4 是单进程可选、集群必须。分步升级、启动的仍是比 v0.5.50 旧的二进制时，这条规则还适用。v0.5.54 自己不能停在 schema 4。

如果这套库还不是 schema 3，先按 [v0.5.46 中文发布说明](v0.5.46.zh-CN.md)，再按 v0.5.50，再按 v0.5.53。schema 2 到 schema 3（`000003_task_desired_and_retry_budget`）在线。schema 1 到 schema 2 仍按 [v0.5.34 升级说明](v0.5.34.zh-CN.md)：停掉每一台进程，执行 `./migrate up`，然后只启动 v0.5.34 或更新的二进制。

没有新的配置项。没有元数据库的 standalone 不跑这些迁移。`stop_gtid` 读的是本进程打得开的分段，所以 standalone 上是同一个查询。

不要 `./migrate down` 退过正在跑的二进制所需要的 schema。v0.5.54 需要 schema 6。这一版没有新迁移，所以没有新的 down 步骤。schema 6 上 `./migrate down --steps 1` 仍是 v0.5.53 的那次 down：把 `uk_task_file_epoch` 加回来。不删行。不删 `file_name`。不删 `uk_task_source_epoch`。回到 version 5。`binlog_files` 行数不变。已经有两行共用 `(task_id, file_name, epoch)` 时，这次 down 会失败。不要为了让它通过而删行。写入方保持 `file_name` 等于 `source_file`。v0.5.54 还在跑时不要做这次 down。v0.5.54 在 schema 5 上不会启动。生产环境的 `./migrate down` 仍要 `ALLOW_DESTRUCTIVE_MIGRATE=1` 才放行。

v0.5.53 的索引规则仍成立。`SHOW INDEX FROM binlog_files` 列出 `uk_task_source_epoch`，不列出 `uk_task_file_epoch`。`file_name` 列还在。再插入相同的 `(task_id, source_file, epoch)` 会失败。重复键是 `uk_task_source_epoch`。

v0.5.52 清理 `.takeover-*` 的规则仍成立。worker 仍会删掉任务目录里留下的普通 `.takeover-*`。v0.5.51 的未知 `end_pos` 规则仍成立。本进程读不到本地字节时，`GET /api/tasks/{id}/files` 的未知 `end_pos` 是 JSON `null`，Console 单元格是空白。本地文件能读到事件时，给出事件跨度。

v0.5.49 的封存位点规则（#189）和 v0.5.48 的空 `task-<id>.binlog` 规则（#205）仍成立。`stop_datetime` 没有改。时间戳大于等于停止时间的事件仍不进入那条命令。BinlogServerQA 的 tip dogfood 在 `8646266e` 上为 PASS。这次没有新的问题。

这一版不是 ADR 0005 的步骤。第 1 到第 9 步已经发出。ADR 0005 没有改。发出第 9 步的是 v0.5.53。
