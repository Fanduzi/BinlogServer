# Binlog Server v0.5.35 中文发布说明

> 对应版本：`v0.5.35`

发布日期：2026-10-05

在控制面加 worker 的部署里，从 API 进程点停止，以前会把任务写成 `STOPPED` 并清掉主人，worker 仍握着 dump 和租约。Console 显示已停止，源库上还有一条 Binlog Dump。这一版让这次停止走到持有租约的 worker。跟踪为 #174。

## 核心变化

- 本进程没有在拉 binlog，且另一个 worker 占着租约时，Stop 写成 `STOPPING`，主人、epoch 和源库配置都留下。`POST /api/tasks/{id}/stop` 仍返回 HTTP 204。Console 显示停止中。
- Worker 认领循环大约每 2 秒一轮。行是 `STOPPING` 或 `STOPPED` 时，取消本进程还活着的 dump。dump 退出后写成 `STOPPED`，并放开租约。
- 这个 worker 上的 store 同步和 `GetTask` 也会取消这次 dump。这些读取不覆盖内存里的主人和 epoch，dump 退出时才能放开租约。
- 最终的 `STOPPED` 保留当时 store 里最新的源库配置。`STOPPING` 期间改过的源库密码，就是下次 Start 用的密码。
- 租约已经过期的 `STOPPING` 会被写成 `STOPPED`。这一轮不会拉起 dump。
- 一体和单机不变。Stop 取消本进程的 dump，dump 退出后行才是 `STOPPED`。

## 升级影响

二进制从 v0.5.34 滚动升级即可。这一版没有 schema migration。元数据 schema 仍是 v0.5.34 引入的版本 2。`schema_migrations` 已经是版本 2 时，不用执行 `./migrate up`。

还在 schema 1 上的库，要先迁移，这个二进制才会启动。按 [v0.5.34 升级说明](v0.5.34.zh-CN.md)：停掉这个元数据库上的每一台 binlog-server，执行 `./migrate up`，然后只启动 v0.5.34 或更新的二进制。

控制面加 worker 时，HTTP 204 表示停止请求已被接受。行是 `STOPPING`，主人和 epoch 还在，Console 显示停止中。源库上的 Binlog Dump 要等持有租约的 worker 取消 dump、行变成 `STOPPED` 且主人已清空之后才退出。行已经是 `STOPPED`，再把这次停止当成完成。行还是 `STOPPING` 时再 Start，返回 HTTP 400，正文 `cannot start from state STOPPING`。

没有新的配置项。

## 已知行为

- 故障切换之后，后一次封存的分段，例如 `mysql-bin.NNNNNN.sealed.e1`，`end_pos` 可能是 0。`size_bytes` 是文件大小。这一行仍可以是 `UPLOADED`，checksum 为 `match`。文件列表里仍有这一段，下载和回放仍能返回它。这是 v0.5.34 已经记下的行为。跟踪为 #189。
- 停止过程中改了源库密码，然后再 Start，源库上可能短暂出现两条 Binlog Dump。之后再一次停到 `STOPPED`，仍可能留下一条 Binlog Dump，需要在源库上手动 `KILL`。控制面上一次普通停止，以及一体进程上的停止，源库进程列表里不再有该任务的 Binlog Dump。跟踪为 #193。
