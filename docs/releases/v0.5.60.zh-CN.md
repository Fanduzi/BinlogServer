# Binlog Server v0.5.60 中文发布说明

> 对应版本：`v0.5.60`

发布日期：2026-10-13

v0.5.60 修复 `GET /api/tasks/{id}/replay` 的一个 P1（#305，PR #306）。以前不带参数的 `/replay` 和 `/replay/archive` 只返回最新的 200 个段文件，不给任何提示，而 `/window` 仍说整条链是连续的。按这组文件恢复会报 ERROR 1032；如果后面的事务碰巧不依赖前面的行，恢复不报错，但更早的事务悄悄缺了。现在不带参数的回放集列出恢复需要的每个文件；显式给 `limit` 时仍按窗口返回，但会写明省略了多少个更早的文件。其余是三处不改行为的内部重构（PR #300、#301、#304）、一个 e2e 测试修复和一次仓库整理。没有新配置项。没有 schema 迁移。schema 仍是 6。`minRequiredSchemaVersion` 仍是 6。地板仍是 v0.5.51。BinlogServerQA 对 `eaa100594b9bd2ebbaa4172a48d294b4dbe93857`（evidence-306）的 tip dogfood 通过，没有 P0、P1、P2。一个 P3 记为 #307。

**历史改写。** BinlogServer 的提交历史在 2026-10-12 改写过。此前的提交哈希都变了，旧发布说明、issue 或 QA 证据里引用的哈希（例如 v0.5.59 说明里的 0a84917a）可能已经找不到。release tag 已指向改写后的提交，已发布的二进制没有变。请按 tag 或 PR 号查找改动。

## 核心变化

- **`/replay` 不再悄悄截断（#305，PR #306，P1）。** 不带 `limit` 的 `GET /api/tasks/{id}/replay` 和 `GET /api/tasks/{id}/replay/archive` 返回保留链里的每个文件，从第一个开始，损坏截断规则不变。它们和 `/window` 读同一条链，两者结论一致。回放不再套用文件列表默认的 200 上限。
- **显式 `limit` 会写明省略了什么。** `?limit=N` 仍返回最新的 N 个文件。完整回放集还有更早的文件时，JSON 多出 `omitted_files` 和 `warning`：写明从哪个文件起被省略，以及单独回放这一组不能从备份开头恢复。tar 用响应头 `X-Replay-Omitted-Files` 和 `X-Replay-Warning` 说明。`limit` 为 0、负数或不是数字时按不带 `limit` 处理。
- **控制台。** 任务抽屉里的回放命令和「下载回放集」不再带 `limit=80`，拿到的是全部文件。文件表仍显示最新 80 行。
- **不改行为的重构。** 都和上一版 main 逐字节对比过：14 个真实任务目录的 API golden 输出、e2e 套件、旧版回切升级脚本、重连和 kill 浸泡测试。
  - **段账本（PR #300，ADR 0006）。** 「磁盘上存着哪些 GTID」只由一个模块回答：分段、已存集合、空洞、损坏、可续传的打开尾部。
  - **存储健康（PR #301，ADR 0007）。** 每个任务目录一个结论：损坏、旧版回切、已存 GTID 洞，按这个顺序判断。`storage_alert`、`/replay`、`/window` 和回放警告都用它。
  - **一次运行的五个阶段（PR #304，ADR 0008）。** 复制主流程拆成续传起点、连接、分段追加/rotate/封存、事件处理、重连与错误分类五个阶段。
- **测试。** `smoke-worker-crash-recovery` 不再比对任务的第一个文件：LATEST 任务从那个 binlog 的中部开始，备份本来就不等于源文件。这是测试问题，不是数据损坏。现在多 rotate 一次，比对最新两个完整文件，其中包括 `kill -9` 时正在写的那个。
- **仓库。** `verify-binlog-server` 技能目录移到 `.agents/skills`（PR #303），不影响发布的二进制。

## 升级影响

- 不带 `limit` 调 `/replay` 或 `/replay/archive` 的脚本，现在拿到全部文件，而不是最多 200 个。链很长时 JSON 和 tar 会更大，这是预期结果：以前的答案不完整。
- 带 `limit` 的调用拿到的路径和以前一样。把这样的集合当作完整恢复之前，先看 `omitted_files`（或 `X-Replay-Omitted-Files`）。
- 如果在 v0.5.59 或更早版本上按不带参数的 `/replay` 做过恢复，而任务当时有超过 200 个段文件，那次恢复可能缺最早的事务。把当时 `paths` 的第一个文件和 `/window` 的 `earliest` 对一下，或按新的完整集合重做恢复。

没有新迁移。已经在 schema 6 上的库仍是 schema 6。确认 `SELECT version, dirty FROM schema_migrations` 是 `(6, 0)`。`migrations/` 仍是 `000001` 到 `000006`，没有 `000007`。`minRequiredSchemaVersion` 仍是 6：v0.5.60 在 schema 5 上不会启动，以退出码 1 结束，还没开始监听，提示含 `schema version too old` 和 `./migrate up`。还不是 schema 6 时先按 [v0.5.56 升级](v0.5.56.zh-CN.md)。地板仍是 v0.5.51。没有新配置项。v0.5.59 的旧版回切规则和 v0.5.58 的 `storage_alert` 规则仍成立。

## 已知行为

- #307（P3）：`limit=0`、负数或非数字被当作「全部文件」接受，写错了不会被发现。带 `stop_datetime`、`stop_gtid` 或 `start_gtid_set` 时 `limit` 不起作用：定点恢复集合总是完整的，没有 `omitted_files`。`warning` 只有英文。
- v0.5.59 的已知行为仍适用。

## QA 摘要

- 带 `limit` 的定点恢复：集合完整，与 main 相同。
- `smoke-worker-crash-recovery` 的新逻辑：3/3 通过。
- 回归：storage alert、旧版回切和 `/window` 的输出与 main 一致。
