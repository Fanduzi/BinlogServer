# Binlog Server v0.5.14 中文发布说明

> 对应版本：`v0.5.14`

发布日期：2026-10-03

`v0.5.14` 是 `v0.5.13` 的运维补丁。dump 文件头不是复制延迟。已经追上的 `RUNNING` 任务把 `delay_seconds` 以 JSON `0` 返回。没有 schema migration，没有新的配置键。30 秒阈值没有变化。已发布的 v0.5.13 压缩包在认领后从最高分段末尾启动、源库已经停在该位点且没有新写入时，仍会把 format description 的时间戳存成 `last_event_at`，并报 `DELAY_EXCEEDS_THRESHOLD`。

## 核心变化

- 认领之后从最高分段末尾启动，源库已经在这个位点、没有新写入时，以前会把 format description 的时间戳存成 `last_event_at`，并报 `DELAY_EXCEEDS_THRESHOLD`。这个误报没有了。仍在追位点的真实延迟继续用事件时间。30 秒阈值没有变化。
- 已经追上的 `RUNNING` 任务现在把 `delay_seconds` 以 JSON `0` 返回，Console 显示「0 秒」。在源 tip 上状态保持 `NORMAL`。还没有事件时间样本的任务仍然省略 `delay_seconds`，Console 仍可以显示「-- 秒」。没有新的配置键。不需要 schema migration。
- 自编译 tip `d833072d` 的试用（不是已发布的 v0.5.13 压缩包）：没配 `meta_dsn`，认领后从最高分段末尾启动，源库停在 `mysql-bin.000005:490`。Console 延迟「0 秒」，复制状态 正常，没有 `DELAY_EXCEEDS_THRESHOLD`。`GET /api/tasks/{id}/replication` 的 `delay_seconds` 是 0。另一个没有样本的任务仍显示「-- 秒」。新的 open 分段是 4 字节，不是 126 字节的 format description，源库位点仍是 490。

## 升级影响

- `v0.5.14` 不需要 schema migration。迁移仍只有 `000001_init_schema`。
- 配置键没有变化。`PRODUCTION=true` 仍要求非空 `--encryption-key`。30 秒阈值没有变化。
- 认领之后从最高分段末尾启动，源库已经在这个位点、没有新写入时，不再把 format description 的时间戳存成 `last_event_at`，也不再报 `DELAY_EXCEEDS_THRESHOLD`。仍在追位点的真实延迟继续用事件时间。已发布的 v0.5.13 压缩包仍会把该时间戳存成 `last_event_at`，并报 `DELAY_EXCEEDS_THRESHOLD`。
- 已经追上的 `RUNNING` 任务把 `delay_seconds` 以 JSON `0` 返回，Console 显示「0 秒」。在源 tip 上状态保持 `NORMAL`。还没有事件时间样本的任务仍然省略 `delay_seconds`，Console 仍可以显示「-- 秒」。
- 自编译 tip `d833072d` 的试用（不是已发布的 v0.5.13 压缩包）：没配 `meta_dsn`，认领后从最高分段末尾启动，源库停在 `mysql-bin.000005:490`。Console 延迟「0 秒」，复制状态 正常，没有 `DELAY_EXCEEDS_THRESHOLD`。`GET /api/tasks/{id}/replication` 的 `delay_seconds` 是 0。另一个没有样本的任务仍显示「-- 秒」。新的 open 分段是 4 字节，不是 126 字节的 format description，源库位点仍是 490。
