# Binlog Server v0.5.37 中文发布说明

> 对应版本：`v0.5.37`

发布日期：2026-10-05

任务碰到本地自己消不掉的错误时，不再停在 `RETRY_BACKOFF`、续着租约、反复去连源库。任务进入 `FAILED`。租约放开。这个 runner 不再被调用，源库上的 Binlog Dump 也不会重新连上。先把原因处理掉，再 Start。跟踪为 #178。

## 核心变化

- `sealed file already exists` 把任务写成 `FAILED`。`last_error` 是 `SEALED_FILE_EXISTS: sealed file already exists: <path>`。租约放开，这个 runner 不再被调用。把多出来的封存文件移走，再 `POST /api/tasks/{id}/start`。
- checkpoint 写入不是瞬时元数据错误时，任务进入 `FAILED`，`last_error` 以 `CHECKPOINT_WRITE_FAILED` 开头，租约放开。先修 `last_error` 里的元数据库错误，再 Start。瞬时 checkpoint 错误仍是 `RETRY_BACKOFF`。判定和元数据客户端的列表一致：deadlock、lock wait timeout、connection reset、connection refused、broken pipe、server has gone away、invalid connection、bad connection、read-only、timeout、eof。`context.Canceled` 和 `context.DeadlineExceeded` 仍可重试。
- 租约 epoch 对不上是移交。丢掉 epoch 的 runner 停下来，只放开自己的 epoch。它不写 `FAILED`，也不写 `RETRY_BACKOFF`，所以不会盖住现在持有任务的 worker 的任务行。没有元数据库时，本进程显示 `STOPPED`，并追加 `TASK_LEASE_YIELDED`。从 `STOPPED` 可以再 Start。
- `SOURCE_UNREACHABLE` 不变：连续十次失败后进入 `FAILED`，一个已经就绪的 runner 会把这个计数清掉。其它可重试的源错误、`OBJECT_PURGE_FAILED`，以及没有存储 GTID 的 MySQL 1236，仍停在 `RETRY_BACKOFF`，没有新的上限。
- 元数据客户端在一次调用里已经把瞬时错误重试五次。调度器这一层的重试，是元数据切换之后任务还能回到 `RUNNING` 的原因。上限设成十次会把这份备份标成 `FAILED`，还得人手动 Start。`OBJECT_PURGE_FAILED` 在下次打开文件时再试。把任务打成失败会停掉采集，直到桶恢复、有人 Start。`gtid_set` 为空的 MySQL 1236 仍是 v0.5.36 的续传缺口。
- 本地 binlog 追加或 flush 失败仍按原样返回并重试。它不是封存文件冲突，也不是这次 checkpoint 写入。

## 升级影响

二进制从 v0.5.36 滚动升级即可。这一版没有 schema migration。元数据 schema 仍是 v0.5.34 引入的版本 2。`schema_migrations` 已经是版本 2 时，不用执行 `./migrate up`。

还在 schema 1 上的库，要先迁移，这个二进制才会启动。按 [v0.5.34 升级说明](v0.5.34.zh-CN.md)：停掉这个元数据库上的每一台 binlog-server，执行 `./migrate up`，然后只启动 v0.5.34 或更新的二进制。

没有新的配置项。

## 已知行为

下面这些在这一版之前就有。QA 在 `9c350c07` 上核对过。这一版没有改它们。

- 一体进程和集群角色上，`SOURCE_UNREACHABLE` 的十次上限不会触发。认领循环大约每 2 秒会再次启动自己名下的 `RETRY_BACKOFF` 任务，并把连续失败计数清掉，任务一直停在 `RETRY_BACKOFF`。没有元数据库的 standalone 仍会在连续十次失败后进入 `FAILED`，`last_error` 以 `SOURCE_UNREACHABLE:` 开头。父提交上就是这样。跟踪为 #203。
- 拉流已经打开时源库宕机，任务可能仍显示 `RUNNING`。租约继续续。dump 库日志是 `retry sync err, wait 1s`。调度器看不到这个错误，任务不进 `RETRY_BACKOFF`，也不累计 `SOURCE_UNREACHABLE`。源库恢复后任务继续，位点能对齐。跟踪为 #204。
- GTID 模式启动，以及文件位点续传在 MySQL 1236 之后打开 `StartSyncGTID`，会写入一条没有 CRC 的人工 Rotate。`mysqlbinlog --verify-binlog-checksum` 在这条事件上报 `Event crc check failed!`。不加这个参数时文件可以读完。已经复制的事件本身是完整的。GTID 启动还会留下一个多余的 `task-N.binlog`。目录把它记成 `SEALED` 并上传。跟踪为 #205。
- 故障切换之后，后一次封存的分段，例如 `mysql-bin.NNNNNN.sealed.e1`，`end_pos` 可能是 0。`size_bytes` 是文件大小。这一行仍可以是 `UPLOADED`，checksum 为 `match`。文件列表里仍有这一段，下载和回放仍能返回它。这是 v0.5.34、v0.5.35 和 v0.5.36 已经记下的行为。跟踪为 #189。
- 停止过程中改了源库密码，然后再 Start，源库上可能短暂出现两条 Binlog Dump。之后再一次停到 `STOPPED`，仍可能留下一条 Binlog Dump，需要在源库上手动 `KILL`。控制面上一次普通停止，以及一体进程上的停止，源库进程列表里不再有该任务的 Binlog Dump。这是 v0.5.35 和 v0.5.36 已经记下的行为。跟踪为 #193。
