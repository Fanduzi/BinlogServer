# Binlog Server v0.5.33 中文发布说明

> 对应版本：`v0.5.33`

发布日期：2026-10-05

`v0.5.33` 上，封存过程中进程挂了，或者文件刚改完名、上传还没记进目录，这份 binlog 仍然会进桶。到 `v0.5.32` 为止，这种文件会停在 `LOCAL_ONLY`，或者根本不进补传集合。后台补传不会去传它。租约被别的 worker 接走时，任务可能以 `SEGMENT_NOT_ON_WORKER` 失败。封存之后的上传以前没有截止时间，对象存储一挂，拉流就停在那里，这个 worker 一直占着租约，直到进程被杀掉。已发布的 v0.5.32 包仍然这样。没有新的上传状态。没有新的配置项。不需要 schema migration。

## 核心变化

- 配了对象存储时，PUT 之前先写目录行。这一行 `state` 是 `SEALED`，`upload_state` 是 `UPLOAD_FAILED`，`upload_error` 是 `upload pending`，对象键已经写上。下一个 binlog 文件的 checkpoint 也在这次 PUT 之前落盘。
- 这次 PUT 用 `meta.timeout.upload_sec` 封顶，默认 30 秒，和后台补传是同一个截止时间。到点之后这一行仍是 `UPLOAD_FAILED`，复制去打开下一个文件。拉流最多等到这个时间，然后继续。
- 下次启动，包括租约接管，本机磁盘上已经封存、还没变成 `UPLOADED` 的文件，会记成 `UPLOAD_FAILED`，带上对象键，`upload_error` 为 `upload pending`。checkpoint 如果还停在这个封存文件上，并且文件末尾最后一个完整事件是指向下一个文件的 rotate，checkpoint 会挪到 rotate 写出的下一个文件和位点。rotate 给出的位点是 0 时，按 4 继续。复制从下一个文件接着跑。真正拉 binlog 的 worker 会跑后台补传，自己把文件传上去并核对 checksum。只做控制面的进程不跑这个循环。等待期间 `GET /api/tasks/{id}/files` 看到 `upload_state` `UPLOAD_FAILED`、`location` `local`。传完、checksum 为 `match`、文件还在磁盘上时，是 `UPLOADED`，`location` `both`。这个 worker 读不到的封存文件，接管仍以 `SEGMENT_NOT_ON_WORKER` 失败。
- 配了对象存储并且有目录时，checksum 还不是 `match` 之前，保留清理留下本地文件和目录行。文件的修改时间已经超过本地保留天数时，这一轮把它留下，并记一条 `RETENTION_SKIPPED_NOT_UPLOADED`。复制继续跑。
- 没配对象存储时，封存仍是 `LOCAL_ONLY`，对象键是空的，文件留在本机。`POST /api/tasks/{id}/files/retry-upload` 返回 HTTP 400，正文 `upload retry is not available`。有目录时，这种行的保留和以前一样。还没 `UPLOADED` 的封存文件，租约接管仍可能以 `SEGMENT_NOT_ON_WORKER` 失败。
- 没有新的上传状态。没有新的配置项。不需要 schema migration。迁移仍只有 `000001_init_schema`。Console 本来就会显示 `upload_state`、`upload_error` 和 `checksum`。已有的重试按钮在 `UPLOAD_FAILED` 上出现。

## 已知行为

- `meta.timeout.upload_sec` 到点之后，`upload_error` 仍是 `upload pending`。用来把超时写进目录的那次更新，用的是同一个已经取消的截止时间，所以写不进去，目录里留下的还是 PUT 之前那句。
- 崩溃之后才补进重试集合的文件，`sealed_at` 是本进程打开这个文件的时间。打开中的行没有单独的封存时间。目录把 `sealed_at` 写成和 `created_at` 相同的值，补登记时沿用这个时间。
- 封存后的 PUT 还挂着时，本进程不写新的本地 binlog 事件。到点之后从下一个文件继续写。这段等待里，租约仍在这个 worker 上。
- PUT 还挂着时，后台补传可能对同一个对象键再 PUT 一次。内容就是这份已经封存的文件，两次字节相同。
- 之后某次任务运行时配上了对象存储，磁盘上还在的封存 `LOCAL_ONLY` 文件会被传上去。到 `v0.5.32` 为止，事后才打开对象存储，这种行不会被上传。只有还在磁盘上的文件会进桶。
- checksum 仍是上传之后比对一次。已经比对为 `match` 的对象，之后在桶里被换掉，不会再比对。

## 升级影响

- `v0.5.33` 不需要 schema migration。迁移仍只有 `000001_init_schema`。
- 没有新的状态。没有新的配置项。`meta.timeout.upload_sec` 是原有的上传截止时间，默认仍是 30 秒。`cluster.failover_policy` 仍然不是开关。`PRODUCTION=true` 仍要求非空 `--encryption-key`。30 秒阈值没有变化。
- 在 `v0.5.32` 及更早版本上，上传过程中崩溃留下的封存文件会停在 `LOCAL_ONLY`，或者不在补传集合里，需要人工处理。升级后，下次带着对象存储启动时，磁盘上还在、还不是 `UPLOADED` 的封存文件会记成 `UPLOAD_FAILED`，由后台补传上传。看 `GET /api/tasks/{id}/files`。`upload_error` 为 `upload pending` 是 PUT 之前写下的那句，上传截止时间已经到过也仍是这句。后台补传稍后会把这个文件传上去。
