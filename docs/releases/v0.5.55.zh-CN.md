# Binlog Server v0.5.55 中文发布说明

> 对应版本：`v0.5.55`

发布日期：2026-10-07

定点恢复可以从已恢复全量备份的已执行 GTID 集合往后接。`GET /api/tasks/{id}/replay` 和 `GET /api/tasks/{id}/replay/archive` 接受 `start_gtid_set`，和已有的 `stop_gtid` 或 `stop_datetime` 一起用。这个集合是恢复实例上的 `@@gtid_executed`、mysqldump 的 `GTID_PURGED`，或 `xtrabackup_binlog_info` 里的 GTID 集合。停止点之前的事务已经都在这个集合里的分段，不进入 `paths`，也不进 tar。`command` 是 `TZ=UTC mysqlbinlog`，带上该集合的 `--exclude-gtids`，所以这些事务不会再应用一次。停止语义与 v0.5.54 相同。非空的 `start_datetime` 不能和 `start_gtid_set` 一起出现。纯文本 400 是 `invalid start_gtid_set`、`start_gtid_set is not supported for this flavor`、`start_gtid_set and start_datetime cannot both be set`、`stop_datetime or stop_gtid is required` 和 `start_gtid_set has a gap before this task's backed-up range`。停止点之前的每一条事务都已经在集合里时，仍是 HTTP 200，`paths` 为 `[]`，`command` 为空，`note` 为 `every transaction up to the stop is already in start_gtid_set`。Console 的定点恢复表单有已执行 GTID 字段，「已执行 GTID」。参数表在 `docs/guide/reference/api.md` 第 5.9 节。Swagger 已重新生成。没有 schema 变更。schema 仍是 6。`minRequiredSchemaVersion` 仍是 6。ADR 0005 没有改。地板仍是 v0.5.51。没有新的配置项。BinlogServerQA 的 tip dogfood 在 `9f1d9b8651971d1ed4196171f2d51938cd0f609d` 上为 PASS。v0.5.54 的 `stop_gtid` 规则仍成立（PR #279）。v0.5.49 的封存位点规则（#189）仍成立。v0.5.48 不留下空 `task-<id>.binlog` 的规则（#205）仍成立。v0.5.52 清理 `.takeover-*` 的规则仍成立（#224，PR #273）。v0.5.53 丢掉 `uk_task_file_epoch` 的规则仍成立（PR #276）。`start_gtid_set` 在 PR #282 落地。

## 核心变化

- 已经恢复的全量备份里已经有事务。xtrabackup、mysqldump 和 clone 把它记成恢复实例上的 `SELECT @@gtid_executed`、mysqldump 的 `SET @@GLOBAL.GTID_PURGED`，或 `xtrabackup_binlog_info` 里的 GTID 集合。把这个集合作为 `start_gtid_set`，再带上 `stop_gtid` 或 `stop_datetime`。已发布的 v0.5.54 包没有 `start_gtid_set`。`start_datetime` 仍是 v0.5.54 那个含该时刻的时间下界。它不是这个集合。
- `start_gtid_set` 是一个 MySQL GTID 集合。单独的 `<server_uuid>:<seq>` 是只含一条事务的集合。空格和换行会去掉。`--exclude-gtids` 收到的是规范形式。规范形式里含逗号时，外面加单引号。空值、只有空白、MariaDB `domain-server-seq`（例如 `0-1-10`）、不是 MySQL GTID 集合的字符串、`<server_uuid>:0` 和 `<server_uuid>:0-5`，在查任务之前就是纯文本 400 `invalid start_gtid_set`。
- `source.flavor` 不是 `mysql` 时，已经按 MySQL 解析成功的集合是纯文本 400 `start_gtid_set is not supported for this flavor`。这条路径不解析 MariaDB GTID。MariaDB 形状在这次 flavor 检查之前就是 `invalid start_gtid_set`。
- `start_gtid_set` 必须带 `stop_datetime` 或 `stop_gtid`。两个都没有是纯文本 400 `stop_datetime or stop_gtid is required`。集合无法解析时，即使停止参数也缺失或无法解析，仍是 `invalid start_gtid_set`。`stop_datetime` 和 `stop_gtid` 同时出现，包括其中一个值为空，是 `stop_datetime and stop_gtid cannot both be set`。这个检查最先做，`start_gtid_set` 无法解析时也一样。非空的 `start_datetime` 和 `start_gtid_set` 一起出现是 `start_gtid_set and start_datetime cannot both be set`。这个检查在解析集合之前。空的 `start_datetime` 当作没给。
- 服务端按 binlog 顺序读每个分段里的 `GTID_EVENT`。这次请求扫描这些字节。不新增列。`stop_datetime` 仍不含时间戳大于等于停止时间的事件。`stop_gtid` 仍停在该事件的起始字节。已经在 `start_gtid_set` 里的事务不算还要应用。一个分段里、停止点之前的事务全都已经在集合里时，这个分段不进入 `paths`，也不进 tar。还剩事务要应用的分段留下。只存在于桶里的封存 `UPLOADED` 对象，和本地文件用同一条规则。
- `command` 以 `TZ=UTC mysqlbinlog` 开头。先写 `--exclude-gtids=<规范集合>`，所以 mysqlbinlog 跳过集合里已有的事务，只放进还没有的事务。设置了 `stop_datetime` 时接着写 `--stop-datetime='<UTC>'`。`stop_gtid` 所在的文件仍是最后一条路径时，再写 `--stop-position=<N>`。`N` 仍是该事件的起始字节。然后是这些路径。不写 `--start-datetime`。停止点所在的文件因为停止点之前没有新事务而被省略时，命令不写 `--stop-position`。前面留下的文件整段应用。路径为空时，`command` 是空字符串。
- 停止点之前的每一条事务都已经在集合里时，仍是 HTTP 200。`paths` 是 `[]`。`command` 是空字符串。`note` 是 `every transaction up to the stop is already in start_gtid_set`。这不是错误。响应里不会给出一条会把这些事务再应用一次的命令。停止点落在第一条事务上、窗口里本来就没有事务时，`paths` 和 `command` 仍为空，不带 `note`。
- 要应用的第一段不能跳过这份任务里没有的事务。这一段如果带有 previous-GTIDs，这个集合必须是 `start_gtid_set` 的子集。无论有没有 previous-GTIDs，该段里每个 UUID 的最小序号 `N` 还要求 `1` 到 `N-1` 已经被 previous-GTIDs、`start_gtid_set` 和更早保留分段里的事务合起来盖住。GTID 拉流会留下源文件开头的 previous-GTIDs，并跳过任务启动前、仍写在同一个源文件里的事务。这些序号不在分段里，必须已经在集合中。盖不住时是纯文本 400 `start_gtid_set has a gap before this task's backed-up range`。备份比保留的 binlog 更老、中间缺了事务时必须拒绝，不能静默跳过。集合与段内事务没有交集、但 `1` 到 `N-1` 已经被盖住时，这是从保留范围的开头续上，仍返回这些分段。
- `stop_gtid` 不是这份备份里的一条 `GTID_EVENT` 时，仍是 `stop_gtid is not in this task's backed-up range`。这句优先于缺口那句。`start_gtid_set` 是合法的 MySQL 集合、任务又不存在时，是 HTTP 404 `task not found`。已选分段打不开是 HTTP 404 `segment not found on this process`。
- 设置了 `start_gtid_set` 时，`limit` 不起作用。`GET /api/tasks/{id}/replay/archive` 接受同一个 `start_gtid_set` 和同一个停止参数。tar 的成员是这些 basename。`--exclude-gtids` 和停止参数留在 JSON 的 `command` 里。它们不是 tar 成员。已经全部包含的窗口是空 tar。集合缺失、flavor 不支持、或有缺口时，错误句子与 JSON 路由相同。正文不是 tar。
- Console 任务详情的定点恢复表单有已执行 GTID 字段。中文是「已执行 GTID」。英文是 `Executed GTID set (start_gtid_set)`。停止时间或停止 GTID 仍至少填一个才能生成命令，也可以下载 `task-{id}-replay.tar`。已执行 GTID 和开始时间都填时，请求同时带上这两个参数，页面显示 `start_gtid_set and start_datetime cannot both be set`。`note` 有文字而 `command` 为空时，页面显示这句说明。这个 Console 在普通 `go build` 打进去的嵌入包里。
- 没有新的配置项。没有 schema 迁移。`minRequiredSchemaVersion` 仍是 6。`migrations/` 仍是 `000001` 到 `000006`。没有 `000007`。ADR 0005 没有改。第 1 到第 9 步已经发出。第 9 步在 v0.5.53 发出。这一版不是新的 ADR 步骤。

## 升级影响

没有新迁移。已经在 v0.5.54 / schema 6 上的库仍是 schema 6。确认 `SELECT version, dirty FROM schema_migrations` 是 `(6, 0)`。`migrations/` 仍是 `000001`、`000002`、`000003`、`000004`、`000005` 和 `000006`。没有 `000007`。

`minRequiredSchemaVersion` 仍是 6。v0.5.55 在 schema 5 上不会启动，以退出码 1 结束，还没开始监听。提示含 `schema version too old` 和 `./migrate up`。这与 v0.5.54 的拒绝相同。schema 4 和 schema 3 同样拒绝启动。

schema 6 已经就位之后再换二进制。库已经是 v0.5.54 / schema 6 时，没有 `./migrate` 这一步。还不是 schema 6 时，先按 [v0.5.54 中文发布说明](v0.5.54.zh-CN.md)，确认 `(6, 0)`，再启动 v0.5.55。

地板仍是 v0.5.51，它是第一版同时带上 ADR 0005 第 6 步和第 7 步的发布。v0.5.50 只发了第 6 步。`./migrate up` 到 schema 6 之前，先停掉仍要求 `uk_task_file_epoch` 的每一台进程。v0.5.51 和 v0.5.52 就是这些二进制。schema 6 上它们拒绝启动。日志含 `missing index` 和 `uk_task_file_epoch`。比 v0.5.51 旧的进程，包括 v0.5.50，都不是地板。`000006` 之前先换掉。然后停掉 v0.5.51 和 v0.5.52。然后执行 `./migrate up`。

schema 4（`000004_pending_dump_cleanup`）仍在迁移链上。v0.5.50 之前，schema 4 是单进程可选、集群必须。分步升级、启动的仍是比 v0.5.50 旧的二进制时，这条规则还适用。v0.5.55 自己不能停在 schema 4。

如果这套库还不是 schema 3，先按 [v0.5.46 中文发布说明](v0.5.46.zh-CN.md)，再按 v0.5.50，再按 v0.5.53。schema 2 到 schema 3（`000003_task_desired_and_retry_budget`）在线。schema 1 到 schema 2 仍按 [v0.5.34 升级说明](v0.5.34.zh-CN.md)：停掉每一台进程，执行 `./migrate up`，然后只启动 v0.5.34 或更新的二进制。

没有新的配置项。没有元数据库的 standalone 不跑这些迁移。`start_gtid_set` 读的是本进程打得开的分段，所以 standalone 上是同一个查询。

不要 `./migrate down` 退过正在跑的二进制所需要的 schema。v0.5.55 需要 schema 6。这一版没有新迁移，所以没有新的 down 步骤。schema 6 上 `./migrate down --steps 1` 仍是 v0.5.53 的那次 down：把 `uk_task_file_epoch` 加回来。不删行。不删 `file_name`。不删 `uk_task_source_epoch`。回到 version 5。`binlog_files` 行数不变。已经有两行共用 `(task_id, file_name, epoch)` 时，这次 down 会失败。不要为了让它通过而删行。写入方保持 `file_name` 等于 `source_file`。v0.5.55 还在跑时不要做这次 down。v0.5.55 在 schema 5 上不会启动。生产环境的 `./migrate down` 仍要 `ALLOW_DESTRUCTIVE_MIGRATE=1` 才放行。

v0.5.53 的索引规则仍成立。`SHOW INDEX FROM binlog_files` 列出 `uk_task_source_epoch`，不列出 `uk_task_file_epoch`。`file_name` 列还在。再插入相同的 `(task_id, source_file, epoch)` 会失败。重复键是 `uk_task_source_epoch`。

v0.5.52 清理 `.takeover-*` 的规则仍成立。worker 仍会删掉任务目录里留下的普通 `.takeover-*`。v0.5.51 的未知 `end_pos` 规则仍成立。本进程读不到本地字节时，`GET /api/tasks/{id}/files` 的未知 `end_pos` 是 JSON `null`，Console 单元格是空白。本地文件能读到事件时，给出事件跨度。

v0.5.54 的 `stop_gtid` 规则仍成立。v0.5.49 的封存位点规则（#189）和 v0.5.48 的空 `task-<id>.binlog` 规则（#205）仍成立。`stop_datetime` 没有改。时间戳大于等于停止时间的事件仍不进入那条命令。BinlogServerQA 的 tip dogfood 在 `9f1d9b86` 上为 PASS。

这一版不是 ADR 0005 的步骤。第 1 到第 9 步已经发出。ADR 0005 没有改。发出第 9 步的是 v0.5.53。

## 已知行为

#224 已在 v0.5.52 修好。#189 已在 v0.5.49 修好。#205 已在 v0.5.48 修好。`stop_gtid` 在 v0.5.54 发出。这一版没有再改这些修复。这一版不是 ADR 0005 的步骤。ADR 0005 没有改。

- `stop_datetime` 仍按事件头的秒切开。同一秒里的事务在时间路径上仍是一起进或一起出。已经知道坏 GTID 时用 `stop_gtid`。`start_gtid_set` 不改变这个停止点。
- 盖不住要应用的第一段之前那些事务的集合会被拒绝。回放不会跳过这个缺口。
- schema 仍是 6。地板仍是 v0.5.51。没有 `000007`。`file_name` 仍是一列。
