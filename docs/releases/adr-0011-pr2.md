# ADR 0011 PR-2: session kill and META_LOCK_STALLED

This note is the operator contract for the session-kill rollout. It is not a published version bump. Checksums for v0.5.76 are unchanged. Scheduler failover cutover, migration 000011, and `CREATE PROCEDURE binlog_server_kill_trx` are a later change.

## RTO

The start is the last successful renew (`task_leases.renewed_at`, the `NOW(6)` of that statement). When this epoch has not renewed, the start is the acquire commit. The end is the new owner's `DumpReady` commit.

```
lease_ttl + max(idle_kill, lock_wait) + claim_interval + start_to_ready
```

`start_to_ready` is 10s: from `STARTING` committed, directory readable, source accepting the dump, to `DumpReady` committed. Grace is not in the formula. `side_kill` is not in the formula. Another `worker_id`'s registration TTL is not in the cross-node formula.

Defaults: lease TTL 15s, idle_kill 5s, lock_wait 4s, claim interval 2s, start_to_ready 10s. `max(idle_kill, lock_wait)` is still 5s, so the bound is 32s. A field TTL of 60s is 60 + 5 + 2 + 10 = 77s.

`idle_kill` is the armed server timeout: MySQL 8 `wait_timeout` (and the same bound on `net_read_timeout` and `net_write_timeout`); MariaDB `idle_transaction_timeout` as well. `lock_wait` is `innodb_lock_wait_timeout`. The idle bound is `min(5s, lease_ttl/2)`, at least 1s. `lock_wait` rounds that bound down to a whole second and is at least 1s. With the default 5s idle bound it is 4s.

Each lock-taking statement has its own client deadline, measured from when that statement starts: `innodb_lock_wait_timeout` plus a fixed margin of at least 1s. The health insert, the lease `SELECT … FOR UPDATE`, the health `FOR UPDATE`, and the health update each get that budget. Time already spent earlier in the transaction cannot shrink it, so the server's 1205 returns before that statement's deadline. An outer deadline still bounds the whole health write. It is only a backstop.

Waiting for a pool connection is not the same wait as a statement. A checkout that times out is a stall only when the pool is saturated (`InUse` equals `MaxOpen`) and at least one in-flight meta write is in a confirmed lock wait or has passed its statement bound. The reason is pool starvation behind a lock wait. A slow pool with no lock evidence stays an unconfirmed deadline, so a busy pool is not reported as a stall.

Health detail reports `side_kill=off` unless a drill has passed.

A transaction frozen inside a statement, with `side_kill` left off, is outside this bound. A live owner that makes no dump progress still uses `no_progress_after` (default 120s) plus one sweep. That threshold is not clamped to the RTO.

## Same-node restart (F10)

The same-node `per_node` restart bound is the cross-node RTO plus this node's registration TTL (`SameNodeRestartBound`). With the defaults that is 32s + 15s = 47s. A clean restart does not take an unexpired registration. That wait is ADR 0001 session ownership: a new process cannot be told apart from `SIGSTOP`. The other F10 option, letting that restart take the registration as soon as it expires by a special path, was not taken.

## Session variables

Cluster startup sets these on every pool connection and every reconnect, as driver system variables:

- `wait_timeout`
- `net_read_timeout`
- `net_write_timeout`
- `innodb_lock_wait_timeout` (strictly below the client deadline; see above)
- MariaDB also `idle_transaction_timeout`

A required `SET` that the server rejects refuses cluster start. Standalone is not armed. `ConnMaxIdleTime` is at most 2s and at most one third of `wait_timeout`, so the pool closes an idle connection before the server kills it. A bound of 2s or less keeps no idle connections (`MaxIdle` 0). A longer bound keeps 8. It is pool hygiene, not the RTO proof.

ProxySQL or MaxScale may swallow `SET`. Startup reads every armed variable back on a fresh pool connection, before the first lease write: `wait_timeout`, `net_read_timeout`, `net_write_timeout`, `innodb_lock_wait_timeout`, and on MariaDB `idle_transaction_timeout`. Each lease acquire and renew reads the same set on that lease transaction. A mismatch, or a read that fails, is degraded on `/api/health` from the moment it is seen, including at startup, and does not refuse start. The alternative, requiring the bounds as server globals, was not taken.

## Meta account

Stall detection needs no `PROCESS` privilege and no `performance_schema` grant. `GRANT ALL ON binlog_server_meta.*` to the meta account is enough: a real row lock ends as MySQL error 1205 because each lock statement's client deadline is longer than `innodb_lock_wait_timeout`.

Naming the holder is a separate check. Startup runs the naming queries (`performance_schema.data_lock_waits` joined to `threads`, and `information_schema.innodb_lock_waits`) and reads a row. `LIMIT 0` does not fill `information_schema`, so MariaDB would skip the `PROCESS` check and a database-only account would look fully privileged. MySQL error 1227 or 1142 means the account cannot use that view. `SHOW GRANTS` text is not a privilege. `information_schema.innodb_trx` succeeding is not enough: without `PROCESS` it returns only this session and does not fail on every server. MySQL 8 with only `PROCESS` does not name the holder either. `lock_detail` stays `reduced` until a naming query answers. The process logs one warning and `/api/health` includes `"lock_detail":"reduced"`. That field is not a degraded reason and does not change the HTTP status. Detection still opens `META_LOCK_STALLED` from 1205.

## side_kill

`cluster.side_kill` is `off` or `auto`. The default is `off`. `auto` is the operator's statement that the meta connection is direct. Do not enable it behind a SQL-parsing proxy (ProxySQL, MaxScale, and the same class). Those proxies handle `KILL` themselves and may drop `CALL`.

The client never sends `KILL`. The drill and a real kill are `CALL binlog_server_kill_trx`. The procedure and `meta_canary` are not installed by this change. Until they exist, `auto` stays off. A missing procedure or a failed drill stays off and does not fail the sweep.

When the procedure exists, the drill locks this node's own `meta_canary` row. MariaDB has no `performance_schema.data_locks`, so a third connection waits on that row before the call; otherwise the lock view cannot see it and `auto` stays off. MySQL 8 also needs `PROCESS` and a readable `performance_schema.data_locks` (fail closed). The definer still needs `PROCESS` inside the procedure. `EXECUTE` on `binlog_server_kill_trx` is granted only to the binlog-server account, not as a database-wide grant for other accounts. RDS names inside the procedure, not the client, are `mysql.rds_kill` on RDS MySQL, RDS MariaDB, and Aurora MySQL. A check-then-act gap inside the server is accepted.

A passing drill writes `Aborted connection` to the server error log. Put that line on the alert whitelist.

## META_LOCK_STALLED (F12, N6)

The finding is written on task `_cluster`, subject the task id, by the node that observed the wait. The write does not lock `task_leases` and does not call `applyOnce`. If the write fails, `/api/health` still returns 503 from the in-process observation.

F12: one lock wait is not a page. The finding and the 503 start on the second observation. This is stricter than a single wait returning 503. The first 1205 is stored only as a count.

Close: the same observer takes that lock twice, and the second take is within `lock_wait` of the first. Another node does not count. A take after `lock_wait` restarts the count at one. The observer does not take the lock away from a holder who still has it.

N6: after the observer heartbeat is older than the effective `node_gone_after`, the `_health` holder closes the finding with the same two takes. `_cluster` reconcile does not close a finding it did not derive. `META_LOCK_STALLED` is not a managed kind.

The health transaction does not retry MySQL 1205. A 1205 is a lock-wait observation, including one from the `task_health` insert that runs before the applying transaction. It does not depend on `PROCESS`. The session deadline is a lock-wait observation only when it fires while that connection is waiting on `task_leases` or `task_health` (`performance_schema.data_lock_waits`, or `information_schema.innodb_trx` in state `LOCK WAIT`). Those views are not required for the 1205 path. When they are readable they add the blocking session's name. A slow statement is not a lock wait. A checkout that times out behind a confirmed lock wait is the same stall. A 1213 on the insert or on the applying transaction is retried once; a second 1213 waits for the next sweep.

## stale_after

Effective `stale_after` is `max(2×sweep + lock_wait, min(S, RTO))`. `S` is `5×sweep` when `health.stale_after_sec` is 0. Defaults are 125s, which is longer than one 60s sweep. It is not clamped below one sweep.

## Rollback

Roll back the binary. No migration ships with this change. `cluster.side_kill` may stay `off` in the config file; older binaries ignore the key only if they never load it, so remove the key before starting an older binary that rejects unknown keys. This tree accepts only `off` and `auto`.
