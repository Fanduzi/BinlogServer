# Binlog Server v0.5.56 中文发布说明

> 对应版本：`v0.5.56`

发布日期：2026-10-07

选定点停止时间之前，可以先读这条任务的保留链。`GET /api/tasks/{id}/window` 返回最早和最晚可恢复的 UTC 事件头时间。链上没有带时间的事件时，这两个字段是 JSON `null`。`continuous` 在 `breaks` 为空时为 true。`breaks` 始终是数组。MySQL 链里有 GTID 事件时，`gtid_set` 是这些已存事件的并集。MariaDB，以及链里没有 GTID 事件时，省略 `gtid_set`。不连续的集合用 go-mysql 的形式，例如 `<server_uuid>:30:32`。每一处缺口写出 `files` 和一句稳定的英文 `reason`：两段保留分段之间缺了源文件、校验和不匹配、配了对象存储时封存分段还不是机外副本（`UPLOAD_FAILED` 或 `LOCAL_ONLY`）、分段读不到，或 MySQL GTID 有洞。`GET /metrics` 增加 `binlog_server_recovery_breaks{task_id}` 和 `binlog_server_recovery_earliest_age_seconds{task_id}`。每次抓取都读这条链再算。Console 任务详情显示最早 → 最晚，链有缺口时给出警告，中文和英文都有。缺口句子保持 API 的英文。`smoke-recovery-window` 是可选场景，不在 quick profile 里。回放、保留和上传没有改。这条路由在嵌入的 Swagger 页上。Swagger 已重新生成。没有 schema 变更。schema 仍是 6。`minRequiredSchemaVersion` 仍是 6。ADR 0005 没有改。地板仍是 v0.5.51。没有新的配置项。BinlogServerQA 的 tip dogfood 在 `72d7d6b7bd9e8ed35d040e0e4ecca10e4fc00195` 上为 PASS（evidence-285）。这次没有新的问题。v0.5.55 的 `start_gtid_set` 规则仍成立（PR #282）。v0.5.54 的 `stop_gtid` 规则仍成立（PR #279）。v0.5.49 的封存位点规则（#189）仍成立。v0.5.48 不留下空 `task-<id>.binlog` 的规则（#205）仍成立。v0.5.52 清理 `.takeover-*` 的规则仍成立（#224，PR #273）。v0.5.53 丢掉 `uk_task_file_epoch` 的规则仍成立（PR #276）。可恢复窗口在 PR #285 落地。

## 核心变化

- 选定点之前先读保留链。`GET /api/tasks/{id}/window` 只读。已发布的 v0.5.55 包没有这条路由。回放、保留和上传没有改。这次请求读分段字节。不新增列。没有查询参数。
- JSON 含 `continuous`、`earliest`、`latest` 和 `breaks`。`earliest` 和 `latest` 是 UTC 事件头时间。链上没有带时间的事件时，各自是 JSON `null`。`breaks` 始终是数组，链连续时也是。空链是连续的：`continuous` 为 true，两个时间都是 `null`，`breaks` 是 `[]`。任务不存在是 HTTP 404 `task not found`。清单里的分段、字节不在本进程上，是一处缺口。选中的分段因其他原因读失败，是 HTTP 500。
- 这条链就是回放清单：全部分封存分段，再加上每个源序号 epoch 最大的 open。本地文件优先。本地没有时，只读封存且 `UPLOADED`、`object_key` 非空的对象。只存在于桶里的封存对象仍在窗口里。目录里的 `file_path` 不会被打开。窗口和这两个指标在响应这次请求的进程上计算。
- 每一处缺口都有 `files` 和 `reason`。`reason` 是稳定的英文句子。源序号跳号是 `missing source file <names> between <left> and <right>`。左右邻居前缀相同、序号宽度也相同（含前导 0）时，`<names>` 是缺掉的源文件，例如 `mysql-bin.000002`。`files` 先列出这些缺掉的名字，再是左邻居，再是右邻居。名字不是这个形状时，句子用 `index <n>` 表示第一个缺掉的序号。封存分段的 `checksum` 是 `mismatch` 时，句子是 `checksum mismatch`。`files` 是该分段的 basename。校验和不匹配不会再报成「不是机外副本」。配了对象存储时，封存分段的 `upload_state` 是 `UPLOAD_FAILED` 或 `LOCAL_ONLY`，并且校验和不是 `mismatch`，句子是 `segment is not durable off-host (UPLOAD_FAILED)` 或 `segment is not durable off-host (LOCAL_ONLY)`。open 分段不是这种缺口，包括 `upload_state` 为 `LOCAL_ONLY` 的 open 文件。没有配对象存储时，`LOCAL_ONLY` 不是这种缺口。字节不在本进程上是 `segment is not readable`。`source.flavor` 为 `mysql` 时，两段保留分段之间的 GTID 洞是 `gtid hole between <left> and <right>`。`files` 是这两个源文件名。MariaDB 不增加这种缺口。
- 只有 `source.flavor` 为 `mysql`、并且链里有 `GTID_EVENT` 时才有 `gtid_set`。它是这些已存事件的并集。previous-GTIDs 头里只点到、分段里没有存下的旧事务不算进这个集合。连续的一段是 `<server_uuid>:1-3`。同一个 UUID 里面有洞时，用 go-mysql 的形式 `<server_uuid>:30:32`。多个 UUID 用逗号分开。MariaDB 省略这个字段。链里没有 GTID 事件时也省略。省略是 JSON 里没有这个键。它不是 JSON `null`。
- 任务从源文件中部接入时，仍保留该文件的 previous-GTIDs 头。这个头和第一件已存事件之间的序号在链之前。它们不是 GTID 洞，也不进 `gtid_set`。洞是上一分段最后一件已存事件之后、下一分段之前提交的事务。下一分段带 previous-GTIDs 时，这个集合必须包含上一分段存下的每一件事件，并且不能已经包含下一序号。下一分段没有 previous-GTIDs 时，同一 UUID 上序号跳过超过 1 就是洞。MySQL 上缺一个文件可以同时是「缺源文件」和「GTID 洞」两处缺口。`binlog_server_recovery_breaks` 两处都计。
- 连续链上，`latest` 之后一秒的 `stop_datetime` 仍返回回放命令。停在 `earliest`，以及停在它之前，仍是 HTTP 200 和空命令，因为 `stop_datetime` 不含时间戳大于等于停止时间的事件。缺口不改变 `paths`。回放仍返回打得开的分段。不会把缺掉的名字补回去。
- `GET /metrics` 暴露 `binlog_server_recovery_breaks{task_id}` 和 `binlog_server_recovery_earliest_age_seconds{task_id}`。每次抓取都做同一次窗口读取，读保留分段。不沿用上一次的答案。缺口指标是 `breaks` 的个数。年龄指标是从 `earliest` 到这次抓取的秒数。负的年龄记为 0。`earliest` 为 JSON `null` 的任务没有年龄序列。某个任务的窗口读取失败时，跳过该任务。没有任务发出序列时，指标是 0，`task_id` 为空。
- Console 任务详情在文件与上传一节显示这段窗口。英文标签是 `Recoverable window`。标记是 `Continuous` 或 `Broken`。警告标题是 `This backup chain has a break`。还没有跨度时是 `No restorable events yet.`。中文标签是「可恢复窗口」。标记是「连续」或「有缺口」。警告标题是「这条备份链有缺口」。还没有跨度时是「还没有可恢复的事件。」。范围是最早 → 最晚，`T` 写成空格，`Z` 写成 ` UTC`。每一行缺口是用逗号连起来的 `files`，后面是 API 的 `reason`。中文页面上这句仍是英文。有 `gtid_set` 时，英文行是 `GTID covered`，中文行是「覆盖的 GTID」。这个 Console 在普通 `go build` 打进去的嵌入包里。
- `smoke-recovery-window` 是可选场景：`./scripts/e2e/run-suite.sh --scenarios smoke-recovery-window`。不在 quick profile 里，也不在 full profile 里。MySQL 8.0 上 GTID 打开。建库建表后，任务从当时的 `GTID_EXECUTED` 启动，插入三行，每次插入后 `FLUSH BINARY LOGS`，然后停任务。窗口是连续的。`earliest`、`latest`、`gtid_set` 都有。`breaks` 为空。`latest` 之后一秒的 `stop_datetime` 得到非空回放命令。`earliest` 之前一秒是空命令。然后删掉中间一条封存分段的本地文件和 `binlog_files` 行。窗口不再连续。`reason` 含 `missing source file`。`binlog_server_recovery_breaks{task_id}` 至少为 1，并且仍有 `binlog_server_recovery_earliest_age_seconds`。同一较晚停止时间的回放路径不再包含被删的文件名。场景里关掉 `binlog_transaction_compression`，结束时恢复为 ON。不使用 MinIO。
- 没有新的配置项。没有 schema 迁移。`minRequiredSchemaVersion` 仍是 6。`migrations/` 仍是 `000001` 到 `000006`。没有 `000007`。ADR 0005 没有改。第 1 到第 9 步已经发出。第 9 步在 v0.5.53 发出。这一版不是新的 ADR 步骤。

## 升级影响

没有新迁移。已经在 v0.5.55 / schema 6 上的库仍是 schema 6。确认 `SELECT version, dirty FROM schema_migrations` 是 `(6, 0)`。`migrations/` 仍是 `000001`、`000002`、`000003`、`000004`、`000005` 和 `000006`。没有 `000007`。

`minRequiredSchemaVersion` 仍是 6。v0.5.56 在 schema 5 上不会启动，以退出码 1 结束，还没开始监听。提示含 `schema version too old` 和 `./migrate up`。这与 v0.5.55 的拒绝相同。schema 4 和 schema 3 同样拒绝启动。

schema 6 已经就位之后再换二进制。库已经是 v0.5.55 / schema 6 时，没有 `./migrate` 这一步。还不是 schema 6 时，先按 [v0.5.55 中文发布说明](v0.5.55.zh-CN.md)，确认 `(6, 0)`，再启动 v0.5.56。

地板仍是 v0.5.51，它是第一版同时带上 ADR 0005 第 6 步和第 7 步的发布。v0.5.50 只发了第 6 步。`./migrate up` 到 schema 6 之前，先停掉仍要求 `uk_task_file_epoch` 的每一台进程。v0.5.51 和 v0.5.52 就是这些二进制。schema 6 上它们拒绝启动。日志含 `missing index` 和 `uk_task_file_epoch`。比 v0.5.51 旧的进程，包括 v0.5.50，都不是地板。`000006` 之前先换掉。然后停掉 v0.5.51 和 v0.5.52。然后执行 `./migrate up`。

schema 4（`000004_pending_dump_cleanup`）仍在迁移链上。v0.5.50 之前，schema 4 是单进程可选、集群必须。分步升级、启动的仍是比 v0.5.50 旧的二进制时，这条规则还适用。v0.5.56 自己不能停在 schema 4。

如果这套库还不是 schema 3，先按 [v0.5.46 中文发布说明](v0.5.46.zh-CN.md)，再按 v0.5.50，再按 v0.5.53。schema 2 到 schema 3（`000003_task_desired_and_retry_budget`）在线。schema 1 到 schema 2 仍按 [v0.5.34 升级说明](v0.5.34.zh-CN.md)：停掉每一台进程，执行 `./migrate up`，然后只启动 v0.5.34 或更新的二进制。

没有新的配置项。没有元数据库的 standalone 不跑这些迁移。窗口读的是本进程打得开的分段，所以 standalone 上是同一个响应。`start_gtid_set` 仍读本进程打得开的分段。

不要 `./migrate down` 退过正在跑的二进制所需要的 schema。v0.5.56 需要 schema 6。这一版没有新迁移，所以没有新的 down 步骤。schema 6 上 `./migrate down --steps 1` 仍是 v0.5.53 的那次 down：把 `uk_task_file_epoch` 加回来。不删行。不删 `file_name`。不删 `uk_task_source_epoch`。回到 version 5。`binlog_files` 行数不变。已经有两行共用 `(task_id, file_name, epoch)` 时，这次 down 会失败。不要为了让它通过而删行。写入方保持 `file_name` 等于 `source_file`。v0.5.56 还在跑时不要做这次 down。v0.5.56 在 schema 5 上不会启动。生产环境的 `./migrate down` 仍要 `ALLOW_DESTRUCTIVE_MIGRATE=1` 才放行。

v0.5.53 的索引规则仍成立。`SHOW INDEX FROM binlog_files` 列出 `uk_task_source_epoch`，不列出 `uk_task_file_epoch`。`file_name` 列还在。再插入相同的 `(task_id, source_file, epoch)` 会失败。重复键是 `uk_task_source_epoch`。

v0.5.52 清理 `.takeover-*` 的规则仍成立。worker 仍会删掉任务目录里留下的普通 `.takeover-*`。v0.5.51 的未知 `end_pos` 规则仍成立。本进程读不到本地字节时，`GET /api/tasks/{id}/files` 的未知 `end_pos` 是 JSON `null`，Console 单元格是空白。本地文件能读到事件时，给出事件跨度。

v0.5.55 的 `start_gtid_set` 规则仍成立。v0.5.54 的 `stop_gtid` 规则仍成立。v0.5.49 的封存位点规则（#189）和 v0.5.48 的空 `task-<id>.binlog` 规则（#205）仍成立。`stop_datetime` 没有改。时间戳大于等于停止时间的事件仍不进入那条命令。回放、保留和上传没有改。BinlogServerQA 的 tip dogfood 在 `72d7d6b7` 上为 PASS。

这一版不是 ADR 0005 的步骤。第 1 到第 9 步已经发出。ADR 0005 没有改。发出第 9 步的是 v0.5.53。

## 已知行为

#224 已在 v0.5.52 修好。#189 已在 v0.5.49 修好。#205 已在 v0.5.48 修好。`stop_gtid` 在 v0.5.54 发出。`start_gtid_set` 在 v0.5.55 发出。这一版没有再改这些修复。这一版不是 ADR 0005 的步骤。ADR 0005 没有改。

- `stop_datetime` 仍按事件头的秒切开。同一秒里的事务在时间路径上仍是一起进或一起出。已经知道坏 GTID 时用 `stop_gtid`。`start_gtid_set` 不改变这个停止点。窗口也不改变这个停止点。
- 盖不住要应用的第一段之前那些事务的集合会被拒绝。回放不会跳过这个缺口。
- 窗口里的缺口不改变回放、保留和上传。回放仍返回打得开的分段。不会把缺掉的源文件补回 `paths`。
- 任务从源文件中部接入不是 GTID 洞。第一件已存事件之前的序号不进 `gtid_set`。
- schema 仍是 6。地板仍是 v0.5.51。没有 `000007`。`file_name` 仍是一列。
