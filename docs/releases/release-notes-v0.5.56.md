# Binlog Server v0.5.56

Release date: 2026-10-07

A task's retained chain can be read before a point-in-time stop is chosen. `GET /api/tasks/{id}/window` returns the earliest and latest restorable UTC event-header times. Each time is JSON `null` when the chain has no timed event. `continuous` is true when `breaks` is empty. `breaks` is always an array. For a MySQL chain that contains GTID events, `gtid_set` is the union of those stored events. It is omitted for MariaDB and when the chain has no GTID event. A non-contiguous set uses the go-mysql form, such as `<server_uuid>:30:32`. A break names `files` and a stable English `reason`: a missing source file between retained segments, checksum mismatch, a sealed segment that is not durable off-host when object storage is configured (`UPLOAD_FAILED` or `LOCAL_ONLY`), a segment that is not readable, or a MySQL GTID hole. `GET /metrics` adds `binlog_server_recovery_breaks{task_id}` and `binlog_server_recovery_earliest_age_seconds{task_id}`. Each scrape computes them by reading the chain. Console task detail shows earliest → latest, and a warning when the chain is broken, in zh-CN and en. The break sentences stay the API English. `smoke-recovery-window` is opt-in and is not in the quick profile. Replay, retention, and upload are unchanged. The route is on the embedded Swagger page. Swagger was regenerated. No schema change. Schema stays 6. `minRequiredSchemaVersion` stays 6. ADR 0005 is unchanged. The floor stays v0.5.51. No new config key. Tip dogfood by BinlogServerQA passed on `72d7d6b7bd9e8ed35d040e0e4ecca10e4fc00195` (evidence-285). That run did not open a new issue. The v0.5.55 `start_gtid_set` rule still holds (PR #282). The v0.5.54 `stop_gtid` rule still holds (PR #279). The v0.5.49 sealed-position rule (#189) still holds. The v0.5.48 empty `task-<id>.binlog` rule (#205) still holds. The v0.5.52 `.takeover-*` cleanup still holds (#224, PR #273). The v0.5.53 drop of `uk_task_file_epoch` still holds (PR #276). The recoverable window landed in PR #285.

## Highlights

- Read the retained chain before you pick a stop. `GET /api/tasks/{id}/window` is read-only. The published v0.5.55 package has no such route. Replay, retention, and upload are unchanged. The request reads segment bytes. It does not add a column. It does not take a query parameter.
- The JSON object has `continuous`, `earliest`, `latest`, and `breaks`. `earliest` and `latest` are UTC event-header times. When the chain has no timed event, each is JSON `null`. `breaks` is always an array, including when the chain is continuous. An empty chain is continuous: `continuous` is true, both times are `null`, and `breaks` is `[]`. A missing task is HTTP 404 `task not found`. A segment in the inventory whose bytes are not on this process is a break. Any other failure to read a selected segment is HTTP 500.
- The chain is the replay inventory: every sealed segment, plus the highest open epoch of each source index. A local file wins. A missing local file is read only for a sealed `UPLOADED` row with a non-empty `object_key`. A sealed object that exists only in the bucket stays in the window. Catalog `file_path` is not opened. The window and the gauges run on the process that serves the request.
- Each break has `files` and `reason`. `reason` is a stable English sentence. A skipped source index is `missing source file <names> between <left> and <right>`. When the two neighbors share a prefix and the same zero-padded width, `<names>` is the missing source file, such as `mysql-bin.000002`. `files` lists those missing names, then the left neighbor, then the right neighbor. When the names do not share that shape, the sentence uses `index <n>` for the first missing index. A sealed segment whose `checksum` is `mismatch` is `checksum mismatch`. `files` is that segment's basename. A checksum mismatch is not also reported as not durable. When object storage is configured, a sealed segment whose `upload_state` is `UPLOAD_FAILED` or `LOCAL_ONLY`, and whose checksum is not `mismatch`, is `segment is not durable off-host (UPLOAD_FAILED)` or `segment is not durable off-host (LOCAL_ONLY)`. An open segment is not this break, including an open file whose `upload_state` is `LOCAL_ONLY`. With no object storage configured, `LOCAL_ONLY` is not this break. A segment whose bytes are not on this process is `segment is not readable`. On `source.flavor` `mysql`, a GTID hole between two retained segments is `gtid hole between <left> and <right>`. `files` is those two source names. MariaDB does not add this break.
- `gtid_set` is present only when `source.flavor` is `mysql` and the chain contains a `GTID_EVENT`. It is the union of those stored events. A previous-GTIDs header that only names older transactions is not part of the set. A contiguous run is `<server_uuid>:1-3`. A gap inside one UUID uses the go-mysql form `<server_uuid>:30:32`. Several UUIDs are separated by a comma. The field is omitted for MariaDB. It is omitted when the chain has no GTID event. An omitted `gtid_set` is absent from the JSON. It is not JSON `null`.
- A task that joins a source file in the middle keeps that file's previous-GTIDs header. Sequences between that header and the first stored event are before the chain. They are not a GTID hole, and they are not in `gtid_set`. A hole is a transaction after the last event stored in one segment and before the next. When the next segment has previous-GTIDs, that set must contain every event the previous segment stored, and must not already contain the next sequence. When it has no previous-GTIDs, a jump of more than one sequence on the same UUID is a hole. One missing MySQL file can be both a missing-source-file break and a GTID-hole break. `binlog_server_recovery_breaks` counts both.
- On a continuous chain, `stop_datetime` one second after `latest` still returns a replay command. A stop at `earliest`, and a stop before it, is still HTTP 200 with an empty command, because `stop_datetime` leaves out an event whose timestamp is greater than or equal to the stop. A break does not change `paths`. Replay still returns the segments it can open. It does not put the missing name back.
- `GET /metrics` exposes `binlog_server_recovery_breaks{task_id}` and `binlog_server_recovery_earliest_age_seconds{task_id}`. Each scrape calls the same window read and reads the retained segments. It does not reuse a previous answer. The breaks gauge is the number of `breaks`. The age gauge is the seconds from `earliest` to the scrape time. A negative age is 0. A task with JSON `null` for `earliest` does not get an age series. A window error for one task skips that task. When no task emits a series, the gauge is 0 and `task_id` is empty.
- Console task detail, under files and upload, shows the span. The English label is `Recoverable window`. The tag is `Continuous` or `Broken`. The warning title is `This backup chain has a break`. An empty span is `No restorable events yet.` The Chinese label is「可恢复窗口」. The tag is「连续」or「有缺口」. The warning title is「这条备份链有缺口」. An empty span is「还没有可恢复的事件。」. The range is earliest → latest, with `T` written as a space and `Z` written as ` UTC`. Each break line is the `files` joined by commas, then the API `reason`. That sentence stays English on the Chinese page. When `gtid_set` is present, the English line is `GTID covered` and the Chinese line is「覆盖的 GTID」. That Console is in the embedded bundle a plain `go build` serves.
- `smoke-recovery-window` is opt-in: `./scripts/e2e/run-suite.sh --scenarios smoke-recovery-window`. It is not in the quick profile and not in the full profile. On MySQL 8.0 with GTID on, it creates a database and a table, starts the task from that `GTID_EXECUTED`, inserts three rows with `FLUSH BINARY LOGS` after each insert, and stops the task. The window is continuous. `earliest`, `latest`, and `gtid_set` are set. `breaks` is empty. `stop_datetime` one second after `latest` returns a non-empty replay command. One second before `earliest` returns an empty command. It then deletes the middle sealed segment's local file and its `binlog_files` row. The window is no longer continuous. `reason` contains `missing source file`. `binlog_server_recovery_breaks{task_id}` is at least 1, and `binlog_server_recovery_earliest_age_seconds` is still present. The same later stop no longer lists the deleted name. The scenario turns `binlog_transaction_compression` off and restores it to ON. It does not use MinIO.
- No new config key. No schema migration. `minRequiredSchemaVersion` stays 6. `migrations/` is still `000001` through `000006`. There is no `000007`. ADR 0005 is unchanged. Steps 1–9 already shipped. Step 9 shipped in v0.5.53. This release is not a new ADR step.

## Upgrade Notes

No new migration. A database already on schema 6 from v0.5.55 stays on schema 6. Confirm `SELECT version, dirty FROM schema_migrations` is `(6, 0)`. `migrations/` is still `000001`, `000002`, `000003`, `000004`, `000005`, and `000006`. There is no `000007`.

`minRequiredSchemaVersion` remains 6. v0.5.56 does not start on schema 5. It exits with code 1 before it listens. The message contains `schema version too old` and `./migrate up`. That is the same refusal as v0.5.55. Schema 4 and schema 3 exit the same way.

Replace the binary after schema 6 is already in place. If the database is already v0.5.55 / schema 6, there is no `./migrate` step. If it is not schema 6 yet, follow the [v0.5.55 upgrade](release-notes-v0.5.55.md) first and confirm `(6, 0)`, then start v0.5.56.

The floor stays v0.5.51, the first release that ships both ADR 0005 step 6 and step 7. v0.5.50 shipped step 6 only. Stop every process that still requires `uk_task_file_epoch` before `./migrate up` to schema 6. v0.5.51 and v0.5.52 are those binaries. On schema 6 they refuse to start. The log contains `missing index` and `uk_task_file_epoch`. A process older than v0.5.51, including v0.5.50, is not the floor. Replace it before `000006`. Then stop v0.5.51 and v0.5.52. Then run `./migrate up`.

Schema 4 (`000004_pending_dump_cleanup`) is still in the chain. Before v0.5.50, schema 4 was optional for one process and required for cluster mode. That rule still applies when you upgrade stepwise and the binary you start is older than v0.5.50. v0.5.56 does not start on schema 4.

If this database is not already schema 3, follow the [v0.5.46 upgrade](release-notes-v0.5.46.md), then the v0.5.50 upgrade, then the v0.5.53 upgrade. Schema 2 to schema 3 (`000003_task_desired_and_retry_budget`) is online. Schema 1 to schema 2 still follows the [v0.5.34 upgrade](release-notes-v0.5.34.md): stop every binlog-server on that database, run `./migrate up`, then start only v0.5.34 or newer.

No new config key. Standalone with no metadata database does not run these migrations. The window reads the segments this process can open, so standalone has the same response. `start_gtid_set` still reads the segments this process can open.

Do not run `./migrate down` past the schema the running binaries need. v0.5.56 needs schema 6. This release adds no migration, so there is no new down step. `./migrate down --steps 1` from schema 6 is still the v0.5.53 down: it adds `uk_task_file_epoch` back. It does not delete rows. It does not drop `file_name`. It does not drop `uk_task_source_epoch`. It returns to version 5. The `binlog_files` row count is unchanged. If two rows already share `(task_id, file_name, epoch)`, that down fails. Do not delete rows to make it pass. The writer keeps `file_name` equal to `source_file`. Do not run that down while v0.5.56 is running. v0.5.56 does not start on schema 5. Production `./migrate down` stays blocked unless `ALLOW_DESTRUCTIVE_MIGRATE=1`.

The v0.5.53 index rule still holds. `SHOW INDEX FROM binlog_files` lists `uk_task_source_epoch` and does not list `uk_task_file_epoch`. The `file_name` column stays. A second insert of the same `(task_id, source_file, epoch)` fails. The duplicate key is `uk_task_source_epoch`.

The v0.5.52 `.takeover-*` cleanup still holds. A worker still removes a regular `.takeover-*` left in a task directory. The v0.5.51 unknown-`end_pos` rule still holds. Unknown `end_pos` is JSON `null` on `GET /api/tasks/{id}/files`, and the Console cell is blank, when this process cannot read the local bytes. A readable local file shows the event span.

The v0.5.55 `start_gtid_set` rule still holds. The v0.5.54 `stop_gtid` rule still holds. The v0.5.49 sealed-position rule (#189) and the v0.5.48 empty `task-<id>.binlog` rule (#205) still hold. `stop_datetime` is unchanged. It still leaves out an event whose timestamp is greater than or equal to the stop. Replay, retention, and upload are unchanged. Tip dogfood by BinlogServerQA passed on `72d7d6b7`.

This release is not an ADR 0005 step. Steps 1–9 already shipped. ADR 0005 is unchanged. v0.5.53 is the release that shipped step 9.

## Known behavior

#224 was fixed in v0.5.52. #189 was fixed in v0.5.49. #205 was fixed in v0.5.48. `stop_gtid` shipped in v0.5.54. `start_gtid_set` shipped in v0.5.55. This release does not change those earlier fixes. This release is not an ADR 0005 step. ADR 0005 is unchanged.

- `stop_datetime` still cuts on the event-header second. Transactions that share that second are still all in or all out on the datetime path. Use `stop_gtid` when the bad GTID is known. `start_gtid_set` does not change that stop. The window does not change that stop.
- A set that does not cover the transactions before the first segment that would be applied is refused. The replay does not skip that hole.
- A break in the window does not change replay, retention, or upload. Replay still returns the segments it can open. It does not put a missing source file back into `paths`.
- A task that joins a source file in the middle is not a GTID hole. Sequences before the first stored event stay out of `gtid_set`.
- Schema stays 6. The floor stays v0.5.51. There is no `000007`. `file_name` stays a column.
