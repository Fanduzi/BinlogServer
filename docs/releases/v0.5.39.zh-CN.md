# Binlog Server v0.5.39 中文发布说明

> 对应版本：`v0.5.39`

发布日期：2026-10-06

拉流已经打开时源库宕机，任务以前一直显示 `RUNNING`。租约继续续。dump 库日志是 `retry sync err, wait 1s`。调度器看不到这个错误，任务不进 `RETRY_BACKOFF`，也不累计 `SOURCE_UNREACHABLE`。大约 5 次重连、每次大约 1 秒之后，`GET /api/tasks/{id}` 和 Console 显示 `RETRY_BACKOFF`。`last_error` 以 `SOURCE_UNREACHABLE:` 开头。每一次这样的失败都计入和首次连接失败相同的十次上限。没有元数据库的 standalone，第十次连续失败进入 `FAILED`，租约放开。一体进程和集群上，认领循环大约每 2 秒会再次启动自己名下的 `RETRY_BACKOFF` 任务，并把失败计数清掉，所以任务到不了 `FAILED`。短暂闪断仍保持 `RUNNING`，`last_error` 不变。源库重新接受连接后，任务回到 `RUNNING`，从 checkpoint 续上。`LATEST` 任务已经连上、但还没写入任何事件时，以前会在这次宕机之后重新解析 `LATEST`，宕机期间已经提交的事务不会进备份。现在第一次解析出的文件和位点会存成 checkpoint，`gtid_set` 为空，重试不再从新的尖端开始。源库重启后 MySQL 送来的人工 Rotate，`end_log_pos` 为 0，不再写入本地 binlog。持久续传会忽略末尾这条位点为 0 的事件，一体进程在源库重启之后不再停在 `FAILED`，`last_error` 以 `SEGMENT_NOT_ON_WORKER` 开头。跟踪为 #204（PR #212）、#213（PR #215）、#214（PR #216）。QA 在 `3460c45` 上 dogfood 通过。

## 核心变化

- dump 库对已经打开的连接最多重连 5 次，大约每秒一次。这 5 次之内源库恢复，任务保持 `RUNNING`。`last_error` 不变。
- 这之后源库仍不可达，`GET /api/tasks/{id}` 和 Console 显示 `RETRY_BACKOFF`。`last_error` 以 `SOURCE_UNREACHABLE:` 开头（例如 `SOURCE_UNREACHABLE: dial tcp ... connection refused`）。每一次失败都计入和首次连接失败相同的十次 `SOURCE_UNREACHABLE` 上限。
- 没有元数据库的 standalone，第十次连续失败进入 `FAILED`，租约放开。一体进程和集群上，认领循环大约每 2 秒会再次启动自己名下的 `RETRY_BACKOFF` 任务，并把失败计数清掉，所以任务到不了 `FAILED`。这一点没有改。跟踪为 #203。
- 源库重新接受连接后，任务回到 `RUNNING`，从 checkpoint 续上。checkpoint 的文件和位点与 `SHOW MASTER STATUS` 对齐。
- `LATEST` 第一次解析出文件和位点时，拉流之前就把它们存成 checkpoint。`gtid_set` 为空。`GET /api/tasks/{id}/checkpoint` 返回这个文件和位点。任务行仍显示 `start.mode=LATEST`。
- 进入 `RETRY_BACKOFF` 之后，下一轮从该文件和位点继续，已经写过事件时从最后一条已复制事件继续。不再重新解析 `LATEST`，也不从新的 `SHOW MASTER STATUS` 开始。宕机期间已经提交的事务会拉下来。本来就有 checkpoint 的任务不变。`GTID` 的 checkpoint 仍在每次落盘时保留并扩展 `gtid_set`。`LATEST` 的 checkpoint 仍没有 `gtid_set`。没有元数据库时，本进程为这次重试留着同一个文件和位点。
- 源库重启后重连时，MySQL 送来的人工 Rotate 的 `end_log_pos` 为 0。这条事件不在源 binlog 里，它指向下一个文件。它不写入本地分段。当前文件按最后一个真实事件封口，拉流从下一个文件继续。
- 本地分段末尾已经有这条 Rotate 时，续传用最后一个 `end_log_pos` 不为 0 的事件。下次打开这个分段时丢掉多出来的字节。目录里的 `file_path` 仍指向本机这个文件，这个文件不会被当成缺失。已经因此 `FAILED`、`last_error` 以 `SEGMENT_NOT_ON_WORKER` 开头的任务，从那个事件再启动。`POST /api/tasks/{id}/start`。不用先手工截断。
- `mysqlbinlog --verify-binlog-checksum` 仍能读本地文件。解码结果里没有 `end_log_pos` 为 0 的 Rotate。

## 升级影响

二进制从 v0.5.38 滚动升级即可。这一版没有 schema migration。元数据 schema 仍是 v0.5.34 引入的版本 2。`schema_migrations` 已经是版本 2 时，不用执行 `./migrate up`。

还在 schema 1 上的库，要先迁移，这个二进制才会启动。按 [v0.5.34 升级说明](v0.5.34.zh-CN.md)：停掉这个元数据库上的每一台 binlog-server，执行 `./migrate up`，然后只启动 v0.5.34 或更新的二进制。

没有新的配置项。

已经因为 open 分段末尾是 `end_log_pos` 为 0 的人工 Rotate 而 `FAILED`、`last_error` 以 `SEGMENT_NOT_ON_WORKER` 开头的任务，用 `POST /api/tasks/{id}/start` 再启动。Start 从最后一个位点不为 0 的事件继续，并丢掉多出来的字节。不用先手工截断。

## 已知行为

下面这些在这一版之前就有。QA 在 `3460c45` 上 dogfood 通过。这一版没有改它们。

- 一体进程和集群上，认领循环大约每 2 秒会再次启动自己名下的 `RETRY_BACKOFF` 任务，并把失败计数清掉，所以任务到不了 `FAILED`。没有元数据库的 standalone 仍会在连续十次失败后进入 `FAILED`。`last_error` 以 `SOURCE_UNREACHABLE:` 开头。拉流已经打开时源库宕机，现在也计入同一份预算。认领循环仍会把计数清掉。跟踪为 #203。
- 同一进程上每个任务的 Stop、Start、租约续约和进度更新，跟事件读取、事件写入共用一把锁。一次慢的元数据写入，或 Console 在读事件，会把其它任务的这些操作挡住。打开下一个 binlog 时，在拉流路径上读该任务的整份文件目录。接管一个很大的已上传分段时，会把整个对象读进这个 worker 的内存。跟踪为 #177。
- 故障切换之后，后一次封存的分段，例如 `mysql-bin.NNNNNN.sealed.e1`，`end_pos` 可能是 0。`size_bytes` 是文件大小。这一行仍可以是 `UPLOADED`，checksum 为 `match`。文件列表里仍有这一段，下载和回放仍能返回它。这是 v0.5.34、v0.5.35、v0.5.36、v0.5.37 和 v0.5.38 已经记下的行为。跟踪为 #189。
- 停止过程中改了源库密码，然后再 Start，源库上可能短暂出现两条 Binlog Dump。之后再一次停到 `STOPPED`，仍可能留下一条 Binlog Dump，需要在源库上手动 `KILL`。控制面上一次普通停止，以及一体进程上的停止，源库进程列表里不再有该任务的 Binlog Dump。这是 v0.5.35、v0.5.36、v0.5.37 和 v0.5.38 已经记下的行为。跟踪为 #193。
- GTID 模式启动，以及文件位点续传在 MySQL 1236 之后打开 `StartSyncGTID`，会写入一条没有 CRC 的人工 Rotate。`mysqlbinlog --verify-binlog-checksum` 在这条事件上报 `Event crc check failed!`。不加这个参数时文件可以读完。已经复制的事件本身是完整的。GTID 启动还会留下一个多余的 `task-N.binlog`。目录把它记成 `SEALED` 并上传。跟踪为 #205。
- 没有配置上传时，按天数清理会删掉本地封存文件，目录行仍是 `SEALED` / `LOCAL_ONLY`，`file_path` 还是旧路径。`GET /api/tasks/{id}/files` 仍列出这个名字，响应里没有 `location`。`GET /api/tasks/{id}/files/{name}` 返回 404。文件列表和磁盘对不上。这是在 `4477d19e` 的 dogfood 上看到的。这一版的保留代码和之前一样。跟踪为 #209。
