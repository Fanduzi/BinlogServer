# Binlog Server v0.5.59 中文发布说明

> 对应版本：`v0.5.59`

发布日期：2026-10-09

v0.5.59 把回切（A→B→A）当作正式的源链处理，并修复或拒绝 v0.5.57 和未发布的 main 0a84917a 在真实回切后写下的任务目录（PR #297）。一台服务器的第 n 段现在写成 `{身份}~{n}.{binlog 文件名}`，A 回切后的文件不会再沿用 A 切走前的名字。升级后，早期版本的回切目录会带上 `storage_alert`，`/replay` 和 `/window` 停在第一份有问题的文件之前。第一次 Start 能证明每份文件只属于一段时就修复，否则拒绝，什么都不改。第一段的文件只剩对象存储里的一份时，Start 先取回并核对，再修复。换过服务器之后出现的“已存 GTID 洞”现在会触发 `storage_alert` 并截断 `/replay` 和 `/window`，恢复不会再越过缺口还返回 rc 0。`/window`、`source_chain.outcome` 和 `binlog_server_source_switchovers` 不再报假的洞，也不再把任务已经跑过去的停止算成仍在停止。dump 中途因换源停下的任务可以再次启动。没有新配置项。没有 schema 迁移。schema 仍是 6。`minRequiredSchemaVersion` 仍是 6。地板仍是 v0.5.51。BinlogServerQA 对 `53db97574b8e77a519639df20b26978b00c84744`（evidence-297）的 tip dogfood 通过，没有 P0、P1、P2。三个 P3 列在「已知行为」里。

## 核心变化

- **回切分段（PR #297，#292 QA P1）。** `.source-chain` 每一行是一段：A→B→A 是三行。之前出现过的服务器的第 n 段写成 `{身份}~{n}.{binlog 文件名}`（第三段是 `A~2.`）。`source_chain.servers[]` 增加 `prefix`，`current` 是正在写的服务器，`/replay` 的顺序是 A、B、`A~2`，在 A 上重启不会再记一条假的 B→A 切换。`GET /api/tasks/{id}/files` 增加可选的 `source_server`（从 1 开始的段号）。切换事件的 `file` 是不带磁盘前缀的源 binlog 名。
- **早期版本的回切目录：修复或拒绝（QA 6c88ad5b P1）。** v0.5.57 和 0a84917a 把 A 第三段的文件写在 A 第一段的名字下，目录行也改指到后一份文件，于是 `/files` 和 `/replay` 静默漏掉第一段那份文件（恢复报 ERROR 1032 或少行），Start 还会写出同名的第三份。现在读接口给出 `storage_alert`（`STORAGE_INCONSISTENT`，`detail` 为 `legacy failback: <文件>`），`/replay` 和 `/window` 停在第一份有问题的文件之前。Start 按每次切换记下的 GTID 集合核对每份文件。具体处理见「升级影响」。
- **第一段的文件只剩对象（QA bbc2c88b P2）。** `detail` 增加 `not on disk: <文件>`。Start 从 `{prefix}/{cluster}/{身份}/<文件>` 取回，核对其中的事务属于这一段，然后才修复。对象不存在、事务不对，或没有配对象存储时，Start 拒绝，什么都不改。之前 Start 会改名，`/window` 显示 `continuous: true`，恢复返回 rc 0，却少了第一段最后的事务。
- **已存 GTID 洞的安全网。** 换过服务器的任务，如果某次继续复制的切换记成“已存下”的事务，在任何本地分段里都没有，并且夹在已存事务中间，就会给出 `storage_alert`（`detail` 为 `stored gtid hole: ...`，带 `missing_gtids`）。`/replay` 和 `/window` 停在它后面的第一个分段之前。同一个源的已存 GTID 中间有起点集合没覆盖的缺口时，`/window` 不会是 `continuous`。
- **补传等修复完成。** 后台补传不会在修复之前按旧的（错误服务器的）对象键上传早期版本的目录行，所以拒绝时目录和对象存储都不变。
- **`/window` 不再报假洞。** 起点集合覆盖了第一份文件里的事务时（mysqldump 种子），回切边界不再报 `gtid hole`；下一台服务器第一份文件的文件头缺少上一台已经存下的事务时，也不再报。真正的洞照样报。
- **切换结果和指标。** 对停在换源上的任务再次 Start 不会再加一次切换。任务重新运行（VIP 指回）后，`source_chain.outcome` 是 `resumed`，那次停止带 `resolved: true`，Console 不再显示停止横幅，`binlog_server_source_switchovers{outcome="stopped"}` 回到 0。停止之后只要有过 `TASK_RUNNING` 事件，普通 Stop 或进程重启都不会把它变回“停止”。
- **dump 中途换源停下后可以再启动。** 之前停止时封存了 open 分段，checkpoint 却还指向它，之后每次 Start 都以 `SEGMENT_NOT_ON_WORKER` 失败。现在 open 分段保持打开。之后的 Start 在另一台服务器上继续时，先把上一台的 open 分段按上一台封存；之前连接时发现的切换会留下这个 open 分段，新 epoch 的清理再把它删掉，丢了上一台最后的事务。
- **测试。** `smoke-source-switchover` 覆盖 A→B→A 回切。`scripts/e2e/upgrade-legacy-failback.sh` 用真实的 v0.5.57 和 0a84917a 二进制做出早期版本的回切目录，检查修复（`FBUP_CASE` 为 plain、`object-only`）和拒绝（`object-gone`：目录和对象存储都不变）。

## 升级影响

**早期版本的回切目录。** 只影响在 v0.5.57 或 0a84917a 上做过真实回切（A→B→A，A 先追平 B）的任务。认法：同一个 binlog 序号有几份文件（无后缀加 `.sealed.eN` / `.open.eN`），`.source-chain` 只有 A 和 B，事件里有继续复制的 B→A 切换。升级后：

1. 读接口给出 `storage_alert`（`STORAGE_INCONSISTENT`，`detail` 为 `legacy failback: ...`），`/replay` 和 `/window` 停在第一份有问题的文件之前。修复之前不要越过这一点恢复。
2. **修复。** 第一次 Start（包括进程启动时的自动续跑）在每份文件都能确定只属于一段时修复目录：把后一段改名为 `{身份}~{n}.`，补回第一段的目录行并标成待重新上传、核对校验和，修正 checkpoint 的文件名，`.source-chain` 写成 A、B、A，记一条 `STORAGE_REPAIRED`。不删任何文件。`.legacy-failback-repair` 计划让下一次 Start 接着做完被中断的修复；QA 在每一步杀掉进程，每次重启都完成了修复，回放结果与源一致。
3. **拒绝。** 某份文件的事务不属于任何一段或属于多段、改名目标已存在、读不了文件，或第一段的文件无法从对象存储取回时，Start 以 `STORAGE_INCONSISTENT` 失败，写出文件名（和对象键），磁盘、目录、对象存储都不改。之后：恢复时不要越过 `storage_alert.segment`（它之前的 `valid_segments` 仍可用），对现在的主库按它的 `@@gtid_executed` 新建任务，旧任务和它的对象留作取证；需要那段时间的数据时，用 `mysqlbinlog --include-gtids` / `--exclude-gtids` 按 GTID 拼。想修复的话，按故障处理 5.4「手工取回」（以及「已知行为」里的说明）把第一段的文件放回去，再 Start。
4. **孤儿对象。** 早期版本把一些文件传到了修复后的目录不再引用的对象键下。`STORAGE_REPAIRED` 在 `orphaned_objects=` 后列出这些键，其中有的可能根本不存在（旧版本没传成功）。服务不会删它们。确认能用修复后的任务恢复之后，再手工删除。
5. 识别依赖元数据库里的切换事件。用早于这些事件的备份恢复元数据库会丢掉它们，这样的目录就认不出是早期版本的回切目录。

健康的目录只读每台重新进入的服务器从切换点开始的文件。除了上面的第一段取回，只检查本地磁盘上的文件。

v0.5.58 的规则仍然成立：从 v0.5.57 升级后，因为多出来的 Rotate 显示 `storage_alert` 的 GTID 任务已经损坏，不要 Start，按 `restart_gtid_set` 恢复。

没有新迁移。已经在 schema 6 的数据库保持 schema 6。确认 `SELECT version, dirty FROM schema_migrations` 是 `(6, 0)`。`migrations/` 仍是 `000001` 到 `000006`，没有 `000007`。`minRequiredSchemaVersion` 仍是 6：v0.5.59 在 schema 5 上不启动，监听之前以退出码 1 退出，信息里有 `schema version too old` 和 `./migrate up`。数据库还不是 schema 6 时，先按 [v0.5.56 升级](release-notes-v0.5.56.md) 操作。地板仍是 v0.5.51。没有新配置项。这一版不是 ADR 0005 的步骤，ADR 0005 没有改。

## 已知行为

以下 P3 是 PR #297 的 QA 发现的，都不会静默丢数据。

- 第一段的对象读不到、Start 已经拒绝之后，`storage_alert.detail` 结尾仍是 `(Start repairs)`，`message` 仍说 Start 会取回。告警是读目录算出来的，不知道对象已经没了。以 `last_error` 为准：它写出文件名和对象键，并说明什么都没改。再 Start 只会重复同样的拒绝。
- 从旧主库手工取回：A 上的同名 binlog 还包含 A 回切后写的事务，原样放回永远对不上第一段，Start 会拒绝（`holds transactions that no stint ... stored`）。先按 A→B 那条 `SOURCE_SWITCHOVER` 事件里的位置截断（`at <文件>:<pos>`，然后 `head -c <pos> <文件>`），核对 GTID，放回，再 Start。QA 用这个办法修复成功，回放结果与源一致。
- 链中间某个封存分段的字节没了（本地文件和对象都被删，或只在本地的文件被删）时，`/window` 报 `segment is not readable` 且不连续，但 `/replay` 仍列出这个分段（`location` 为 `bucket` 或空），没有 `warning`。下载返回 404，`mysqlbinlog` 报 `Could not open log file` 停下，后面的文件不会被套用。恢复前先看 `/window` 的 `breaks`。
- `stop_datetime` 仍按事件头的秒截断。知道出问题的 GTID 时用 `stop_gtid`。源上手工 `GTID_NEXT` 造成的洞，`/window` 仍报 `gtid hole`。

## QA 摘要

BinlogServerQA，PR #297 head `53db9757`，MySQL 8.0.46，用真实 v0.5.57 → 0a84917a 做出的早期回切目录。PASS，没有 P0/P1/P2。

- 第一段只剩对象（混合和仅 INSERT）：修复成功，取回的文件逐字节一致，`/window` 连续，回放校验和与 GTID 集合与源一致。
- 对象也没了：拒绝；Start 前后磁盘、目录、对象存储逐字节相同。
- 修复过程中在七个时刻 `kill -9`（取回开始、取回中途、取回之后、journal、改名、目录、上传）：每次重启都只完成一次修复，回放与源一致。
- 回归：32 分钟重连浸泡（74,238 个事务，42 轮 KILL，29 次 FLUSH，15 次代理断开），`FAILED`、`STREAM_REGRESSION`、`storage_alert` 都是 0；#293 redump、带 `GTID_NEXT` 洞的 MTA 副本、真实 A→B→A 回切、kill-cut 都回放一致。schema 仍是 6。
